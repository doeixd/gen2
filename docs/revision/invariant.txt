## Recommended model

```ts id="qbi13k"
const RuleNotSqlLowerable = gen.diagnostic.define(
  "RULE_NOT_SQL_LOWERABLE",

    severity: "error",

    params: {
      rule: gen.param.node(RuleNodeKind),
      target: gen.param.target(),

        "unsupported_operation",
        "unsupported_type",
```

Yes. In Gen2, an **invariant should basically be a typed rule/predicate plus diagnostic and enforcement metadata**.

I would model it as a first-class semantic node, not just a rule with a string attached.

Something like:

```txt id="mloc8r"
Invariant =
  predicate expression
  subject/scope
  severity
  diagnostic messages
  error code
  enforcement surfaces
  provenance
  remediation hints
  target lowering metadata
  observability metadata
```

A rule says:

```txt id="i9w1ey"
This boolean condition is true or false.
```

An invariant says:

```txt id="uycyor"
This condition must hold at this point in the system,
and if it does not, here is the typed failure object.
```

So yes: the predicate can reuse the same rule-expression system described in the README, where rules are pure boolean expressions over the universal expression system.  But an invariant carries more operational meaning than a generic rule.

For example:

```ts id="40kgvo"
const userEmailIsUnique = gen.invariant("userEmailIsUnique", {
  subject: User,
  when: ({ user }) =>
    User.where((u) => u.email.eq(user.email))
      .count()
      .lte(1),

  code: gen.error.code("USER_EMAIL_NOT_UNIQUE"),

  message: {
    user: "That email address is already in use.",
    developer: "User.email must be globally unique.",
    backend: "Invariant violation: duplicate User.email.",
  },

  severity: "error",

  enforce: [
    gen.enforce.database.uniqueIndex(),
    gen.enforce.server.guard(),
    gen.enforce.form.validation(),
  ],
});
```

That creates semantic facts like:

```txt id="lxjo3p"
Node(Invariant): userEmailIsUnique
Edge(HasPredicate): userEmailIsUnique -> Expr<boolean>
Edge(Reads): userEmailIsUnique -> User.email
Edge(AppliesTo): userEmailIsUnique -> User
Edge(EmitsDiagnostic): userEmailIsUnique -> USER_EMAIL_NOT_UNIQUE
Edge(LowersTo): userEmailIsUnique -> DatabaseUniqueIndex
Edge(LowersTo): userEmailIsUnique -> ServerValidation
Edge(LowersTo): userEmailIsUnique -> FormValidation
```

Thought for 15s

MLIR’s model is close to what you’re describing, but it is more compiler-oriented than app/user-error-oriented.

MLIR separates:

Invariant definition
  -> encoded in op/type/attribute constraints, traits, interfaces, or verifier code

Invariant checking
  -> verifier runs over IR

Failure reporting
  -> diagnostic attached to a source/location

In MLIR, invariants are usually not first-class runtime objects with user messages, backend messages, error codes, remediation metadata, etc. They are mostly validity rules for IR.

For example, MLIR operation definitions use ODS/TableGen as a “single source of truth” for operation facts, including operands, attributes, results, constraints, builders, verifiers, parsers, printers, and generated utilities.

The invariant mechanisms are roughly:

ODS constraints
  Declarative constraints on operands, attributes, results, regions, etc.

Traits
  Reusable properties/invariants, e.g. same operand/result type, commutative, terminator, no side effects.

Interfaces
  Generic semantic contracts that passes can query without knowing the exact op.

Custom verifier
  C++ code for invariants too specific or complex for declarative constraints.

Region verifier
  Separate verifier for invariants that need to inspect nested operations.

MLIR’s own docs say traits often describe verification constraints on valid IR and allow complex invariants to be captured and checked. Traits are also described as reusable properties/constraints across operations, attributes, types, etc. Interfaces let analyses and transformations operate generically across dialects without hardcoding knowledge of every operation.

The verifier ordering is also instructive. MLIR verifies structural traits first, then ODS-generated verifyInvariants, then trait/interface verifiers, then custom op verifiers. If the op has regions, it has a second phase for region-aware verifiers after nested operations are verified.

That maps beautifully to Gen2:

Gen2 type/shape constraints
  ~= MLIR ODS constraints

Gen2 traits/laws
  ~= MLIR traits

Gen2 protocols
  ~= MLIR interfaces

Gen2 verify passes
  ~= MLIR verifier

Gen2 dialect-specific checks
  ~= custom op/type/region verifiers

Gen2 target legalization
  ~= later compiler legality checks

Where MLIR is especially relevant for your design is diagnostics.

An MLIR diagnostic has four core pieces:

source location
severity
diagnostic arguments
metadata

Severity can be error, note, remark, or warning; metadata is attached for diagnostic handlers/filtering and is not part of the printed message. Diagnostics are emitted through DiagnosticEngine, but operations usually use convenience methods like emitError, emitWarning, emitRemark, or emitOpError; emitOpError prefixes the diagnostic with the operation name.

That means MLIR’s diagnostic model is closer to:

Diagnostic {
  location
  severity
  message arguments
  metadata
  optional notes
}

than to:

Invariant {
  predicate
  userMessage
  backendMessage
  errorCode
  remediation
  httpStatus
  telemetry metadata
}

For Gen2, I would copy MLIR’s structure, but make it more application-aware.

MLIR-style:

op verifier fails
  -> emit diagnostic at op location

Gen2-style:

invariant/rule verifier fails
  -> emit typed diagnostic
  -> attach source graph location
  -> attach user/developer/backend messages
  -> attach error code
  -> attach target surfaces
  -> attach remediation
  -> optionally lower into runtime error schema

So your instinct is right, but Gen2 should probably go further than MLIR.

MLIR invariants are mostly about IR well-formedness:

This op must have one region.
This operand type must equal the result type.
This attribute must be valid.
This terminator must be present.
This symbol reference must resolve.

Gen2 invariants would cover both IR well-formedness and application semantics:

This action must be guarded.
This client boundary must not expose sensitive fields.
This operation must be idempotent if used with at-least-once delivery.
This rule must be SQL-lowerable if emitted as RLS.
This user-facing form must handle this invariant violation.
This mutation must have a rollback plan if optimistic.

MLIR’s testing story is also worth copying. MLIR has diagnostic verification tests where expected diagnostics are embedded in .mlir files, useful for checking malformed IR, operation invariants, and analysis results. Gen2 could have the equivalent:

expectGraphDiagnostic(graph, {
  code: "GEN2_RULE_NOT_SQL_LOWERABLE",

  severity: "error",
});

1. Separate invariant definitions from diagnostic occurrences.

2. Make invariant predicates use the same typed expression/rule system.

3. Make diagnostics first-class typed graph/runtime objects.

4. Attach locations everywhere:

5. Use MLIR-style verifier layering:

6. Keep metadata machine-readable, not just strings.

I’ll ground this in MLIR’s own docs/source because the distinction between diagnostics, verifiers, traits, and invariants is pretty specific.

Thought for 25s

MLIR separates invariants from diagnostics.

The rough model is:

Invariant / constraint:
  "What must be true for this IR to be valid?"

Verifier:
  Code generated or written to check that invariant.

Diagnostic:
  Structured compiler message emitted when verification fails.

MLIR does not usually model invariants as first-class “rule nodes with user/backend messages.” Instead, invariants live in a few places.

1. ODS constraints

MLIR operations are often defined with ODS, the Operation Definition Specification, using TableGen. ODS lets you declare facts about an operation: operands, results, attributes, traits, constraints, builders, parser/printer, and verifier hooks. MLIR’s docs explicitly describe ODS as a “single source of truth” for operation facts and say it can generate verification, builders, accessors, parsing, printing, and analysis helpers.

Example shape:

def MyOp : Op<"my_op", [
  SameOperandsAndResultType,
  Pure
]> {
  let arguments = (ins AnyTensor:$input);
  let results = (outs AnyTensor:$output);
}

That says, semantically:

MyOp must have input/output type agreement.
MyOp has no side effects.

Those constraints become generated verifier code.

2. Traits

Traits encode reusable properties or constraints of operations, attributes, or types. MLIR docs say traits can describe properties like “no side effects” or “output has the same type as input,” and the LangRef says traits often describe verification constraints on valid IR.

So a trait is a bit like a reusable invariant/law marker:

SameOperandsAndResultType
Commutative
Terminator
IsolatedFromAbove
HasParent<ModuleOp>

This maps pretty directly to your Gen2 idea of operation traits/laws.

3. Declarative constraints / predicates

ODS constraints can be built from predicates. MLIR has CPred as an atomic predicate, plus combinators like And, Or, and Neg. The docs describe constraints as central to operation verification and matching, and say a constraint may apply to a single attribute/result/operand, multiple operands/results, or the operation itself.

Example from the MLIR style of thinking:

def HasSomeProperty :
  AttrConstraint<CPred<"HasSomeProperty($_self)">,
                 "has some property">;

So yes: MLIR has something predicate-like. But the predicate is usually a TableGen/C++ verifier predicate, not an IR-level semantic rule expression.

4. Custom verifiers

For anything ODS cannot express, an op can define custom verifier methods:

let hasVerifier = 1;
let hasRegionVerifier = 1;

MLIR generates method declarations like LogicalResult verify() / verifyRegions(), and you implement additional checks in C++. The verification order is structured: structural traits first, then ODS-generated verifyInvariants, then trait/interface verifiers, then custom verifiers; region verifiers run later after nested operations are verified.

That is very relevant for Gen2. You probably want a similar staged system:

structural verification
type verification
trait/law verification
local node verification
region/body verification
global graph verification
target legalization verification
5. MLIR verifier discipline: mostly local invariants

This is a key MLIR lesson.

MLIR’s developer guide says verifiers should generally verify local aspects of an operation and should not follow def-use chains or inspect non-local producer/user relationships. It also says that when an invariant fails, the IR is considered invalid and compilation aborts; passes assume valid input and must produce valid output.

That means MLIR distinguishes:

Local validity:
  This op is structurally/type-wise valid.

Analysis facts:
  This op's operand was produced by a constant with value 10.

Optimization facts:
  This can be folded / canonicalized / lowered.

Undefined behavior:
  Some bad runtime cases may be legal IR but semantically undefined.

For Gen2, I would copy the principle but adapt it:

Node verifier:
  local structure and type invariants

Graph verifier:
  global semantic invariants

Target verifier/legalizer:
  "Can this be emitted to Postgres/React/Alchemy/etc.?"

Business invariant:
  first-class domain contract with typed violation metadata
6. Diagnostics

MLIR diagnostics are structured compiler messages. A diagnostic has:

source location
severity: error / note / remark / warning
arguments used to build the message
metadata
attached notes

The docs state that diagnostics contain source location, severity, diagnostic arguments, and metadata; metadata can be used by handlers for filtering and is not part of the output message.

MLIR operations have helper methods:

op->emitError(...)
op->emitWarning(...)
op->emitRemark(...)
op->emitOpError(...)

emitOpError() prefixes the message with the operation name.

Notes are attached to a primary diagnostic:

op->emitError("...").attachNote(noteLoc) << "...";

MLIR also has debugging options to attach the current operation or stack trace to diagnostics, useful for verifier failures.

7. Tests expect diagnostics

MLIR has diagnostic tests using -verify-diagnostics, where test files contain comments like:

// expected-error@+1 {{invalid predicate attribute specification: "foo"}}
%result = arith.cmpf "foo", %a, %a : f32

The testing guide says diagnostic tests are used for verifying operation invariants, checking analysis results, and detecting malformed IR.

This is another thing Gen2 should steal: generated examples/tests that assert exact diagnostics.

The important comparison for Gen2

MLIR’s model is roughly:

Constraint / trait / verifier
  -> emits diagnostic
  -> invalid IR
  -> compiler stops

Gen2 probably wants:

Invariant node
  -> predicate / rule expression
  -> typed violation object
  -> diagnostics
  -> possible generated runtime errors
  -> possible UI validation
  -> possible DB constraint
  -> possible API error schema
  -> possible tests/docs/telemetry

So Gen2 should be more semantic and user-facing than MLIR.

MLIR diagnostics are compiler diagnostics. They are not designed around:

backend log message
HTTP status
form field path
business error code
localization key
retryability
telemetry category
public/private exposure

For Gen2, those should absolutely be modeled.

A good Gen2 design would combine both:

Then separately:

  Does this invariant have a boolean predicate?
  Does the predicate only reference variables in scope?
  Is the error code unique?

  Can this error shape lower to OpenAPI?

## Example: generic field invariant

```ts
const RequiredField = gen.invariant.family("RequiredField", {
  params: {
    entity: gen.param.entity(),
    field: gen.param.fieldOf("entity"),
  },

  infer: ({ entity, field }) => ({
    subject: entity,
    path: field,
    valueType: field.type,
  }),

  predicate: ({ subject, field }) =>
    subject.field(field).isPresent(),

  diagnostic: ({ entity, field }) => ({
    code: gen.error.code(`${entity.name}_${field.name}_REQUIRED`),
    user: `${field.label} is required.`,
    developer: `${entity.name}.${field.name} must be present.`,
    severity: "error",
  }),
});
```

Then:

```ts
const UserEmailRequired = RequiredField({
  entity: User,
  field: User.fields.email,
});
```

The compiler can infer:


## Invariant families vs invariant instances

I would make this distinction explicit.

```txt
InvariantFamily<TParams, TSubject, TPredicate, TViolation>
  Generic invariant template.

InvariantInstance<TFamily, TResolvedParams, TSubject, TViolation>
  Concrete invariant attached to the graph.
```

For example:

```txt
Family:
  Unique<Field>

Instance:
  User.email is unique
```

or:

```txt
Family:
  AtLeastOnceDeliveryRequiresIdempotency<Dispatch>

Instance:
  sendEmailWhenUserArchived must declare idempotency
```

That gives you reuse without losing type safety.

## Inference should flow from parameters

You want the user to write as little as possible:

```ts
gen.invariant.unique(User.fields.email)
```

and have Gen2 infer:

```txt
entity = User
field = email
field type = Email
storage column = users.email
database constraint kind = unique
form field = email
HTTP error = 409 Conflict
safe user message = "That email is already in use."
```

The generic invariant should be parameterized over semantic capabilities, not just raw TypeScript types.

For example, `UniqueField` should not accept any value. It should require something like:

```txt
FieldRef<T>
  must belong to Entity
  must be comparable
  must be storage-lowerable if database enforcement is requested
  must have stable encoded representation
```

So the constraint is semantic:

```ts
const UniqueField = gen.invariant.family("UniqueField", {
  params: {
    field: gen.param.field({
      traits: [Comparable, Persisted, HasStableEncoding],
    }),
  },
  ...
});
```

That is better than saying “any `string` field can be unique.” The invariant cares about graph capabilities.

## Users should be able to define custom invariant types

For an AI app generator, this is important. Many app-specific business rules will not fit built-ins.

Example:

```ts
const BookingDoesNotOverlap = gen.invariant.family("BookingDoesNotOverlap", {
  params: {
    booking: gen.param.entity(),
    start: gen.param.field({ type: gen.type.datetime() }),
    end: gen.param.field({ type: gen.type.datetime() }),
    resource: gen.param.field(),
  },

  predicate: ({ booking, start, end, resource }) =>
    booking.noOther((other) =>
      other.field(resource).eq(booking.field(resource))
        .and(other.field(start).lt(booking.field(end)))
        .and(other.field(end).gt(booking.field(start)))
    ),

  diagnostic: {
    code: gen.error.code("BOOKING_OVERLAPS_EXISTING_BOOKING"),
    user: "This time overlaps with an existing booking.",
    developer: "Bookings for the same resource must not overlap.",
    severity: "error",
    httpStatus: 409,
  },

  lowerings: {
    postgres: gen.lowering.exclusionConstraint().whenSupported(),
    server: gen.lowering.runtimeCheck(),
    client: gen.lowering.asyncValidation(),
    tests: gen.lowering.propertyTests(),
  },
});
```

Then a generated booking app can instantiate it:

```ts
BookingDoesNotOverlap({
  booking: Reservation,
  start: Reservation.fields.startsAt,
  end: Reservation.fields.endsAt,
  resource: Reservation.fields.roomId,
});
```

That is exactly the kind of app-specific invariant an AI generator should be able to synthesize.

## The type shape should include capabilities

A good invariant type might look conceptually like this:

```ts
type InvariantFamily<
  Params,
  Subject,
  Predicate extends Expr<boolean>,
  Violation,
  Requirements,
  Effects,
  Traits,
  Lowerings
> = ...
```

Where:

```txt
Params
  Generic parameters needed to instantiate the invariant.

Subject
  Entity, action, dispatch, field, boundary, UI slot, deployment resource, etc.

Predicate
  Typed expression that must hold.

Violation
  Typed failure object.

Requirements
  Context needed to check it.

Effects
  Usually none for pure invariants, but runtime checks may require reads.

Traits
  pure, client-safe, SQL-lowerable, storage-lowerable, async-checkable, etc.

Lowerings
  Database constraint, server validation, form validation, deployment check, tests, docs.
```

This allows the compiler to say:

```txt
This invariant is valid.
This invariant is valid but only server-checkable.
This invariant cannot lower to SQL.
This invariant cannot run on the client because it reads sensitive data.
This invariant needs an async uniqueness check.
This invariant needs an index to be efficient.
```
