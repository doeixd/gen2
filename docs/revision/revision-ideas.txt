Yes. After the kernel rebase, most of these folders should **not remain as independent architectural peers**.

Right now the repo has many subsystem folders, and `GenContext` stores many separate registries for entities, relations, functions, policies, routes, views, providers, workflows, reactions, resources, queues, and so on. That is the thing we want to eliminate: not the concepts, but the parallel sources of truth. The useful concepts should survive as **dialects, frontends, target emitters, or compatibility shims** over one graph.

## What happens to each current folder

| `src/query`         | **Merge into `dialects/callable` + `dialects/reactivity`**                            | Query is a readable callable with key/read edges. ## What gets combined

These should collapse into fewer conceptual dialects:

```txt
entity + relation + parts of types
  -> dialects/domain

types + merge + operation pieces
  -> kernel/type + dialects/operation

expression + rules
  -> dialects/expression + dialects/rule

function + query + crud action pieces
  -> dialects/callable

api + router + boundary
  -> dialects/boundary + targets/http/router/rpc

context + requirements + services
  -> dialects/core/context + requirement + provider

state + hydration + parts of reactivity
  -> dialects/resource + placement + boundary

events + reaction + offline + orchestration
  -> dialects/event + dispatch + queue + workflow

ui + forms + list + editor + admin
  -> dialects/ui + admin preset

storage + db
  -> dialects/storage + targets/postgres/sqlite
```

These should be treated as **targets/adapters**, not core semantics:

```txt

  src/adapters/effect or src/targets/effect

TanStack Query / Effect Atom
  src/adapters/tanstack-query
  src/adapters/effect-atom

React / Solid / React Native
  src/targets/react
  src/targets/solid
  src/targets/react-native

Postgres / SQLite
  src/targets/postgres
  src/targets/sqlite

  src/targets/openapi

Docs/tests/devtools
  src/targets/docs
  src/targets/tests
```

Adapters should not define canonical business semantics. They translate graph semantics into external ecosystems.

## What gets simplified

A lot of folders become much smaller because they no longer own registries/checkers/emitters.

For example, `ui` no longer needs to manually stitch together views, slots, styles, behaviors, forms, themes, platforms, renderers in one flat input object. Instead:

```txt
ViewNode
SlotNode
StyleNode
BehaviorNode
FormNode
DesignSystemNode

StyleAttachesToSlot edge
BehaviorAttachesToSlot edge
FormSubmitsAction edge
ViewUsesDesignSystem edge
```

Then `checkUi` becomes dialect verify passes.

Similarly, `reaction` no longer needs its own complete checker. It becomes:

```txt
DispatchNode
RuleTrigger edge
RunsAction edge
DeliveryPlan node
IdempotencyPlan node
OutboxPlan node
```

Then generic dispatch/effect passes check idempotency, delivery, unsafe inline execution, outbox mismatch, etc.

Users should not have to write low-level graph code.

This should still exist:

```ts
gen.entity(...)
gen.rule(...)
gen.query(...)
gen.action(...)
gen.reactivity.key(...)
gen.ui.view(...)
gen.form(...)
gen.event(...)
gen.reaction(...)
```

But internally those are frontends over:

```txt
Graph.addNode
Graph.addEdge
Graph.addType
Graph.addExpr
Graph.applyTrait
```

## The new mental model

After the rebase:

```txt
kernel
  defines what a semantic graph is

dialects
  define vocabularies over that graph

gen
  gives ergonomic builders for dialects

passes
  verify, derive, canonicalize, legalize, lower, emit

targets
  generate artifacts from legalized graph IR

adapters
  interop with external libraries
```

So the answer is:

> Most current folders are still conceptually needed, but not as separate sources of truth. They should be collapsed into dialects, targets, adapters, or public builder namespaces over the new kernel graph. The only permanent core should be `kernel`, `dialects`, `targets`, `adapters`, `gen`, `lifecycle`, and the root exports.
