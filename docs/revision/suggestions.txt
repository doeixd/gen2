### How the TypeScript Magic Works under the hood

To make `.use()` work without destroying the language server's performance, the implementation in `@gen2/core` looks like this:

```typescript

export class GenBuilder<TNamespaces extends Record<string, any> = {}> {
  private graphContext = new GraphContext();
  private namespaces: TNamespaces = {} as TNamespaces;

  // The magic is here: We take the current TNamespaces, and intersect it
  // with a new Record holding the Dialect's builders.
  use<
    Name extends string, 
    Builders
  >(
    dialect: DialectDef<Name, Builders>
  ): GenBuilder<
    // Compute is a utility type that flattens the intersection so tooltips are readable
    Compute<TNamespaces & { [K in Name]: Builders }>
  > {
    
    // Register the node/edge kinds into the internal graph registry
    this.graphContext.registerDialect(dialect);
    
    // Instantiate the ergonomic builders and bind them to the namespace
    const newBuilders = dialect.builders(this.graphContext);
    this.namespaces[dialect.name as string] = newBuilders;

    // Return a new builder instance casted to the intersected type
    return new GenBuilder<any>() as any; 
  }

  // Escape hatch that unwraps the builder into the final `gen` object
  buildVocab(): Compute<TNamespaces & CoreGenHelpers> {
    return {
      ...this.namespaces,
      createApp: () => new AppRegistry(this.graphContext),
    } as any;
  }
}

Context
  What ambient capabilities are required or provided at runtime.

Scope
  What names, refs, variables, operations, placements, and capabilities are visible during construction or lowering.

Resource
  A durable thing the app depends on, manages, reads from, writes to, deploys, or exposes.
```

The revised phase plan already points this way: it says modules become dialects, context/provider concepts become graph IR, requirements and providers are nodes/edges, and final semantic state should live in the graph rather than old top-level registries.  The revised core doc also moves `Provider`, `Requirement`, `StorageContainer`, `ReactiveResource`, etc. out of the kernel and into graph-backed stdlib concepts built from `Node`, `Edge`, `Trait`, `Type`, `Expr`, and `Pass`. 

## Modules

I would not make “module” mean only one thing.

There are at least three useful module concepts:

```txt id="w42fol"
1. Code module
   A TypeScript/file/package boundary.

2. Graph module
   A namespace/ownership boundary for semantic objects.

3. Dialect module
   A package of semantic vocabulary: node kinds, edge kinds, traits, protocols, passes, lowerings.
```

For Dirived, the most important one is the **graph module**.

A graph module should group semantic definitions:

```txt id="g7xraz"
billing module
  Customer
  Subscription
  Invoice
  canManageBilling
  createInvoice
  listInvoices
  BillingSettingsView
```

Represent that as either:

```txt id="hzewxo"
Module metadata on symbols/refs
```

or, when you need richer behavior:

```txt id="8objz7"
Node(kind: Module)
Edge(kind: Contains): BillingModule -> Customer
Edge(kind: Contains): BillingModule -> createInvoice
Edge(kind: Exports): BillingModule -> listInvoices
Edge(kind: Imports): BillingModule -> AuthModule
```

My recommendation:

```txt id="qj2lu7"
Use module/namespace fields for simple identity.
Use Module nodes only when modules need ownership, visibility, dependency analysis, docs, devtools, plugin boundaries, or emitted artifact grouping.
```

So the kernel does not need “Module” as a hard primitive. But the stdlib almost certainly should have a module/package dialect.

## Context

Context should be a first-class stdlib/dialect concept.

This is how actions, queries, rules, providers, boundaries, and generated runtime code describe what they need from the environment.

Examples:

```txt id="e4zne5"
AuthSession
CurrentUser
CurrentTenant
Clock
Database
EmailService
Logger
FeatureFlags
RequestInfo
DeploymentEnv
```

Graph model:

```txt id="s6z6bo"
Node(kind: Service)
Node(kind: Context)
Node(kind: Requirement)
Node(kind: Provider)

Edge(kind: Requires): archiveUser -> AuthSession
Edge(kind: Requires): sendEmail -> EmailService
Edge(kind: Provides): AuthSessionProvider -> AuthSession
Edge(kind: Provides): DatabaseProvider -> Database
Edge(kind: PlacedIn): AuthSessionProvider -> ServerRequest
```

This gives the compiler questions it can answer:

```txt id="9drr7e"
Does this action have all required providers?
Can this provider run in this placement?
Can this client boundary access this context?
Does provider lifetime satisfy consumer lifetime?
Does the target know how to lower this service?
```

This is also where Effect interop fits nicely:

```txt id="zzi38r"
Dirived Service node
  -> Effect Context.Service

Dirived Provider node
  -> Effect Layer

Dirived Requires edge
  -> Effect requirements
```

So yes: context should be graph-backed, typed, and provider/requirement-oriented.

## Scope

Scope is different.

Scope is mostly a **compiler/builder concept**, not always a durable semantic object.

You need scope for things like:

```txt id="0a3ql3"
Which variables are visible in this rule?
Which entity fields are in scope?
Which operations are allowed here?
Are we building a query, action, rule, UI view, target lowering, or runtime boundary?
Are we in client, server, database, worker, or deployment scope?
Which refs may be captured?
Which values are local expression values vs stable graph refs?
```

Example:

```ts id="5zmppx"
gen.rule("canArchiveUser", {
  vars: { actor: User, user: User },
  when: ({ actor, user }) =>
    actor.role.eq("admin")
      .or(actor.organizationId.eq(user.organizationId)),
});
```

Inside `when`, the scope knows:

```txt id="o6v564"
actor is a local value of type User
user is a local value of type User
actor.role points to FieldRef<User.role>
user.organizationId points to FieldRef<User.organizationId>
only pure expression operations are allowed
effects are not allowed
field reads should be extracted
```

I would model scope as:

```txt id="90osg3"
ScopeFrame
  lexical variables
  available refs
  phase
  placement
  target capabilities
  allowed protocols
  parent scope
```

Most scope frames can be ephemeral compiler data. But when useful for diagnostics or devtools, you can materialize them:

```txt id="1e6s7r"
Diagnostic:
  cannot capture server-only AuthSession in client UI scope
```

That diagnostic should point to the relevant scope chain.

So:

```txt id="7jdzmd"
Scope is not always a node.
Scope becomes graph-visible when it affects diagnostics, provenance, lowering, or agent edits.
```

## Resources

“Resource” is overloaded, so I would define it carefully.

There are several resource families:

```txt id="l6v0es"
Runtime resources
  Database, EmailService, Logger, Clock, AuthSession.

Storage resources
  Table, Bucket, KV namespace, Queue, Stream, Outbox, Index.

Reactive resources
  Query-backed data, local cache, live subscription, materialized view.

Deployment resources
  Worker, Lambda, database instance, secret, cron, bucket, queue.

UI resources
  Design system, component registry, theme, asset catalog.
```

The common abstraction is:

```txt id="c3y7lg"
Resource = graph node representing a capability, state container, external system, or deployable thing.
```

Then edges define how it participates:

```txt id="nzq9f1"
Action requires Resource
Provider provides Resource
Entity storedIn Resource
Field mapsTo Resource
Dispatch uses Resource
Boundary exposes Resource
Target lowersTo Resource
Artifact generatedFrom Resource
```

Examples:

```txt id="yytlt1"
sendArchiveEmail requires EmailService
EmailProvider provides EmailService
EmailService requires SENDGRID_API_KEY Secret

archiveUser emits UserArchived
UserArchived dispatch uses OutboxQueue
OutboxQueue lowersTo CloudflareQueue

User entity storedIn PostgresDatabase
User.email mapsTo users.email column
```

This is exactly why first-class edges matter. A resource is not interesting by itself. It becomes meaningful through relationships.

From this, Dirived can derive:

```txt id="qavxgj"
server action requirements

```

## My recommended taxonomy

I would define them like this:

```txt id="tycqe0"
Dialect
  A semantic vocabulary package.

Module
  A graph namespace/ownership/import/export boundary.

Context
  A typed runtime environment surface.

Requirement
  A need for a context/service/capability.

Provider
  Something that satisfies a requirement.

Scope
  A lexical/compiler/placement environment for building or lowering graph facts.

Resource
  A durable runtime, storage, reactive, UI, or deployment capability represented as a node.

Capability
  A trait-like claim about what a resource, target, type, operation, or provider can do.
```

The crisp design rule:

```txt id="m4yukg"
Modules organize graph facts.
Context describes ambient runtime needs.
Scope controls what can be referenced or built.
Resources are semantic/deployable capabilities.
Edges connect all of them.
```

So yes — we have the concepts. I would just make sure they land in the right layer:

```txt id="2rqmd7"
Kernel:
  Node, Edge, Type, Expr, Trait, Protocol, Graph, Pass, Id/Ref

Stdlib/dialects:
  Module, Context, Requirement, Provider, Scope, Resource

Targets:
  Effect services/layers, Postgres resources, Alchemy deployment, React providers, etc.
```

That gives Dirived enough structure without bloating the kernel.
