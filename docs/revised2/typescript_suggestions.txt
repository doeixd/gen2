The current direction is already good: `defineEdgeFromKind`, `nodesOfKindDef`, `edgesOfKindDef`, and `defineDialect` are using typed witnesses instead of pure strings. The biggest remaining problem is that those witnesses are **not carried far enough**. Types are inferred at creation time, then erased into broad `KernelGraph`, `KernelEdge`, `KernelObjectRef`, `string`, or `Dialect` later.

Your own cheat sheet’s core rule fits these files well: create typed values first, then let APIs infer from those values; avoid user-written casts; keep the captured generic alive through derived APIs. 

## 1. Make `KernelGraph` generic over its registered contents

Right now `KernelGraph` stores broad maps:

```ts
nodes: ReadonlyMap<string, KernelNode>;
edges: ReadonlyMap<string, KernelEdge>;
```

and `registerNode` / `registerEdge` return plain `KernelGraph`, so every registration loses the specific node/edge type immediately.  

A better public API would accumulate graph state:

```ts
type KernelGraphState = {
  types: Record<string, KernelType<any>>;
  nodes: Record<string, KernelNode<any, any, any, any>>;
  edges: Record<string, KernelEdge<any, any, any>>;
  traits: Record<string, TraitDef>;
};

type KernelGraph<TState extends KernelGraphState = EmptyGraphState> = {
  readonly id: KernelId<"graph">;
  readonly nodes: ReadonlyMap<keyof TState["nodes"] & string, TState["nodes"][keyof TState["nodes"] & string]>;
  readonly edges: ReadonlyMap<keyof TState["edges"] & string, TState["edges"][keyof TState["edges"] & string]>;
};
```

Then registration can preserve state:

```ts
function registerNode<
  const TGraph extends KernelGraph<any>,
  const TNode extends KernelNode<any, any, any, any>,
>(
  graph: TGraph,
  node: TNode,
): AddNode<TGraph, TNode>;

function registerEdge<
  const TGraph extends KernelGraph<any>,
  const TEdge extends KernelEdge<any, any, any>,
>(
  graph: TGraph,
  edge: TEdge,
): AddEdge<TGraph, TEdge>;
```

This would let later graph queries infer from what was actually registered.

## 2. Add a fluent graph builder for better DX

The functional API is clean, but repeated immutable calls get noisy:

```ts
let graph = createKernelGraph();
graph = registerNode(graph, a);
graph = registerEdge(graph, e);
```

Since registration accumulates meaningful type state, this is a good place for a type-state builder:

```ts
const graph = createGraph()
  .node(userNode)
  .node(sessionNode)
  .edge(ownsEdge)
  .edge(dependsOnEdge)
  .done();

graph.nodes.of(USER_NODE_KIND);
// typed as user nodes only
```

Shape:

```ts
type GraphBuilder<TState extends KernelGraphState> = {
  node<const TNode extends KernelNode<any, any, any, any>>(
    node: TNode,
  ): GraphBuilder<AddNodeState<TState, TNode>>;

  edge<const TEdge extends KernelEdge<any, any, any>>(
    edge: TEdge,
  ): GraphBuilder<AddEdgeState<TState, TEdge>>;

  done(): KernelGraph<TState>;
};
```

This follows the type-state pattern from the cheat sheet: use fluent builders when chained calls accumulate meaningful type information. 

## 3. Make `KernelObjectRef` kind-aware and target-aware

`KernelEdgeEndpoint` currently stores:

```ts
target: KernelObjectRef;
```

which means endpoint roles know their role ID, but not what kind of object they are allowed to point to. 

I’d make refs carry object kind, node/edge/type kind, and ID:

```ts
type KernelRef<
  TObjectKind extends "node" | "edge" | "type" | "trait",
  TKind,
  const TId extends string,
> = {
  objectKind: TObjectKind;
  kind: TKind;
  id: KernelId<TObjectKind>;
  name?: string;
};
```

Then endpoints can be constrained:

```ts
type EndpointRoleDef<
  const TName extends string,
  TTarget extends KernelRef<any, any, any> = KernelRef<any, any, any>,
> = {
  name: TName;
  target: TTarget;
};
```

So an edge kind can say:

```ts
const SATISFIES = defineEdgeKind({
  id: "edge.kind.satisfies",
  endpoints: {
    provider: endpoint("provider").target(PROVIDER_NODE_KIND),
    requirement: endpoint("requirement").target(REQUIREMENT_NODE_KIND),
  },
});
```

Then this becomes a type error:

```ts
defineEdgeFromKind(SATISFIES, "edge:x", {
  provider: refTo(requirementNode), // error
  requirement: refTo(providerNode), // error
});
```

This is probably the highest-value type-safety upgrade.

## 4. Preserve endpoint output types in `defineEdgeFromKind`

`defineEdgeFromKind` already infers endpoint input names from the edge kind, which is good. But the return type erases endpoint shape back to `readonly KernelEdgeEndpoint[]`. 

Current:

```ts
): KernelEdge<EdgeKindFromDef<Kind>, readonly KernelEdgeEndpoint[], Metadata>
```

Better:

```ts
type EndpointTupleFor<Kind extends EdgeKindDef> = {
  readonly [K in keyof Kind["endpoints"]]: EndpointOutputFor<Kind["endpoints"][K]>;
};

type EdgeFromKind<
  Kind extends EdgeKindDef,
  Metadata extends EdgeMetadataFor<Kind> = EdgeMetadataFor<Kind>,
> = KernelEdge<
  EdgeKindFromDef<Kind>,
  EndpointTupleFor<Kind>,
  Metadata
>;

function defineEdgeFromKind<
  const Kind extends EdgeKindDef,
  const Metadata extends EdgeMetadataFor<Kind> = EdgeMetadataFor<Kind>,
>(
  kind: Kind,
  id: EdgeIdFor<Kind>,
  endpoints: EndpointInputsFor<Kind>,
  input?: EdgeInputFor<Kind, Metadata>,
): EdgeFromKind<Kind, Metadata>;
```

Then `edge.endpoints` stays typed without needing a second read helper.

## 5. Make `readEdgeEndpoints` require a matching edge kind

`readEdgeEndpoints(kind, edge)` returns endpoints for `kind`, but accepts any `KernelEdge`. Internally it searches by role ID and casts the object to `EndpointOutputsFor<Kind>`. 

Make the edge parameter generic on the same kind:

```ts
function readEdgeEndpoints<
  const Kind extends EdgeKindDef,
  const Edge extends EdgeFromKind<Kind>,
>(
  kind: Kind,
  edge: Edge,
): EndpointOutputsFor<Kind>;
```

For dynamic cases, expose an unsafe/dynamic variant separately:

```ts
function tryReadEdgeEndpoints<const Kind extends EdgeKindDef>(
  kind: Kind,
  edge: KernelEdge,
): EndpointOutputsFor<Kind> | undefined {
  if (edge.kind.id !== kind.id) return undefined;
  // runtime validation here
}
```

That gives you two clear modes:

```ts
readEdgeEndpoints(SATISFIES, typedEdge);    // fully typed
tryReadEdgeEndpoints(SATISFIES, unknownEdge); // runtime checked
```

## 6. Replace role-prefix graph traversal with edge-kind direction metadata

`edgesBetween` and `neighborhood` infer direction using string prefixes like `"edge.role.owner"`, `"edge.role.source"`, `"edge.role.from"`, `"edge.role.writer"`, etc.  The same source/target heuristic appears again in `neighborhood`. 

That is brittle. Direction should be part of the edge-kind witness:

```ts
const OWNS = defineEdgeKind({
  id: "edge.kind.owns",
  endpoints: {
    owner: endpoint("owner").direction("out"),
    owned: endpoint("owned").direction("in"),
  },
});
```

Then graph traversal can become:

```ts
graph.edges.from(node).via(OWNS);
graph.edges.to(node).via(OWNS);
graph.neighborhood(node, {
  depth: 2,
  via: [OWNS, DEPENDS_ON, SATISFIES],
});
```

Type shape:

```ts
type EndpointDirection = "source" | "target" | "undirected";

type DirectedEndpointRoleDef<Name extends string, Direction extends EndpointDirection> =
  EndpointRoleDef<Name> & {
    direction: Direction;
  };
```

This improves both correctness and DX: users no longer need to encode semantics into naming conventions.

## 7. Accept typed refs/nodes, not `string` IDs, in graph queries

These APIs accept `string` IDs:

```ts
edgesFrom(graph, nodeId: string)
edgesTo(graph, targetId: string)
edgesBetween(graph, fromId: string, toId: string)
neighborhood(graph, nodeId: string, ...)
```



Prefer overloads that accept typed nodes or refs:

```ts
function edgesFrom<const TNode extends KernelNode<any, any, any, any>>(
  graph: KernelGraph<any>,
  node: TNode | RefOf<TNode>,
): readonly OutgoingEdgesFor<typeof graph, TNode>[];

function edgesFrom(
  graph: KernelGraph,
  nodeId: KernelId<"node">,
): readonly KernelEdge[];
```

Usage:

```ts
graph.edges.from(userNode);
graph.edges.from(refOf(userNode));
graph.edges.from(nodeId("node:user:1"));
```

You can keep the raw ID API, but it should be the low-level overload, not the best-DX path.

## 8. Turn graph queries into a typed query object

Current query functions are flat utilities:

```ts
nodesOfKindDef(graph, kind)
edgesOfKindDef(graph, kind)
nodesWithTrait(graph, trait)
```

They work, but composition is awkward. 

A composable API could look like:

```ts
graph
  .nodes(PROVIDER_NODE_KIND)
  .withTrait(EXTERNAL_IMPL)
  .where((node) => node.metadata.custom.source_kind === "service_constructor")
  .toArray();

graph
  .edges(SATISFIES_EDGE_KIND)
  .whereEndpoint("provider", providerNode)
  .map((edge) => edge.endpoints.requirement.target);
```

Type shape:

```ts
type NodeQuery<TGraph, TNode> = {
  withTrait<const TTrait extends TraitDef>(
    trait: TTrait,
  ): NodeQuery<TGraph, TNode & HasTrait<TTrait>>;

  where(fn: (node: TNode) => boolean): NodeQuery<TGraph, TNode>;

  map<TResult>(fn: (node: TNode) => TResult): readonly TResult[];

  toArray(): readonly TNode[];
};
```

This makes graph traversal composable without giving up inference.

## 9. Make dialect registry generic over registered dialects

`defineDialect` preserves literal arrays nicely, but `DialectRegistry` stores broad `Dialect` values in `Map<string, Dialect>` and returns broad `Dialect | undefined` from lookups.  

Make the registry carry the dialect tuple:

```ts
type DialectRegistry<const TDialects extends readonly Dialect[]> = {
  getById<const TId extends DialectIds<TDialects>>(
    id: TId,
  ): ExtractDialectById<TDialects, TId>;

  getDialectForNodeKind<const TKind extends NodeKindsOf<TDialects>[number]>(
    kind: TKind,
  ): DialectOwningNodeKind<TDialects, TKind>;

  getDialectForEdgeKind<const TKind extends EdgeKindsOf<TDialects>[number]>(
    kind: TKind,
  ): DialectOwningEdgeKind<TDialects, TKind>;
};
```

Usage:

```ts
const registry = defineDialectRegistry([coreDialect, storageDialect] as const);

const d1 = registry.getById(BUILT_IN_DIALECTS.CORE);
// typed as typeof coreDialect

const d2 = registry.getDialectForNodeKind(PROVIDER_NODE_KIND);
// typed as the dialect that owns PROVIDER_NODE_KIND
```

Also, take node-kind witnesses instead of `kindId: string`:

```ts
registry.getDialectForNodeKind(PROVIDER_NODE_KIND);
registry.getDialectForEdgeKind(SATISFIES_EDGE_KIND);
registry.getDialectForTrait(providerTraits.EXTERNAL_IMPL);
```

The current string-based lookup API loses the witness relationship. 

## 10. Make `defineDialect` default arrays without `as unknown as`

`defineDialect` currently uses casts for omitted arrays:

```ts
nodeKinds: def.nodeKinds ?? ([] as unknown as NodeKinds)
```

and the same pattern for edge kinds, endpoint roles, traits, passes, and lowerings. 

A cleaner API is to normalize through overloads or a helper:

```ts
const empty = <const T extends readonly unknown[]>(): T => [] as unknown as T;
```

But even better, make the input require arrays with defaults at the call helper layer:

```ts
function defineDialect<const TDef extends DialectDefShape>(
  def: TDef,
): DialectFromDef<WithDialectDefaults<TDef>> {
  return {
    id: def.id,
    label: def.label,
    nodeKinds: def.nodeKinds ?? [],
    edgeKinds: def.edgeKinds ?? [],
    endpointRoles: def.endpointRoles ?? [],
    traits: def.traits ?? [],
    passes: def.passes ?? [],
    lowerings: def.lowerings ?? [],
    metadata: def.metadata,
  } as DialectFromDef<WithDialectDefaults<TDef>>;
}
```

This still uses one internal cast, but the public type is derived from the user’s literal input. That matches the cheat sheet’s guidance: casts are acceptable when centralized in factories and users do not need to write them. 

## 11. Brand IDs by domain, kind, and dialect

`defineEdge` accepts `id: string` and casts it to `KernelId<"edge">`.  `dialectId` similarly creates a branded dialect ID from a string. 

Push that pattern further:

```ts
type EdgeId<const TKindId extends string> =
  KernelId<"edge"> & { readonly __edgeKind: TKindId };

type NodeId<const TKindId extends string> =
  KernelId<"node"> & { readonly __nodeKind: TKindId };

function edgeId<const TKind extends EdgeKindDef>(
  kind: TKind,
  local: string,
): EdgeId<TKind["id"]> {
  return `edge:${kind.id}:${local}` as EdgeId<TKind["id"]>;
}
```

Usage:

```ts
defineEdgeFromKind(SATISFIES_EDGE_KIND, edgeId(SATISFIES_EDGE_KIND, "provider->requirement"), ...);
```

Now you cannot accidentally pass a node ID as an edge ID or use a `PLACED_IN` edge ID for a `SATISFIES` edge.

## 12. Infer endpoint object shape from named endpoint records, not endpoint names

You support both tuple-ish endpoints and record-ish endpoint shape via `EndpointShapeOf`, then map role names into object keys. 

The DX would be better if `defineEdgeKind` canonicalized all endpoint definitions into a named record:

```ts
const SATISFIES = defineEdgeKind({
  id: "edge.kind.satisfies",
  endpoints: {
    provider: endpointRole("provider"),
    requirement: endpointRole("requirement"),
  },
});
```

Then `EndpointInputsFor` becomes much simpler:

```ts
type EndpointInputsFor<Kind extends EdgeKindDef> = {
  [K in keyof Kind["endpoints"]]: EndpointInputFor<Kind["endpoints"][K]>;
};
```

This avoids the current extra conditional machinery and makes autocomplete match the user’s object literal keys exactly.

## 13. Add dialect-scoped builders

Dialects are the natural “project generic” boundary. The dialect already owns node kinds, edge kinds, endpoint roles, traits, passes, and lowerings. 

A dialect-scoped builder would improve composability:

```ts
const core = defineDialectBuilder(BUILT_IN_DIALECTS.CORE)
  .nodeKind(REQUIREMENT_NODE_KIND)
  .nodeKind(PROVIDER_NODE_KIND)
  .edgeKind(SATISFIES_EDGE_KIND)
  .trait(providerTraits.EXTERNAL_IMPL)
  .pass(checkRequirements)
  .lowering(lowerRequirements)
  .done();
```

Then registry and graph APIs can carry `typeof core`:

```ts
const graph = createGraph({ dialects: [core] });

graph.edge(SATISFIES_EDGE_KIND, ...); // ok
graph.edge(UNKNOWN_EDGE_KIND, ...);   // type error unless dialect registered
```

This is the same “project-carried generic” idea from the cheat sheet: once a library has an app/schema/project type, that generic should be carried by the whole API. 

## 14. Expose dynamic APIs separately from typed APIs

Some APIs are inherently dynamic: JSON import, graph visualization, external plugin loading, CLI inspection. Those should stay broad. But typed code paths should not pay the dynamic tax.

Use two layers:

```ts
// typed
graph.edges.ofKind(SATISFIES_EDGE_KIND);

// dynamic
graph.edges.ofKindId("edge.kind.satisfies");

// typed
registry.getDialectForNodeKind(PROVIDER_NODE_KIND);

// dynamic
registry.getDialectForNodeKindId("node.kind.provider");
```

This is an “overload inference facade”: expose clean typed call shapes while keeping implementation dynamic underneath.

## 15. Suggested end-state API

A high-DX version could look like this:

```ts
const core = defineDialect({
  id: BUILT_IN_DIALECTS.CORE,
  label: "Core",
  nodeKinds: [REQUIREMENT_NODE_KIND, PROVIDER_NODE_KIND],
  edgeKinds: [SATISFIES_EDGE_KIND, DEPENDS_ON_PROVIDER_EDGE_KIND],
  traits: [providerTraits.EXTERNAL_IMPL, providerTraits.LOCAL_IMPL],
});

const registry = defineDialectRegistry([core]);

const graph = createKernelGraph({ registry })
  .node(requirementNode)
  .node(providerNode)
  .edge(
    SATISFIES_EDGE_KIND,
    {
      provider: ref(providerNode),
      requirement: ref(requirementNode),
    },
    {
      provenance: explicit(),
    },
  );

const satisfies = graph.edges.ofKind(SATISFIES_EDGE_KIND);

for (const edge of satisfies) {
  edge.endpoints.provider.target;    // typed provider ref
  edge.endpoints.requirement.target; // typed requirement ref
  edge.metadata?.custom;             // typed metadata for SATISFIES_EDGE_KIND
}
```

## Highest-impact changes

I’d prioritize these in order:

1. **Generic `KernelGraph<TState>` or `GraphBuilder<TState>`** so registration does not erase types.
2. **Kind-aware `KernelRef` / `KernelObjectRef`** so endpoints can require specific target node kinds.
3. **Preserve endpoint shape in `KernelEdge` return types** instead of returning `readonly KernelEdgeEndpoint[]`.
4. **Direction metadata on endpoint roles** so traversal does not depend on role ID prefixes.
5. **Generic `DialectRegistry<TDialects>`** so lookups return the actual owning dialect type.
6. **Typed APIs first, dynamic string-ID APIs second** for better autocomplete and safer usage.


Yes, I get what you’re going for.

You’re building something like a **typed semantic IR kernel**: dialects define the legal vocabulary, node/edge kinds act as typed witnesses, graphs store runtime objects, and passes/adapters/lowerings should be composable without losing the type relationships. The ideal shape is:

```ts
dialect witnesses
  → graph captures registered vocabulary
  → APIs carry graph/dialect generic
  → queries/passes infer from kind/ref arguments
  → result types fall out automatically
```

That matches the cheat sheet’s core principle almost exactly: create typed values first, carry the project generic, infer from arguments, and derive return types automatically.

## Yes, FP could help — but mostly as typed composition, not as heavy FP ceremony

I would not reach for a full `fp-ts`-style API first. I would use FP ideas selectively:

1. **Pure graph transforms**
2. **Composable graph queries**
3. **Pass pipelines**
4. **Curried/bound APIs**
5. **Typed `.pipe()`**
6. **`Result` / diagnostics accumulation**
7. **Small algebraic data types for dynamic refinement**

The goal is not “make it functional.” The goal is:

> make graph construction, graph querying, verification, and lowering compose while preserving the witness generics.

That matters because the current APIs already start typed, then often erase. For example, `KernelGraph` stores broad `ReadonlyMap<string, KernelNode>` and `ReadonlyMap<string, KernelEdge>`, so registered node/edge specificity is not kept in the graph type.  Similarly, `registerNode` and `registerEdge` accept typed values but return plain `KernelGraph`, so the type information does not accumulate. 

## 1. FP-style graph construction: pure, composable, type-accumulating

Instead of only this:

```ts
let graph = createKernelGraph();
graph = registerNode(graph, providerNode);
graph = registerEdge(graph, satisfiesEdge);
```

Expose a functional layer:

```ts
const graph = pipeGraph(createKernelGraph())
  .through(addNode(providerNode))
  .through(addNode(requirementNode))
  .through(addEdge(satisfiesEdge))
  .value();
```

But the important part is the type:

```ts
type GraphStep<TIn extends KernelGraph<any>, TOut extends KernelGraph<any>> =
  (graph: TIn) => TOut;

type GraphPipe<TGraph extends KernelGraph<any>> = {
  through<TNext extends KernelGraph<any>>(
    step: GraphStep<TGraph, TNext>,
  ): GraphPipe<TNext>;

  value(): TGraph;
};
```

That is directly the cheat sheet’s **Project-Aware Type Pipe** idea: `.pipe()` should carry both the whole project type and the current value type.

For your case, rename “project” to “kernel graph” or “dialect world”:

```ts
KernelPipe<TDialects, TGraph, TFocus>
```

where:

* `TDialects` stays stable
* `TGraph` accumulates registered objects
* `TFocus` changes as you query or transform

## 2. Passes should be typed graph transformations

This is probably the cleanest FP win.

Instead of passes being just runtime visitors, define them as typed transformations:

```ts
type KernelPass<
  TInputGraph extends KernelGraph<any>,
  TOutputGraph extends KernelGraph<any>,
> = {
  readonly name: string;
  run(input: TInputGraph): PassResult<TOutputGraph>;
};
```

Then:

```ts
const graph2 = graph
  .pipe()
  .through(inferProviderDependencies)
  .through(checkRequirementSatisfaction)
  .through(lowerToRuntimePlan)
  .value();
```

Each pass can either:

```ts
Graph<A> -> Graph<B>
```

or:

```ts
Graph<A> -> Result<Graph<B>, Diagnostic[]>
```

That makes verification/lowering compositional while still type-aware.

This is especially useful because dialects already conceptually own passes and lowerings. The `Dialect` type stores `nodeKinds`, `edgeKinds`, `traits`, `passes`, and `lowerings`, which makes dialects a natural generic boundary for pass composition. 

## 3. Queries should be composable selectors, not one-off helpers

Current graph queries are useful but flat:

```ts
nodesOfKindDef(graph, PROVIDER_NODE_KIND)
edgesOfKindDef(graph, SATISFIES_EDGE_KIND)
edgesFrom(graph, nodeId)
edgesBetween(graph, fromId, toId)
```

The first two are moving in the right direction because they accept kind witnesses, but the graph still returns broad-ish values and later traversal drops to strings and role-prefix checks. 

A more composable API:

```ts
const providers = graph
  .nodes(PROVIDER_NODE_KIND)
  .withTrait(providerTraits.EXTERNAL_IMPL)
  .where((node) => node.metadata.custom.source_kind === "service_constructor")
  .toArray();

const bindings = graph
  .edges(SATISFIES_EDGE_KIND)
  .map((edge) => ({
    provider: edge.endpoints.provider.target,
    requirement: edge.endpoints.requirement.target,
  }));
```

This is FP-ish: `filter`, `map`, `flatMap`, `collect`, `partition`, `groupBy`. But it is not abstract for abstraction’s sake. It gives you a fluent typed query algebra.

The key type shape:

```ts
type EdgeQuery<
  TGraph,
  TKind extends EdgeKindDef,
  TEdge extends EdgeFromKind<TKind>,
> = {
  where(fn: (edge: TEdge) => boolean): EdgeQuery<TGraph, TKind, TEdge>;

  map<TResult>(
    fn: (edge: TEdge) => TResult,
  ): readonly TResult[];

  endpoints(): readonly EndpointOutputsFor<TKind>[];
};
```

That would also reduce the need for helper code like `readEdgeEndpoints`. Right now `readEdgeEndpoints` accepts any `KernelEdge` and casts the result to `EndpointOutputsFor<Kind>`, which means the kind/edge relationship is not enforced at the call boundary. 

## 4. Add a typed `Option` / `Result` refinement layer for dynamic graph reads

Graphs are runtime data structures. Sometimes you really do need to load unknown JSON or inspect unknown edges.

So do not pretend everything is typed. Instead, split APIs:

```ts
// Static path: edge already known to be SATISFIES.
readEdgeEndpoints(SATISFIES_EDGE_KIND, edge);

// Dynamic path: unknown edge refined at runtime.
matchEdge(SATISFIES_EDGE_KIND, unknownEdge);
```

Example:

```ts
const maybeSatisfies = edge.as(SATISFIES_EDGE_KIND);

if (maybeSatisfies.ok) {
  maybeSatisfies.value.endpoints.provider;
  maybeSatisfies.value.endpoints.requirement;
}
```

Type shape:

```ts
type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };

function refineEdge<const TKind extends EdgeKindDef>(
  kind: TKind,
  edge: KernelEdge,
): Result<EdgeFromKind<TKind>, Diagnostic>;
```

This is a good FP import: use `Result` where runtime refinement may fail. It keeps the unsafe cast inside a small, audited boundary, which matches your cheat sheet’s “library internals may cast, userland should not need to cast” rule.

## 5. Use curried APIs to bind dialect/graph context once

The current API repeatedly passes `graph`, `kind`, `edge`, IDs, etc. A curried binder can improve DX and inference:

```ts
const q = queryGraph(graph);

const providers = q.nodes(PROVIDER_NODE_KIND);
const satisfies = q.edges(SATISFIES_EDGE_KIND);
```

or:

```ts
const defineCore = defineForDialect(coreDialect);

const satisfies = defineCore.edge(SATISFIES_EDGE_KIND, {
  provider: providerRef,
  requirement: requirementRef,
});
```

That is exactly where **Curried Type Binder** and **Typed Builder Instance** fit. The cheat sheet explicitly calls out callbacks, builders, currying, and `.pipe()` as tools to improve inference when they create a useful type boundary.

A nice shape:

```ts
const core = defineDialect({...});

const kernel = createKernel(core);

kernel.edge(SATISFIES_EDGE_KIND, {
  provider: ref(providerNode),
  requirement: ref(requirementNode),
});
```

Because `kernel` captured `core`, `kernel.edge(...)` can reject edge kinds that do not belong to the dialect.

## 6. Make dialect registry a registry-derived API

`DialectRegistry` is currently dynamic: it stores broad `Dialect` values and exposes string lookup methods like `getDialectForNodeKind(kindId: string)`. 

That should have two layers:

```ts
registry.getDialectForNodeKind(PROVIDER_NODE_KIND);
// typed

registry.getDialectForNodeKindId("node.kind.provider");
// dynamic
```

And ideally:

```ts
const registry = defineDialectRegistry([
  coreDialect,
  storageDialect,
] as const);

const owner = registry.ownerOf(PROVIDER_NODE_KIND);
// typeof coreDialect
```

This is the cheat sheet’s **Registry-Derived API** pattern. A literal registry should generate a typed API from its contents.

## 7. Use FP-style `fold` / `match` for edge kinds and graph objects

Anywhere you currently do:

```ts
if (edge.kind.id !== SATISFIES_EDGE_KIND.id) continue;
```

or switch on kind IDs, consider a matcher:

```ts
matchEdge(edge)
  .case(SATISFIES_EDGE_KIND, (edge) => {
    edge.endpoints.provider;
    edge.endpoints.requirement;
  })
  .case(PLACED_IN_EDGE_KIND, (edge) => {
    edge.endpoints.placed;
    edge.endpoints.location;
  })
  .otherwise(() => {});
```

This gives you:

* exhaustiveness when matching a known dialect
* endpoint inference per case
* less manual role lookup
* less string matching

This matters because `defineEdgeFromKind` already has enough type information to infer endpoint inputs from the edge-kind witness, but its return type currently erases the endpoint structure to `readonly KernelEdgeEndpoint[]`. 

## 8. Direction and traversal should be declared, not inferred by string prefix

This is one place where FP will not solve the root issue. The root issue is semantic data modeling.

`edgesBetween` currently guesses source/target roles by checking prefixes like `"edge.role.owner"`, `"edge.role.source"`, `"edge.role.from"`, and so on. 

Instead, put direction on the endpoint role witness:

```ts
const SATISFIES_EDGE_KIND = defineEdgeKind({
  id: "edge.kind.satisfies",
  endpoints: {
    provider: endpoint("provider").source(),
    requirement: endpoint("requirement").target(),
  },
});
```

Then traversal can be functional and typed:

```ts
graph
  .from(providerNode)
  .via(SATISFIES_EDGE_KIND)
  .targets("requirement");
```

or:

```ts
graph.traverse(providerNode, {
  depth: 2,
  via: [SATISFIES_EDGE_KIND, DEPENDS_ON_PROVIDER_EDGE_KIND],
});
```

FP helps compose traversal, but the type-safety comes from endpoint direction being part of the witness.

## Core design

I’d model it like this:

```ts
type GraphState = {
  readonly nodes: Record<string, KernelNode>;
  readonly edges: Record<string, KernelEdge>;
};

type EmptyGraphState = {
  readonly nodes: {};
  readonly edges: {};
};

type TypedGraph<TKernel, TState extends GraphState> = KernelGraph & {
  readonly __kernel?: TKernel;
  readonly __state?: TState;
};

type GraphStep<
  TKernel,
  TIn extends GraphState,
  TOut extends GraphState,
> = {
  readonly run: (graph: TypedGraph<TKernel, TIn>) => TypedGraph<TKernel, TOut>;
};
```

Then:

```ts

  node(requirementNode),
  node(providerNode),
  edge(SATISFIES_EDGE_KIND, {
    provider: ref(providerNode),
    requirement: ref(requirementNode),
  }),
);
```

would infer something like:

```ts
TypedGraph<

  {
    nodes: {
      [requirementNode.id]: typeof requirementNode;
      [providerNode.id]: typeof providerNode;
    };
    edges: {
      [satisfiesEdge.id]: EdgeFromKind<typeof SATISFIES_EDGE_KIND>;
    };
  }
>
```

That gives you a runtime graph, but with accumulated type knowledge.

## The hard part: variadic type inference

The runtime implementation is easy:

```ts
function pipe(...steps: GraphStep<any, any, any>[]) {
  return steps.reduce((graph, step) => step.run(graph), createKernelGraph());
}
```

The type-level implementation is the challenge.

You need a recursive tuple type:

```ts
type ApplySteps<
  TKernel,
  TState extends GraphState,
  TSteps extends readonly GraphStep<any, any, any>[],
> =
  TSteps extends readonly [
    GraphStep<TKernel, TState, infer TNextState>,
    ...infer TRest extends readonly GraphStep<any, any, any>[],
  ]
    ? ApplySteps<TKernel, TNextState, TRest>
    : TState;
```

Then:

```ts
function pipe<
  const TKernel,
  const TSteps extends readonly GraphStep<TKernel, any, any>[],
>(
  ...steps: TSteps
): TypedGraph<TKernel, ApplySteps<TKernel, EmptyGraphState, TSteps>>;
```

In practice, TypeScript sometimes struggles with deeply recursive variadic inference. A pragmatic alternative is overloads up to, say, 10 or 20 steps. Your cheat sheet calls this an **Overload Inference Facade**: clean public call shapes, loose internal implementation.

# 2. Replace `opCall` / `opCallTyped` split with one typed facade

```ts
opCall(operation, args)
opCallTyped(operation, args)
```

The untyped version accepts `readonly KernelExpr[]`, and the typed version casts into it. 

I would expose this instead:

```ts
expr.call(operation, ...args)
```

Example:

```ts
const sameOrg = expr.call(
```

```ts
function call<const Op extends OpSignature>(
  operation: Op,
  ...args: OperationExprArgsFor<Op>

```

Then keep a dynamic escape hatch:

```ts
expr.callUnchecked(operation, args)
```

That gives you:

```txt
typed path by default

unsafe cast inside the library
```

This is straight from the cheat sheet: the user should pass typed witnesses, while internal casts stay inside factory/helper boundaries.

# 4. Laws should be graph claims with typed witnesses

`law.ts` is a strong concept. Laws are semantic claims about operations, transforms, nodes, and expressions, and witnesses can be identity expressions, inverse transforms, proofs, or custom data. 

Current API:

```ts
defineLaw(...)
defineLawWithIdentity(...)
defineLawWithInverse(...)
defineLawWithProof(...)
defineLawWithWitness(...)
```

That works, but I would make the public API feel like this:

```ts
const addMoney = defineOperation({
  id: "op.money.add",
  args: [Money, Money] as const,
  output: Money,
});

const graph = kernel.graph.pipe(
  operation(addMoney),

  claim(addMoney, LAWS.ASSOCIATIVE),
  claim(addMoney, LAWS.COMMUTATIVE),
  claim(addMoney, LAWS.IDENTITY, {
    identity: expr.literal(Money, 0),
  }),
);
```

Or builder style:

```ts
const addMoney = operation("op.money.add")
  .args(Money, Money)
  .returns(Money)
  .law(LAWS.ASSOCIATIVE)
  .law(LAWS.COMMUTATIVE)
  .law(LAWS.IDENTITY, {
    identity: expr.literal(Money, 0),
  })
  .define();
```

The important type relationship:

```ts
claim(target, law, witness)
```

should enforce:

```txt
law.target must match target kind
identity witness must be an Expr
inverse witness must be a Transform
proof witness must be proof-shaped
custom witness must match law payload
```

Right now laws have `target: "operation" | "transform" | "node" | "expr"` and optional witness payloads.  I would strengthen that into:

```ts
type LawDef<
  TTarget extends LawTarget,
  TWitness = { kind: "none" },
> = {
  id: KernelId<"law">;
  target: TTarget;
  witness: WitnessSchema<TWitness>;
};
```

Then:

```ts
claim(addMoney, LAWS.PURE);
// type error if LAWS.PURE targets expr only

claim(addMoney, LAWS.IDENTITY, {
  identity: expr.literal(Money, 0),
});
// ok if IDENTITY targets operation and expects identity expr
```

## Why laws matter

This should be a headline feature, not internal plumbing.

Laws power:

```txt
optimistic updates
rollback plans
retry safety
offline replay
CRDT-like merges
incremental view maintenance
cacheability
parallel execution
idempotent queues
```

Your original doc already talks about operations with laws like commutative, associative, idempotent, reversible, monotonic, identity, inverse, and retry-safe.  This API should make that real.

# 5. Rules should be authored as typed expressions, then lowered into graph facts

The rule adapter currently does a lot manually:

```ts

```

It builds rule nodes, body edges, var declaration edges, and `RULE_READS` edges. 

This is the right semantic model, but the public API should be:

```ts
const canArchiveUser = defineRule("canArchiveUser", (ctx) =>
  expr.and(
    expr.eq(ctx.actor.role, Role.Manager),
    expr.eq(ctx.actor.organizationId, ctx.user.organizationId),
  )
);
```

Then:

```ts
const graph = kernel.graph.pipe(
  rule(canArchiveUser),
);
```

`rule(canArchiveUser)` should expand to:

```txt
Node(kind: RULE)
Node(kind: VAR_DECL) for each var
Expr body
Edge(kind: RULE_HAS_BODY)
Edge(kind: RULE_DECLARES_VAR)
Edge(kind: RULE_READS) for every field/entity read by the expression
Trait(rule.pure)
Trait(rule.predicate)
```

The rule’s dependency surface should come from the typed expression body, not from untyped bridge metadata.

The current rule bridge stores original domain objects in edge metadata:

```ts

custom: { _bridgeEntity: entity }
```

and later casts them back out during graph dependency extraction. 

That is okay as a temporary bridge, but it is not the final API.

Prefer graph-native refs:

```ts
edge(ruleReads, {
  reader: ref(canArchiveUser),
  read: ref(User.organizationId),

```

Then dependency extraction becomes:

```ts
const deps = graph
  .edges.ofKind(ruleReads)
  .whereEndpoint("reader", ref(canArchiveUser))
```

No `_bridgeEntity`.
No `as Field`.
No tuple endpoint lookup.

```ts
const deps = graph.rules.dependenciesOf(canArchiveUser);
```

## Why this fits especially well here

Your current expression layer already has the important relationship: an operation signature determines argument expression types and output expression type through `OperationExprArgsFor<Op>` and `OperationCallExpr<Op>`. 

So `defineAction` should preserve that same relationship upward:

```txt
operation signature
  → typed expression call
  → typed action body
  → action reads/writes/effects/errors
  → graph edges
  → compiler passes
```

That is exactly where generics need to “bubble up.” The action API should not erase operation, expression, rule, input, and output types too early.

## Suggested overload shape

Conceptually:

```ts
type DefineAction = {
  (): ActionBuilder<DefaultCtx, UnnamedActionState>;

  <const TName extends string>(
    name: TName,
  ): ActionBinder<DefaultCtx, TName>;

  with<const TCtx>(): {
    (): ActionBuilder<TCtx, UnnamedActionState>;

    <const TName extends string>(
      name: TName,
    ): ActionBinder<TCtx, TName>;
  };
};
```

Then:

```ts
const defineAppAction = defineAction.with<AppCtx>();

const archiveUser = defineAppAction("archiveUser")({
  input: {
    actor: Actor,
    user: User,
  },
  guard: canArchiveUser,
  body: (ctx) => ctx.pipe(/* ... */),
});
```

The generic is bound at `.with<AppCtx>()`.

The name is inferred later as the literal `"archiveUser"`.

That is much cleaner than trying to make `defineAction<AppCtx>("archiveUser")` do everything.

## The binder can accept either object or function

The returned function can have two overloads:

```ts
type ActionBinder<TCtx, TName extends string> = {
  <const TSpec extends ActionObjectSpec<TCtx>>(
    spec: TSpec,
  ): ActionDef<TCtx, TName, NormalizeActionSpec<TCtx, TSpec>>;

  <const TResult extends ActionBuildResult>(
    build: (
      ctx: ActionDefineContext<TCtx>,
      action: ActionBuilder<TCtx, NamedActionState<TName>>,
    ) => TResult,
  ): ActionDef<TCtx, TName, NormalizeActionBuildResult<TResult>>;
};
```

So users can write declarative object config:

```ts
const archiveUser = defineAction("archiveUser")({
  input: {
    actor: Actor,
    user: User,
  },
  guard: canArchiveUser,
  writes: [User.archivedAt],
  emits: [UserArchived],
});
```

or callback/builder config:

```ts
const archiveUser = defineAction("archiveUser")((ctx, action) =>
  action
    .input({
      actor: ctx.entities.Actor,
      user: ctx.entities.User,
    })
    .guard(ctx.rules.canArchiveUser)
    .writes(ctx.entities.User.archivedAt)
    .emits(ctx.events.UserArchived)
);
```

The object form is concise.

The callback form gives better contextual autocomplete and lets `ctx` carry the project/kernel/dialect generic.

## Builder mode should be type-stateful

The no-argument builder should accumulate state:

```ts
const archiveUser = defineAction()
  .name("archiveUser")
  .input({
    actor: Actor,
    user: User,
  })
  .guard(canArchiveUser)
  .writes(User.archivedAt)
  .emits(UserArchived)
  .body((ctx) =>
    ctx.pipe(
      op.set(ctx.input.user.archivedAt, expr.now()),
      op.emit(UserArchived),
    )
  )
  .done();
```

Type-state should know:

```txt
name has been set
input has been set
guard exists
writes are known
emits are known
body returns the right operation/result type
```

So you can prevent invalid builder states:

```ts
defineAction()
  .body(/* ... */)
  // ^ type error or degraded context:
  // body needs input first if it references ctx.input

defineAction()
  .name("archiveUser")
  .input({ user: User })
  .guard(canArchiveUserForProject)
  // ^ type-check guard against input context
```

Shape:

```ts
type ActionBuilder<TCtx, TState> = {
  name<const TName extends string>(
    name: TName,
  ): ActionBuilder<TCtx, TState & { name: TName }>;

  input<const TInput extends ActionInputSpec<TCtx>>(
    input: TInput,
  ): ActionBuilder<TCtx, TState & { input: TInput }>;

  guard<const TRule extends RuleForAction<TCtx, NoInfer<TState>>>(
    rule: TRule,
  ): ActionBuilder<TCtx, TState & { guard: TRule }>;

  body<const TBody extends ActionBodyFor<TCtx, NoInfer<TState>>>(
    body: TBody,
  ): ActionBuilder<TCtx, TState & { body: TBody }>;

  done(): CompleteActionDef<TCtx, TState>;
};
```

`NoInfer` matters here: once `input(...)` defines the action input, later methods like `guard(...)`, `writes(...)`, and `body(...)` should be checked against that input rather than widening or redefining it. Your cheat sheet explicitly calls out `NoInfer` for this one-way inference case.

## My recommendation

Support `defineAction<Ctx>()("name")` or `defineAction.with<Ctx>()("name")`.

Be cautious about making `defineAction<Ctx>("name")` the main documented API. It looks nice, but it fights TypeScript’s partial generic inference. The curried generic binder is more reliable:

```ts
const archiveUser = defineAction.with<AppCtx>()("archiveUser")((ctx, action) =>
  action
    .input({ actor: ctx.Actor, user: ctx.User })
    .guard(ctx.canArchiveUser)
    .body((body) =>
      body.pipe(
        ctx.ops.set(ctx.User.archivedAt, ctx.expr.now()),
        ctx.ops.emit(ctx.UserArchived),
      )
    )
);
```

That gives you the thing you want:

```txt
builder when called with no args
curried when called with a name
object or ctx/builder callback as the second step
context generic bound once
literal name preserved
action type inferred from input, guard, body, operations, effects, errors, and laws
```

So yes — this is the right direction. The main adjustment is: **bind generics through `.with<T>()` or a kernel value, then infer the name and spec from later arguments.**

Yes — dialects can be **very type-safe and highly inferred**, and they probably should be one of the nicest DX surfaces in the whole system.

The key distinction:

```txt
Static dialects declared in TypeScript
  → can be strongly typed and inferred.

Dynamic/plugin dialects loaded at runtime
  → must be decoded/refined first, then become typed.
```

So “fully type safe” is possible for authored dialects, graph steps, builders, passes, lowerings, and queries inside the same TypeScript program. Runtime-loaded dialects need a validation boundary.

Your current `Dialect` model is already pointing the right way: a dialect owns node kinds, edge kinds, endpoint roles, traits, passes, and lowerings. `defineDialect` also already uses `const` generics to preserve literal node/edge/trait arrays.  The main gap is that `DialectRegistry` stores broad `Dialect` values and exposes string lookups like `getDialectForNodeKind(kindId: string)`, which erases the specific owning dialect type. 

I would evolve dialects into the **primary typed vocabulary boundary**.

## Graph steps should declare required dialects

```ts
type GraphStep<TRequires, TIn, TOut> = {
```

```ts
node(app.nodes.action, archiveUser)
```

## Dialect-local authoring APIs

A dialect should export its own nice mini-DSL.

Example:

```ts
const app = defineDialect("app")((d) => {
  const action = d.nodeKind("action", {
    metadata: schema<ActionMetadata>(),

  const rule = d.nodeKind("rule", {
    traits: [d.trait("pure"), d.trait("predicate")],

    nodes: { action, rule },
    edges: { guards },

});
```

```ts
const canArchiveUser = app.rule("canArchiveUser", (ctx) =>

```

That is the best version of dialect DX: dialects do not just hold raw kinds; they generate typed authoring helpers.

## What “fully type-safe dialects” means

I would define it as:

### TypeScript can prove:

```txt
This node kind belongs to this dialect.
This edge kind belongs to this dialect.
This trait can target this object kind.
```

```txt
Duplicate kind IDs.
Missing imported dialects at runtime.
Conflicting lowerings.
Unsupported target combinations.
Invalid graph-wide invariants.
Plugin schema mismatches.
Dynamic JSON/plugin dialect correctness.
```

This matches the broader system framing: TypeScript catches local mistakes, compiler passes catch global mistakes, and diagnostics explain what cannot be proven statically. Your existing copy already says this directly for graph-wide safety and inference.

# 8. Operations, expressions, and laws as first-class dialect concepts

The ideal design should expose those as authoring primitives:

```ts
const setArchivedAt = operation.define("setArchivedAt")

  .returns(User)

  .law(LAWS.ROLLBACK_SAFE)
```

```ts
const setArchivedAt = operation.define("setArchivedAt")({
  args: [User, DateTime],

    LAWS.IDEMPOTENT,
    LAWS.ROLLBACK_SAFE,
```

```ts
const graph = kernel.graph.pipe(
```

```ts
      field,
    },

    edges: {
      ownsField,
    },
  };
});
```

Now the kind is not just:

```ts
{ id: string; label: string }
```

It is a typed witness that knows:

```txt
node metadata shape
valid traits
valid edge endpoints
valid endpoint targets
direction
dialect ownership
```

Then usage becomes:

```ts
const User = node(domain.nodes.entity, "User", {
  metadata: {
    name: "User",
    pluralName: "Users",
  },
});

const email = node(domain.nodes.field, "User.email", {
  metadata: {
    name: "email",
    nullable: false,
  },
});

const graph = kernel.graph.pipe(
  User,
  email,

  edge(domain.edges.ownsField, {
    entity: ref(User),
    field: ref(email),
  }),
);
```

Bad composition should fail:

```ts
edge(domain.edges.ownsField, {
  entity: ref(email),
  //      ^ type error: expected Entity node ref

  field: ref(User),
  //    ^ type error: expected Field node ref
});
```

That is the ideal: **kinds live inside dialects, and dialects generate typed graph APIs.**

# 2. Ideal `type.ts`: typed value factories, not one broad `defineType`

Current `KernelType<Decoded>` has a `Decoded` generic, but `defineType` returns plain `KernelType`, so the decoded type is mostly lost at the factory boundary. 

Current-ish:

```ts
const email = defineType(typeKinds.EMAIL, "type:email");
// KernelType, not strongly KernelType<Email>
```

Ideal:

```ts
const t = defineTypeSystem("core.types")({
  string: scalar("string").decoded<string>(),
  number: scalar("number").decoded<number>(),
  boolean: scalar("boolean").decoded<boolean>(),

  uuid: scalar("uuid")
    .decoded<Uuid>()
    .trait(traits.TYPE.UUID),

  email: scalar("email")
    .decoded<Email>()
    .trait(traits.TYPE.EMAIL),

  datetime: scalar("datetime")
    .decoded<Date>()
    .trait(traits.TYPE.DATETIME),
});
```

Then richer factories:

```ts
const User = t.object("User", {
  id: t.uuid,
  email: t.email,
  name: t.string,
  archivedAt: t.optional(t.datetime),
});

type UserValue = InferDecoded<typeof User>;
// {
//   id: Uuid;
//   email: Email;
//   name: string;
//   archivedAt?: Date;
// }
```

Ideal type helpers:

```ts
const Status = t.enum("UserStatus", ["active", "archived"] as const);
// InferDecoded<typeof Status> = "active" | "archived"

const PublicUser = t.pick(User, {
  id: true,
  name: true,
});
// InferDecoded<typeof PublicUser> = { id: Uuid; name: string }
```

Traits should be checked at the type factory:

```ts
const SecretToken = t.string
  .brand<"SecretToken">()
  .trait(traits.TYPE.SECRET)
  .trait(traits.TYPE.SERVER_ONLY);
```

Bad trait target:

```ts
t.email.trait(traits.NODE.ACTION);
//      ^ type error: node trait cannot apply to type
```

The ideal API should preserve decoded type through every type combinator:

```txt
object → InferDecoded object
array → InferDecoded[]
optional → T | undefined
union → union
brand → branded primitive
refinement → branded/refined primitive
```

# 3. Ideal `trait.ts`: target-safe traits with payload inference

Current traits have a `target` field and helpers like `traitAppliesTo(...)`, but target compatibility is mostly runtime. 

Ideal trait definition:

```ts
const serverOnly = defineTrait("serverOnly", {
  target: ["type", "node"] as const,
  payload: schema<{
    reason?: string;
  }>(),
});

const destructive = defineTrait("destructive", {
  target: ["node"] as const,
  payload: schema<{
    requiresConfirmation: boolean;
  }>(),
});

const writes = defineTrait("writes", {
  target: ["edge"] as const,
});
```

Then application is typed:

```ts
const deleteUser = node(app.nodes.action, "deleteUser")
  .trait(destructive, {
    requiresConfirmation: true,
  });
```

Bad payload:

```ts
deleteUser.trait(destructive, {
  confirm: true,
  // ^ type error: expected requiresConfirmation
});
```

Bad target:

```ts
const emailType = t.email.trait(destructive, {
  requiresConfirmation: true,
});
// ^ type error: destructive applies to node, not type
```

Traits should also be able to refine API capabilities:

```ts
const action = app.action("deleteUser")
  .trait(destructive, { requiresConfirmation: true });

action.requiresConfirmation;
// typed true / available because trait is present
```

And conflicts should be checked both locally and globally:

```ts
const clientEvaluable = defineTrait("clientEvaluable", {
  target: ["expr"],
  conflictsWith: [serverOnlyExpr],
});

const expr = defineExpr(...)
  .trait(clientEvaluable)
  .trait(serverOnlyExpr);
// local type error if both known,
// compiler diagnostic if dynamic/plugin-derived
```

Ideal principle:

```txt
trait definition carries target + payload + implications + conflicts
trait application checks target and payload
graph passes check global implication/conflict closure
```

# 4. Ideal `scope.ts`: scope as inferred context, not string lookup

Current scope bindings are individually typed, but `ExecutionScope` stores `readonly ScopeBinding[]`, and lookup is by `name: string`, returning `ScopeBinding | undefined`. 

Ideal scope should be a typed record:

```ts
const actionScope = defineScope("archiveUser")
  .binding("actor", "actor", Actor)
  .binding("user", "input", User)
  .binding("now", "context", t.datetime)
  .done();
```

Then:

```ts
type Ctx = ScopeContext<typeof actionScope>;

ctx.actor;
// ExprRef<Actor>

ctx.user;
// ExprRef<User>

ctx.now;
// ExprRef<Date>
```

Better: scopes should be created by action/rule builders automatically.

```ts
const archiveUser = app.action("archiveUser")((ctx, action) =>
  action
    .input({
      actor: Actor,
      user: User,
    })
    .context({
      now: t.datetime,
    })
    .body((body) =>
      body.pipe(
        op.set(ctx.user.archivedAt, ctx.now),
      )
    )
);
```

Here `ctx` is inferred from the action input and context.

Bad binding access:

```ts
ctx.tenant;
// ^ type error if tenant was not declared
```

Bad use of field:

```ts
op.set(ctx.user.archivedAt, ctx.actor);
//                         ^ type error: expected DateTime, got Actor
```

For dynamic lookup, keep a separate API:

```ts
scope.lookup("actor");
// dynamic: ScopeBinding | undefined
```

But the main authored API should be:

```ts
ctx.actor
ctx.input.user
ctx.session
ctx.tenant
ctx.before
ctx.after
```

not string lookup.

# 5. Ideal `artifact.ts`: artifacts typed by target and kind

Current artifacts use:

```ts
target: ArtifactTarget
kind: string
content?: string | Uint8Array | JsonValue
generatedFrom: ArtifactSource[]
generatedBy: KernelId<"pass">
metadata?: ReadonlyMap<string, unknown>
```

So the artifact target is a union, but `kind`, `content`, metadata, and sources are broad. 

Ideal target/dialect API:

```ts
const reactTarget = defineTarget("react")((t) => {
  const component = t.artifactKind("component", {
    content: tsx(),
    path: pathTemplate("src/components/{name}.tsx"),
    metadata: schema<{
      componentName: string;
      exports: readonly string[];
    }>(),
    sources: [ui.nodes.view, app.nodes.action, app.nodes.rule],
  });

  const hook = t.artifactKind("hook", {
    content: typescript(),
    path: pathTemplate("src/hooks/{name}.ts"),
    metadata: schema<{
      hookName: string;
    }>(),
  });

  return {
    artifacts: {
      component,
      hook,
    },
  };
});
```

Then emission:

```ts
const artifact = emit(reactTarget.artifacts.component, {
  id: "artifact:react.component.UserList",
  source: ref(UserListView),
  generatedBy: passRef(emitReact),
  path: {
    name: "UserList",
  },
  metadata: {
    componentName: "UserList",
    exports: ["UserList"],
  },
  content: tsx`
    export function UserList() {
      return <div />;
    }
  `,
});
```

Bad content type:

```ts
emit(reactTarget.artifacts.component, {
  content: { json: true },
  //       ^ type error: React component expects TSX/TypeScript content
});
```

Bad source kind:

```ts
emit(reactTarget.artifacts.component, {
  source: ref(postgresTable),
  //      ^ type error if component sources must be UI/app graph refs
});
```

Artifact source tracing should be typed:

```ts
artifact.generatedFrom[0].target;
// Ref<typeof ui.nodes.view, typeof UserListView>
```

Artifact queries should be typed:

```ts
const components = graph.artifacts.ofKind(reactTarget.artifacts.component);

for (const component of components) {
  component.metadata.componentName;
  component.content.code;
}
```

Generated-from should also be graph-native:

```ts
edge(core.edges.generatedFrom, {
  artifact: ref(artifact),
  source: ref(UserListView),
});
```

The artifact object can keep `generatedFrom` inline for serialization, but the graph should know it too.

# 6. Ideal `bridge.ts`: no public mutation helpers; use writer phases

Current bridge helpers explicitly cast readonly maps to mutable maps and mutate them in place for dual-write paths. The file comments even say they are bridge-only and should be removed once pass pipelines land. 

Ideal replacement:

```ts
const graph = kernel.graph.pipe(
  entity(User),
  action(archiveUser),
  rule(canArchiveUser),
);
```

For performance-sensitive building, expose an internal `GraphWriter`, not raw mutation helpers:

```ts
const graph = kernel.graph.build((w) => {
  w.add(entity(User));
  w.add(action(archiveUser));
  w.add(rule(canArchiveUser));
});
```

Type shape:

```ts
type GraphWriter<TKernel, TState> = {
  add<TStep extends GraphStep<TKernel, any, any>>(
    step: TStep,
  ): void;

  node<TNode extends AnyNode>(node: TNode): RefOf<TNode>;

  edge<TEdgeKind extends EdgeKindDef>(
    kind: TEdgeKind,
    endpoints: EndpointInputsFor<TEdgeKind>,
  ): RefOf<EdgeFromKind<TEdgeKind>>;
};
```

This lets the implementation mutate internally for speed while the public API remains safe:

```ts
const graph = kernel.graph.mutable((graph) => {
  const user = graph.add(entity(User));
  const action = graph.add(action(archiveUser));

  graph.add(edge(app.edges.writes, {
    action: ref(action),
    field: ref(User.archivedAt),
  }));
});
```

The important rule:

```txt
mutation is an implementation detail
graph steps are the public API
```

So `attachNode`, `attachEdge`, `attachExpr` should become internal-only machinery under `GraphWriter`, not user-facing helpers.

# 7. Ideal graph-step protocol for all these concepts

Every semantic object should be usable as a graph fragment.

```ts
const graph = kernel.graph.pipe(
  t.register(UserType),

  entity(User),
  field(User.email),

  action(archiveUser),
  rule(canArchiveUser),

  artifact(reactTarget.artifacts.component, UserListComponent),

  pass(checkGuards),
  pass(emitReact),
);
```

Under the hood:

```ts
type GraphStep<TKernel, TIn, TOut> = {
  readonly kind: "graph.step";
  readonly requires: DialectSet;
  apply(graph: TypedGraph<TKernel, TIn>): TypedGraph<TKernel, TOut>;
};
```

Then these helpers produce steps:

```ts
type(typeDef)
trait(traitDef)
node(kind, value)
edge(kind, endpoints)
scope(scopeDef)
artifact(kind, input)
pass(passDef)
fragment(...)
```

That means the API is composable at the top level instead of having disconnected `defineX` helpers.

# 8. Ideal end-to-end design

This is what the “good” version could look like:

```ts
const core = defineDialect("core")((d) => {
  const generatedFrom = d.edgeKind("generatedFrom", {
    endpoints: {
      artifact: d.endpoint("artifact").target(core.nodes.artifact).source(),
      source: d.endpoint("source").targetAnyGraphObject().target(),
    },
  });

  return {
    edges: {
      generatedFrom,
    },
  };
});

const domain = defineDialect("domain")((d) => {
  const entity = d.nodeKind("entity", {
    metadata: schema<{ name: string }>(),
  });

  const field = d.nodeKind("field", {
    metadata: schema<{ name: string; nullable: boolean }>(),
  });

  const ownsField = d.edgeKind("ownsField", {
    endpoints: {
      entity: d.endpoint("entity").target(entity).source(),
      field: d.endpoint("field").target(field).target(),
    },
  });

  return {
    nodes: { entity, field },
    edges: { ownsField },
  };
});

const app = defineDialect("app")((d) => {
  const action = d.nodeKind("action");
  const rule = d.nodeKind("rule");
  const field = d.import(domain.nodes.field);

  const guards = d.edgeKind("guards", {
    endpoints: {
      rule: d.endpoint("rule").target(rule).source(),
      action: d.endpoint("action").target(action).target(),
    },
  });

  const writes = d.edgeKind("writes", {
    endpoints: {
      action: d.endpoint("action").target(action).source(),
      field: d.endpoint("field").target(field).target(),
    },
    metadata: schema<{
      operation: "set" | "increment" | "append" | "delete";
      reversible?: boolean;
    }>(),
  });

  return {
    nodes: { action, rule },
    edges: { guards, writes },
  };
});

const react = defineTarget("react")((t) => ({
  artifacts: {
    component: t.artifactKind("component", {
      content: tsx(),
      path: pathTemplate("src/components/{name}.tsx"),
      metadata: schema<{ componentName: string }>(),
    }),
  },
}));

const kernel = createKernel({
  dialects: { core, domain, app },
  targets: { react },
});

const User = domain.entity("User")({
  fields: {
    id: t.uuid,
    email: t.email,
    archivedAt: t.optional(t.datetime),
  },
});

const canArchiveUser = app.rule("canArchiveUser")((ctx) =>
  expr.eq(ctx.actor.organizationId, ctx.user.organizationId)
);

const archiveUser = app.action("archiveUser")((ctx, action) =>
  action
    .input({
      actor: Actor,
      user: User,
    })
    .guard(canArchiveUser)
    .writes(User.fields.archivedAt, {
      operation: "set",
      reversible: true,
    })
);

const graph = kernel.graph.pipe(
  User,
  canArchiveUser,
  archiveUser,

  pass(app.passes.checkGuards),
  pass(app.passes.deriveAffectedQueries),

  emit(react.artifacts.component, {
    source: ref(UserListView),
    path: { name: "UserList" },
    metadata: {
      componentName: "UserList",
    },
    content: tsx`
      export function UserList() {
        return null;
      }
    `,
  }),
);
```

What this gives you:

```txt
dialects define typed vocabulary
types preserve decoded values
traits are target-safe and payload-safe
scopes become inferred ctx objects
artifacts are target/kind/content/source typed
bridge mutation disappears behind graph writer/pipe
graph steps compose everything
passes verify global semantics
```

# 9. The ideal layering

I would split the kernel into three layers.

## Layer 1: runtime IR

Simple, serializable, broad:

```ts
RuntimeGraph
RuntimeNode
RuntimeEdge
RuntimeArtifact
RuntimeType
RuntimeTrait
```

This is what you save, load, inspect, and pass between plugins.

## Layer 2: typed witnesses

Factories that create type-rich values:

```ts
defineDialect(...)
defineNodeKind(...)
defineEdgeKind(...)
defineType(...)
defineTrait(...)
defineTarget(...)
defineArtifactKind(...)
defineScope(...)
```

These centralize internal casts and preserve inference.

## Layer 3: composable authoring API

Everything becomes graph steps:

```ts
kernel.graph.pipe(
  entity(...),
  action(...),
  rule(...),
  edge(...),
  scope(...),
  artifact(...),
  pass(...),
);
```

This is the API users touch.

# 10. The core design rule

The current design says:

```txt
define broad object
store broad object
recover meaning later with string checks and casts
```

The ideal design says:

```txt
create typed witness
compose witness into graph step
kernel carries dialect/target generic
graph pipe accumulates state
queries infer from witness
dynamic data is decoded at boundaries
```

That is the version I would aim for.

Yes — the new TypeScript compiler changes the design calculus a lot.

But I would phrase it carefully:

```txt
Fast TypeScript makes “the graph in TypeScript” much more viable.

It does not make TypeScript a formal verification system.
```

TypeScript 7.0 Beta is the Go/native compiler line, and Microsoft says it is often about 10× faster than TypeScript 6.0, with shared-memory parallelism and structurally identical type-checking semantics to TS 6.0. It is available as `@typescript/native-preview@beta` and run via `tsgo`. ([Microsoft for Developers][1])

That matters for Gen2 because our biggest fear with “let TypeScript see the graph” was compile-time cost and editor collapse. The new compiler gives us a larger type-level budget.

## What this unlocks

We can make the **authoring graph** much more TypeScript-native.

For example:

```ts
const graph = createGen()
  .use(domain)
  .use(app)
  .use(ui)
  .graph.pipe(
    User,
    canArchiveUser,
    archiveUser,
    UserListView,
  );
```

and TypeScript can know things like:

```txt
User exists
User.fields.email exists
archiveUser writes User.fields.archivedAt
canArchiveUser is a Rule<boolean>
UserListView uses listActiveUsers
ui behavior target slot is interactive
```

So yes, we can push more checks into TypeScript:

```txt
wrong edge endpoint
wrong field type
unknown slot
action writes non-field
behavior attaches to non-interactive slot
rule body is not boolean
operation args mismatch
trait target mismatch
artifact metadata mismatch
unregistered dialect in graph step
```

That is a big deal.

## But it is not formal verification

TypeScript’s own design goals explicitly say a sound or “provably correct” type system is a non-goal; TypeScript balances correctness and productivity instead. It also uses a fully erasable structural type system. ([GitHub][2])

So TypeScript gives us:

```txt
excellent static checking
rich inference
editor feedback
compile-time invalid-state prevention
```

It does not give us:

```txt
soundness
proofs
semantic equivalence
total correctness
target correctness
law correctness
security guarantees
runtime data validity
```

A faster compiler does not change that. It gives us more performance headroom, not new proof semantics.

## The right design is “TypeScript as proof-carrying authoring,” not “TypeScript as the only verifier”

I would use TypeScript for **local structural correctness**.

Examples:

```ts
edge(app.edges.writes, {
  action: ref(archiveUser),
  field: ref(User.fields.archivedAt),
});
```

TypeScript can reject:

```ts
edge(app.edges.writes, {
  action: ref(User.fields.email),
  field: ref(archiveUser),
});
```

It can also check operation calls:

```ts
expr.call(AddNumber, expr.literal(t.number, 1), expr.literal(t.number, 2));
```

and reject:

```ts
expr.call(AddNumber, expr.literal(t.number, 1), expr.literal(t.string, "two"));
```

That is compile-time verification of construction rules.

But global properties still need passes:

```txt
Every action exposed to the client has server enforcement.
Every at-least-once dispatch has idempotency.
Every rule used as RLS is SQL-lowerable.
Every required provider is satisfied in the target boundary.
Every generated artifact traces back to source graph facts.
No sensitive field crosses a client boundary.
A state-machine transition is total/exhaustive.
```

Those are graph verification problems, not just TypeScript type problems.

## “Entire graph in TypeScript” should mean three artifacts

I would not make the runtime graph itself an enormous type-level object only.

I would use three layers:

```txt
1. TypeScript authoring graph
   Rich typed witnesses, builders, .class forms, graph.pipe.

2. Runtime graph IR
   Simple serializable nodes/edges/traits/refs/artifacts.

3. Generated .d.ts graph witness
   A compact static view of the graph for editor/checker feedback.
```

So users write:

```ts
class User extends domain.entity.class("User", {
  fields: {
    id: field(t.uuid),
    email: field(t.email),
  },
}) {}
```

Gen2 emits/stores:

```json
{
  "nodes": [
    { "id": "entity:User", "kind": "domain.entity" },
    { "id": "field:User.email", "kind": "domain.field" }
  ],
  "edges": [
    {
      "kind": "domain.ownsField",
      "endpoints": {
        "entity": "entity:User",
        "field": "field:User.email"
      }
    }
  ]
}
```

And optionally generates:

```ts
declare namespace GraphWitness {
  export const User: EntityWitness<{
    id: Uuid;
    email: Email;
  }>;

  export const archiveUser: ActionWitness<{
    writes: [typeof User.fields.archivedAt];
  }>;
}
```

That gives us fast editor/type-checking without making the serialized graph depend on TypeScript’s type system.

## What should move into TypeScript types

With TS 7 speed, I would push more of this into types:

```txt
Dialect registration
  graph only accepts steps from registered dialects

Endpoint correctness
  edge endpoints match required node kinds

Trait application
  trait target and payload are checked

Operation calls
  args, output, requirements, effects inferred

Scope contexts
  ctx.input, ctx.actor, ctx.session, ctx.before, ctx.after

UI slots
  behavior target requirements match slot traits

Artifact kinds
  content, metadata, source kinds, path params

Invariant families
  params infer subject/path/violation shape

State machines
  transition from/to variants checked

Graph pipe
  accumulated graph state for named symbols when feasible
```

This is where TypeScript shines.

## What should stay in graph passes

Do not try to encode these primarily as type-level computation:

```txt
reachability / graph shaking
cycle checks
global provider satisfaction
SQL lowerability
client/server leakage
operation law validity
equivalence between server rule and DB predicate
migration diff correctness
incremental view maintenance safety
offline replay safety
deployment resource availability
AI-imported JSON spec validity
runtime data validation
```

These should be `verify`, `derive`, `legalize`, and `lower` passes with typed diagnostics.

TypeScript can help construct the graph correctly. Passes prove or reject global semantic properties at graph scale.

## Does this provide formal verification?

Not by itself.

The closest honest wording is:

```txt
TypeScript provides static construction verification.

Gen2 passes provide semantic graph verification.

Formal verification would require a proof backend.
```

If we want actual formal verification, Gen2 could add a proof/solver target:

```txt
Gen2 graph
  -> SMT / Z3 constraints
  -> Alloy model
  -> TLA+ spec
  -> Lean theorem skeleton
  -> property-test generator
```

Examples:

```txt
state-machine reachability
invariant preservation under all actions
authorization non-bypass
queue idempotency/retry safety
migration preserves data constraints
operation laws over finite domains
```

That would be real “formal-ish” or formal verification depending on target and proof discipline.

TypeScript is the front-line checker. It is not the proof engine.

## The updated architecture implication

I would revise the mental model to:

```txt
TypeScript authoring layer:
  high-inference, witness-rich, compile-time local correctness

Graph IR:
  simple, serializable, indexed, target-neutral source of truth

Pass verifier:
  global semantic validation with diagnostics

Optional proof targets:
  SMT/Alloy/TLA+/Lean/property tests for stronger claims
```

That is a very strong architecture.

## Practical recommendation

Use the new TS compiler to be more ambitious, but do not overfit the graph to TypeScript.

Good:

```ts
const graph = kernel.graph.pipe(
  User,
  canArchiveUser,
  archiveUser,
);
```

Good:

```ts
type AppGraph = InferGraph<typeof graph>;
```

Good:

```ts
expectTypeOf(
  graph.edges.ofKind(app.edges.writes).targets("field"),
).toEqualTypeOf<readonly FieldRef[]>();
```

Risky:

```ts
type EntireApplicationProof = ProveAllInvariants<
  ProveAllTargets<
    ProveAllSyncPlans<
      typeof graph
    >
  >
>;
```

That will become unreadable and brittle even with a faster compiler.

The best split:

```txt
Use TypeScript to prevent bad graph construction.
Use Gen2 passes to validate whole-graph semantics.
Use proof/solver targets for true formal claims.
```

So yes: the new compiler makes an “entire graph in TypeScript” authoring experience much more realistic. But the formal verification story should be layered, not reduced to TypeScript.
