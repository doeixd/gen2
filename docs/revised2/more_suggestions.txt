
This batch is **foundational**. These files are not just another feature area; they are the lower-level type/operation substrate that the rest of Gen2 depends on.

My read:

```txt
semantic.ts
  strong ergonomic semantic type layer, but should become graph-native Type dialect IR

representation.ts
  very good physical/wire representation layer; keep it separate from semantic types

operation.ts
  important operation/law/effect model, but should merge with the newer Operation dialect design

implementation.ts
  useful minimal AST bridge, but should eventually be replaced by/lowered from Expr IR

trait(1).ts
  useful seed, but too type-local and underpowered for final graph-wide traits
```

## 1. `representation.ts`: keep this almost exactly as a low-level layer

This is one of the cleanest pieces. It separates **semantic type** from **physical/wire representation**, with precise layouts like `u8`, `i64`, `fixed_string`, `bytes`, `optional`, `array`, `map`, `struct`, `tagged`, and `document`. It also includes byte width, signedness, endianness, text encoding, comparison semantics, aggregate semantics, and precision checks.

That separation is exactly right.

You want:

```txt
SemanticType:
  email
  money
  datetime
  UserId
  IncidentStatus

Representation:
  text
  i64
  fixed_bytes(16)
  tagged(...)
  struct(...)
```

This is the foundation that lets Gen2 generate exact target artifacts:

```txt
Postgres column types
SQLite column types
Protobuf fields
Cap'n Proto schemas
JSON schema
binary encodings
check constraints
indexes
sortability checks
aggregation checks
```

The key design win is that representation carries target-relevant facts without polluting semantic meaning:

```ts
datetime()
  semantic: Date
  storage repr: i64 microseconds
  wire repr: maybe ISO string
```

I would keep `Representation` as a **standard type-system dialect object**, but make it graph-visible:

```txt
Node(Type): datetime
Node(Representation): i64
Edge(TypeHasStorageRepresentation): datetime -> i64
Edge(TypeHasWireRepresentation): datetime -> iso_string
Trait(TotalOrdering): i64
Trait(Aggregatable): i64
```

### Suggested improvement

Add explicit target mapping/legalization:

```ts
const datetime = t.datetime({
  storage: repr.i64(),
  wire: repr.text({ encoding: "utf8" }),
});

targets.postgres.legalize(datetime);
// datetime -> TIMESTAMPTZ or BIGINT depending target profile
```

Also, `Representation.metadata` should stay passive. Any behavior like “orderable,” “aggregateable,” “fixed width,” “supports exact equality,” or “lossy” should be a field, trait, or derived fact, not hidden in metadata.

## 2. `semantic.ts`: good ergonomic layer, but it should not remain object-only

`semantic.ts` defines the ergonomic domain-facing type layer: built-ins like `string`, `int`, `bigint`, `decimal`, `money`, `boolean`, `uuid`, `datetime`, `json`, `email`, `url`, `phone`, arrays, structs, tagged unions, branded types, literals, objects, validators, serializers, custom types, factories, extension, nullable types, traits, and merge strategies. It explicitly says semantic types drive TypeScript inference, validation traits, serializer/deserializer wiring, and column codegen.

That is the right public API.

But architecturally, this file currently packs too much into one runtime object:

```ts
interface SemanticType {
  name
  kind
  ts_type_name
  storage_repr
  wire_repr
  has_serializer
  has_deserializer
  server_only
  traits
  enum_values
  validate
  merge_strategy
}
```

That is fine as a transitional object, but final Gen2 should lower each behavior-relevant part into graph facts.

Final graph model:

```txt
Node(Type): email
Node(Representation): text
Node(Validator): email_format
Node(Serializer): email_to_wire
Node(MergeStrategy): last_write_wins

Edge(TypeHasStorageRepresentation): email -> text
Edge(TypeHasWireRepresentation): email -> text
Edge(TypeHasValidator): email -> email_format
Edge(TypeUsesMergeStrategy): email -> merge_strategy
Trait(ClientSafe): email
Trait(Pii): email
```

### Important correction

`server_only` on `SemanticType` is probably too coarse.

A type itself is rarely inherently server-only. Usually a **field**, **projection**, **provider**, or **usage** is server-only.

Better:

```txt
Type:
  SecretString

Field:
  User.passwordHash has Trait(ServerOnly)

Provider:
  EmailApiKey has Trait(Secret)

Projection:
  ClientUser excludes passwordHash
```

You can keep `t.secretString()` as a convenience, but internally it should apply traits/policies to usages, not only mutate a type flag.

### Branded types are excellent

`brand("UserId", uuid())` is very important. It gives nominal distinctions while reusing physical representation.

This should become a first-class graph relation:

```txt
Node(Type): UserId
Node(Type): uuid
Edge(TypeBrands): UserId -> uuid
Edge(TypeHasRepresentation): UserId -> fixed_bytes(16)
```

This improves inference and prevents accidental ID mixing.

## 3. `operation.ts`: important, but it should merge with the operation/law/effect dialect

This file defines a unified `Operation` model replacing separate unary/binary/comparison/aggregate/reducer/predicate/effect operation types. It models operation kinds, capabilities, laws, effects, runtime implementations, and checks for operation invariants like boolean outputs for predicates/comparisons, non-empty effects for effect operations, and duplicate implementations per runtime.

The direction is good.

The key ideas to keep:

```txt
Operation kind
input/output type
capabilities
laws
effects
implementations
invariant checks
plugin-branded capabilities/effects
```

But final architecture should avoid string-heavy capability/law/effect lists as the main semantic model.

Current:

```ts
capabilities: Capability[]
laws: Law[]
effects: Effect[]
implementations: Implementation[]
```

Final graph:

```txt
Node(Operation): add
Node(Capability): deterministic
Node(Law): associative
Node(Effect): db_write
Node(Implementation): postgres.add

Edge(OperationRequiresCapability): add -> deterministic
Edge(OperationHasLaw): add -> associative
Edge(OperationHasEffect): sendEmail -> email
Edge(OperationHasImplementation): add -> postgres.add
```

And laws need richer assurance than `"claim" | "tested" | "proven"` eventually. You already moved toward this in the newer design:

```txt
asserted
derived
tested
checked_by_target
proved_by_solver
by_construction
trusted_target
```

So I’d update this file’s `Law` to align with the wider assurance model.

### Capabilities and effects should be standard dialect concepts

The capability list is useful, but it mixes many categories:

```txt
purity/determinism
runtime placement
target features
database features
effect categories
platform APIs
```

I’d split them conceptually:

```txt
Trait:
  pure
  deterministic
  reversible
  cacheable
  serverOnly
  clientSafe

Effect:
  db_read
  db_write
  email
  queue
  network
  random
  clock

TargetCapability:
  joins
  jsonb
  transactions
  queues
  workers
  full_text_search

Requirement:
  needs provider/service/context
```

They can still share a builder style, but passes should know which category they are reasoning about.

## 4. `implementation.ts`: good bridge, but final implementation bodies should be Expr/target IR

`implementation.ts` defines a lightweight `ImplementationAst` with `kind`, `children`, optional `ref`, and optional serialized literal. It exists because `types/` cannot import the expression package without a circular dependency.

That is a valid transitional compromise.

But final design should try to eliminate this duplicate AST long-term.

You likely want:

```txt
Expr IR:
  typed, operation-backed, analyzable

Implementation IR:
  target-specific lowered form

Opaque implementation:
  declared blast radius
```

So instead of `ImplementationAst` as a permanent parallel AST, I’d model implementation bodies as:

```ts
type ImplementationBody =
  | { kind: "expr"; expr: ExprRef }
  | { kind: "target_ir"; target: TargetRef; node: TargetIrRef }
  | { kind: "opaque"; symbol: string; blastRadius: OpaqueContract };
```

The current lightweight AST is useful for avoiding cycles, but the final package structure should solve the dependency layering:

```txt
kernel
type dialect
operation dialect
expr dialect
implementation/lowering dialect
```

Then `types/` does not need to import full `expression`; both can depend on kernel symbols and refs.

## 5. `trait(1).ts`: useful seed, but too narrow for final traits

This file defines traits as reusable validation/storage/behavior/privacy/UI modifiers attached to semantic types, plus typed expressions for validation/storage expressions and a stub `checkTraitApplications`.

The idea is right, but the scope is too narrow.

Current trait:

```ts
interface Trait {
  name
  applies_to?: string
  validate_expression?
  error_message?
  storage_expression?
  queryable
}
```

This is more like a **type annotation** than the final Gen2 trait model.

Final traits should be graph-wide and target-typed:

```txt
Trait can apply to:
  Type
  Field
  Entity
  Operation
  Action
  Query
  Resource
  Provider
  Boundary
  Queue
  UI Component
  Artifact
  MigrationStep
```

And trait definitions should have typed targets:

```ts
const serverOnly = trait.define("serverOnly", {
  appliesTo: [domain.nodes.field, provider.nodes.provider, callable.nodes.action],
  payload: t.object({
    reason: t.optional(t.string),
  }),
});
```

Trait applications should be graph facts:

```txt
TraitApplication:
  trait: serverOnly
  target: User.passwordHash
  payload: { reason: "password hash must never hydrate" }
```

### `applies_to?: string` should become typed target constraints

This is important. String matching on semantic type names will become fragile.

Replace:

```ts
applies_to?: string
```

with something like:

```ts
appliesTo: TraitTargetConstraint
```

Examples:

```ts
appliesTo: type.kind("email")
appliesTo: domain.nodes.field
appliesTo: operation.nodes.operation
appliesTo: target.hasTrait(traits.clientRenderable)
```

## 6. The deeper architectural point: you need a clean type stack

These files reveal the right stack:

```txt
Representation
  physical/wire layout

SemanticType
  domain meaning + TS decoded type

Serializer / Transform
  conversion between semantic/wire/storage types

Operation
  typed computation over semantic types

Expr
  operation application tree

Trait
  semantic claim on graph object

Law
  semantic claim about operation behavior

Implementation
  target-specific realization of operation/expr
```

I would make that explicit in the design doc and README.

A good final model:

```txt
Type layer:
  Representation
  Type
  Serializer
  Transform

Logic layer:
  Operation
  Expr
  Rule
  Law

Behavior layer:
  Action
  Query
  Effect
  Requirement
  Provider

Compiler layer:
  Pass
  Diagnostic
  Artifact
```

## 8. Concrete changes I’d make

### `SemanticType`

Keep:

```txt
name
kind
decoded TypeScript phantom
storage representation
wire representation
serializer/deserializer concept
traits
enum values
validators
merge strategy
brands
object/struct/tagged helpers
```

Change:

```txt
server_only boolean
  -> trait application on type/field/provider/projection

has_serializer / has_deserializer booleans
  -> edges to Serializer nodes, or derived facts from serializer existence

merge_strategy field
  -> TypeUsesMergeStrategy / FieldUsesMergeStrategy edges

traits array
  -> trait applications with typed target/payload

validate function
  -> Validator node or opaque validator contract

ts_type_name string
  -> okay for artifact generation, but canonical TS witness should be generated structurally
```

### `Representation`

Keep mostly as is.

Add:

```txt
target legalization results
lossiness markers
canonical textual form
stable representation IDs
```

Example:

```ts
repr.i64({ semantic: "microseconds_since_epoch" })
repr.decimal({ precision: 19, scale: 4 })
repr.text({ collation: "case_insensitive" })
```

### `Operation`

Keep:

```txt
unified Operation
operation kinds
capabilities
effects
laws
implementations
duplicate implementation checks
plugin-branded extension hooks
```

Change:

```txt
Law assurance enum
  -> shared assurance model

capabilities/effects/laws arrays
  -> graph trait/edge applications

ImplementationAst
  -> ExprRef / TargetIrRef / OpaqueContract

requires_numeric / requires_orderable booleans
  -> type constraints or operation input constraints
```

For example:

```ts
const sum = operation.aggregate("sum", {
  input: t.generic("T").where(type.traits.numeric),
  output: t.same("T"),
  laws: [laws.associative(), laws.commutative()],
});
```

### `Trait`

Keep:

```txt
trait concept
validation expression
storage expression
queryable marker
trait application
```

Change:

```txt
applies_to string
  -> typed target constraints

Trait attached only to SemanticType
  -> graph-wide TraitApplication

checkTraitApplications stub
  -> real pass over graph trait applications

error_message
  -> DiagnosticDefinition edge

validate_expression/storage_expression
  -> Expr nodes / Transform nodes
```

## 9. How this improves code generation from schema + operations + rules

This batch strengthens the core generation story.

With `SemanticType + Representation`, Gen2 can generate exact storage and wire artifacts:

```txt
t.uuid with fixed_bytes(16)
  -> Postgres UUID or BYTEA depending target profile
  -> JSON string codec
  -> OpenAPI format uuid
  -> TypeScript string brand

t.datetime with i64 storage
  -> BIGINT microseconds in storage target
  -> ISO string in OpenAPI
  -> Date in TS witness
  -> serializer/deserializer code
```

With `Operation + Law + Effect`, Gen2 can generate safe runtime behavior:

```txt
operation is patchable + invertible
  -> optimistic update
  -> rollback plan

operation is idempotent
  -> safe retry
  -> queue dedup test

operation has db_write effect
  -> server placement required
  -> transaction boundary
  -> cannot run at edge unless target supports it
```

With `Trait`, Gen2 can generate validation, storage, UI, and docs:

```txt
field has validation trait
  -> form validation
  -> server validation
  -> OpenAPI schema
  -> generated tests
  -> docs
```

So these files are exactly in the path of the README’s “schema + operations + rules generate everything” story.

## 10. Verdict

This batch is very important and mostly directionally right.

```txt
representation.ts
  strongest as-is; keep as the physical/wire substrate.

semantic.ts
  good public type API; should lower to graph-native Type/Serializer/Merge/Trait facts.

operation.ts
  good unified model; should become graph-native Operation/Law/Effect/Implementation dialect.

implementation.ts
  useful temporary lightweight AST; final design should use Expr/TargetIR/OpaqueContract.

trait(1).ts
  useful seed; final traits must be graph-wide, typed, payload-bearing, and diagnostic-linked.
```

The big design recommendation:

```txt
Make the type system explicitly layered:

SemanticType is meaning.
Representation is layout.
Serializer/Transform is conversion.
Operation is computation.
Expr is operation use.
Trait is a graph claim.
Law is a behavioral claim.
Implementation is target realization.
```

That stack gives Gen2 the precision it needs to generate high-quality database schemas, codecs, APIs, UI, tests, sync plans, migrations, and target-specific code from one semantic graph.

I think the library is **very compelling**, but it is also at the point where the main risk is no longer “is the idea good?” The idea is good. The main risk is **scope control, DX, and making the graph feel helpful instead of heavy**.

My honest take:

```txt
This is not just a framework.
It is a semantic application compiler.

If executed well, it could be unusually powerful.
If executed poorly, it could become an over-abstracted meta-framework.
```

## What is genuinely strong

The strongest idea is:

```txt
Define semantic facts once.
Derive implementations, tests, docs, migrations, UI, sync, deployment, and diagnostics from the graph.
```

That is a real thesis. It is not cosmetic.

Most app frameworks encode meaning in scattered places:

```txt
database schema
server handlers
client hooks
forms
lists
cache invalidation
OpenAPI
tests
docs
deployment config
auth policies
```

Gen2’s bet is that those are all projections of the same semantic graph. I think that is the right bet.

The second strongest idea is the separation between:

```txt
Authoring API:
  rich, typed, ergonomic, recipe-driven

Runtime/compiler IR:
  boring graph of Node / Edge / Trait

Passes:
  verify, derive, canonicalize, legalize, lower, emit
```

That separation is what keeps the project from collapsing under its own abstraction.

## The library has a real identity

A lot of libraries are “React but better,” “Prisma but better,” “tRPC but better,” or “Rails but TypeScript.”

This is more like:

```txt
MLIR for application semantics
+
Rails-style productivity
+
Effect-style explicitness
+
semantic graph devtools
+
AI-editable application IR
```

That is distinctive.

The best possible pitch might be:

```txt
Gen2 is a typed semantic graph compiler for full-stack applications.

It lets you define domain, rules, actions, UI, sync, policies, storage,
deployment, tests, docs, and migrations as one inspectable graph, then derives
target-specific artifacts from verified semantics.
```

That is a strong category.

The main worry is **too much surface area too early**.

You now have concepts for:

```txt

fields
relations
types
transforms
expressions
operations
laws
rules
policies
actions
queries
resources
state
sync

boundary

effects
```

All of those are defensible. But users cannot meet them all at once.

So the product lives or dies on progressive disclosure.

The library needs three clearly different entry points:

```txt

  app.kit.saas(...)
  app.crud(...)
  app.form.fromAction(...)
  app.ui.list(...)
  app.deploy(...)

Compiler/plugin author:
  dialects, passes, protocols, target IR, lower/emit
```

If users hit dialect/pass terminology in the first 15 minutes, the library will feel intimidating.

## The best version of this library

The best version is not a giant DSL where users manually define every graph fact.

The best version is:

```ts
const app = gen.quick.saas("OpsDesk", {
  auth: "tenant",
  database: "postgres",
  ui: "dashboard",
});

const Incident = app.entity("Incident", {
  title: t.string,
  severity: t.enum(["sev1", "sev2", "sev3", "sev4"]),
  status: app.stateMachine(["open", "acknowledged", "resolved"]),
});

app.crud(Incident);
app.dashboard(Incident);
app.deploy(targets.alchemy);
```

Then users can expand:

```ts
app.expand(Incident);
app.preview(IncidentDashboard);
app.explain(acknowledgeIncident);
```

And progressively reveal the graph.

That would be magical.

## The biggest DX requirement

The library needs to make derived behavior visible.

Because the compiler derives so much, users will constantly ask:

```txt
Why did this invalidate that?
Why is this server-only?
Why did this form get this widget?
Why is this action not offline-safe?
Why did this migration become destructive?
Why is this target unsupported?
Why did this provider leak to the client?
```

So `explain(...)` is not optional. It is central.

I would prioritize these APIs:

```ts
app.preview(x)
app.explain(edgeOrDiagnostic, subject)
app.expand(recipe)
app.traceArtifact(path)
app.capabilities.report(...)
app.diff(previous, current)
```

Without those, Gen2 feels like magic. With those, it feels like a compiler.

## The best technical direction

The architectural direction I’d keep strict:

```txt
No side registries as source of truth.
No behavior hidden in metadata.
No raw strings for semantic identity.
No target emitters reading high-level source IR directly.
No recipe that cannot expand/explain itself.
No opaque code without declared blast radius.
```

The graph should own meaning.

Metadata should describe. It should not control behavior.

Targets should consume legalized target dialect IR, not arbitrary source objects.

## The most important next implementation milestone

I would stop adding concepts for a bit and build the spine:

```txt
1. Stable Id / Ref / SymbolDef
2. Typed NodeKind / EdgeKind / TraitDef witnesses
3. Indexed GraphStore + GraphView
4. GraphFragment / module composition
5. Dialect registry
6. Pass registry and pipeline runner
7. Diagnostics with remediation
8. Entity / Field / Type graph-native implementation
9. Requirement / Provider / Placement graph-native implementation
10. Query / Action read-write edges
```

Once that spine is excellent, everything else becomes much easier.

If the spine is weak, every advanced feature becomes painful.

## The biggest product opportunity

AI app-building.

This architecture is unusually well-suited for AI because the graph gives agents:

```txt
structured facts
stable refs
diagnostics
repair hints
artifact provenance
semantic diffs
textual IR
safe import/export boundaries
```

Most AI coding systems edit source code directly and hope tests catch issues. Gen2 could let AI edit semantic graph facts, run diagnostics, apply graph patches, and explain consequences before emitting code.

That is a major differentiator.

The AI loop should be:

```txt
Prompt
  -> candidate graph patch
  -> verify
  -> diagnostics with repairs
  -> semantic diff
  -> user review
  -> emit artifacts
```

That is much safer than “AI rewrote your app.”

## The library’s biggest danger

Trying to be:

```txt
ORM
RPC framework
React framework
state manager
workflow engine
deployment tool
migration engine
test generator
AI builder
```

as separate products.

It should not present itself that way.

It should present itself as:

```txt
one semantic compiler
many projections
```

That framing keeps the project coherent.

Yes. Writing the full example exposed a few design improvements I’d make before locking the library shape.

The big theme: **the architecture is right, but the public API needs more “progressive disclosure.”** The ultimate API can support everything, but most users and AI agents should not have to touch every layer manually.

## 1. Add higher-level “application kits”

The example required the user to wire domain, rules, actions, queries, events, dispatch, reactivity, UI, storage, and deployment separately. That is powerful, but verbose.

I’d add opinionated kits that expand into graph facts:

```ts
const app = gen.kit.saas({
  tenant: Organization,
  user: User,
  auth: AuthSession,
  database: targets.postgres,
  frontend: targets.react,
});
```

Then common patterns become one call:

```ts
const IncidentFeature = app.feature("Incident", {
  entity: Incident,
  lifecycle: IncidentStatus,
  list: {
    key: "openIncidents",
    query: "listOpenIncidents",
  },
  actions: {
    acknowledge: {
      from: "open",
      to: "acknowledged",
      guard: canAcknowledgeIncident,
    },
    resolve: {
      from: ["acknowledged", "mitigated"],
      to: "resolved",
      guard: canResolveIncident,
    },
  },
  ui: {
    dashboard: true,
    detail: true,
  },
  sync: {
    optimistic: true,
    offline: ["acknowledge"],
  },
});
```

Internally this still emits nodes/edges/traits. But users get a much smaller surface.

## 2. Make “feature modules” a first-class concept

The example would be easier if everything related to incidents lived in a typed graph fragment:

```ts
export const IncidentModule = gen.module("incident")((m) =>
  m
    .entity(Incident)
    .rules(canViewIncident, canManageIncident)
    .queries(listOpenIncidents, getIncidentDetail)
    .actions(declareIncident, acknowledgeIncident, resolveIncident)
    .events(IncidentDeclared, IncidentAcknowledged, IncidentResolved)
    .ui(IncidentDashboard)
    .storage(IncidentStorage)
);
```

Then:

```ts
const appGraph = gen.graph.pipe(
  CoreModule,
  AuthModule,
  IncidentModule,
  NotificationModule,
  DeploymentModule,
);
```

This gives agents and humans natural edit boundaries. It also helps graph shaking, documentation, tests, and ownership.

## 3. Add “graph recipes” for common patterns

There are patterns that should not be manually assembled every time:

```txt
CRUD resource
state-machine action
event + outbox dispatch
notification queue
audit log
tenant-scoped policy
client-safe projection
optimistic mutation
offline command
JSON-render screen
```

Example:

```ts
const acknowledgeIncident = gen.recipes.stateTransitionAction({
  name: "acknowledgeIncident",
  entity: Incident,
  field: Incident.fields.status,
  from: "open",
  to: "acknowledged",
  guard: canAcknowledgeIncident,
  audit: true,
  event: "IncidentAcknowledged",
  optimistic: true,
});
```

This recipe can still expose the generated pieces:

```ts
acknowledgeIncident.action;
acknowledgeIncident.event;
acknowledgeIncident.mutation;
acknowledgeIncident.auditEntry;
acknowledgeIncident.tests;
```

Recipes make the system usable without compromising the kernel.

## 4. Introduce “capability reports” as a product feature

Gen2 should be able to explain what each target can or cannot support:

```ts
const report = appGraph.capabilities.report({
  targets: [targets.postgres, targets.react, targets.alchemy],
});
```

Output:

```txt
IncidentDashboard
  React: supported
  JSON-Render: supported
  Client rule evaluation: partial
    canResolveIncident reads server-only field Incident.assignedTeamId

IncidentSyncPlan
  Optimistic patches: supported for acknowledgeIncident
  Offline replay: unsupported for resolveIncident
    reason: missing idempotency strategy
```

This would be extremely helpful for AI repair and developer trust.

## 5. Make diagnostics the primary UX, not an afterthought

The design already treats diagnostics as first-class, which is right. The current architecture doc also emphasizes typed diagnostics with remediation hints for the AI repair loop.

I would go further: every advanced API should define its failure modes first.

For example, `dispatch.outbox(...)` should come with built-in diagnostics:

```txt
dispatch:at_least_once_requires_idempotency
dispatch:outbox_requires_persistent_storage
dispatch:handler_effect_not_supported_by_boundary
dispatch:event_payload_not_serializable
```

A good Gen2 API is one where the user can do something wrong and get a **specific graph repair**, not a vague TypeScript error.

## 6. Add assurance levels for laws and traits

The example uses laws like:

```ts
laws.idempotent(...)
laws.rollbackSafe(...)
laws.validStateTransition(...)
```

But not all laws are equally trustworthy. Some are compiler-derived, some are asserted by the user, some are tested, and some are formally proven.

I’d model this explicitly:

```ts
laws.idempotent({
  key: ({ input }) => input.updateId,
  assurance: "by_construction",
});
```

or:

```ts
laws.commutative({
  assurance: gen.assurance.propertyTest({
    samples: 10_000,
  }),
});
```

Possible assurance levels:

```txt
asserted
derived
tested
checked_by_target
proved_by_solver
by_construction
```

This prevents “law traits” from becoming wishful metadata.

## 7. Make unsafe/opaque code painfully explicit

Opaque code is necessary, but the API should force users to declare its blast radius:

```ts
expr.opaque("riskScore", {
  input: { incident: Incident },
  output: t.number,
  placement: ServerBoundary,

  reads: [
    Incident.fields.severity,
    Incident.fields.projectId,
  ],

  effects: [],
  lowerability: {
    sql: false,
    client: false,
  },

  fallback: {
    reactivity: "invalidate",
    target: "server_only",
  },
});
```

This keeps escape hatches safe.

Rule of thumb:

```txt
Opaque code is allowed.
Unknown impact is not.
```

## 8. Add projection APIs as a first-class safety feature

A lot of client/server leakage problems can be solved with projections.

Example:

```ts
const IncidentCard = gen.projection("IncidentCard", {
  from: Incident,
  fields: {
    id: Incident.fields.id,
    title: Incident.fields.title,
    severity: Incident.fields.severity,
    status: Incident.fields.status,
    updatedAt: Incident.fields.updatedAt,
  },
  placement: ClientBoundary,
});
```

Then UI uses:

```ts
OpenIncidentsResource.output(t.array(IncidentCard.type));
```

This gives the compiler a safe shape for client data and avoids accidentally exposing server-only fields.

## 1. `query.ts`: keep the semantics, split the layers

This file is a strong seed for the callable/query dialect. It already models structured query semantics: source, predicate, projection, joins, order, limit, offset, group-by, result type, requirements, effects, target runtimes, and target stores. It also includes cross-store composition and planning machinery through `QueryBackedField`, `CrossStoreQuery`, `StoreQueryPlan`, `FieldAssignment`, and `QueryPlan`.

That is exactly the kind of information Gen2 needs for:

```txt id="atngq5"
query lowering
read-edge derivation
sync planning
projection safety
cross-store planning
materialized views
server composition
target capability checking
```

But I would not keep `QueryExpression` as one large standalone object that owns everything.

I would split it into graph concepts.

### Current shape

```txt id="c8ey4j"
QueryExpression
  source
  predicate
  projection
  joins
  order_by
  limit / offset
  group_by
  result_type
  requirements
  effects
  target_runtimes
  target_stores
```

### Revised graph shape

```txt id="jbbgoa"
Node(Query)
Node(QueryPlan)
Node(QuerySource)
Node(QueryProjection)
Node(QueryJoin)
Node(QueryOrderBy)
Node(CrossStoreCompositionPlan)
Node(StoreQueryPlan)

Edges:
  QueryHasSource
  QueryHasPredicate
  QueryProjectsField
  QueryUsesJoin
  QueryOrdersBy
  QueryGroupsBy
  QueryReturnsType
  QueryRequires
  QueryHasEffect
  QueryTargetsRuntime
  QueryTargetsStore
  QueryHasPlan
  QueryReadsField
  QueryReadsEntity
  QueryReadsRelation
  QueryLoweredTo
```

The public API can still look like:

```ts id="gx8dte"
const listOpenIncidents = app.query("listOpenIncidents")((ctx, q) =>
  q
    .from(Incident)
    .where((i) => expr.not(expr.includes(["resolved", "cancelled"], i.status)))
    .select(IncidentCard)
    .orderBy((i) => [i.severity.desc(), i.updatedAt.desc()])
    .key(OpenIncidentsKey)
);
```

But internally, the query should lower to graph facts.

## 2. Query planning belongs in passes, not the source query object

The planning types are valuable:

```txt id="v9oyr0"
CrossStoreQuery
StoreQueryPlan
FieldSource
FieldAssignment
QueryPlan
QueryPlanner
```

But those are derived/target-planning artifacts, not the logical query source itself. `query.ts` currently puts the logical query IR and compiled planning IR side-by-side.

In the new architecture:

```txt id="70y3op"
Logical query dialect:
  Query, source, predicate, projection, order, group, result type

Derive passes:
  QueryReadsField
  QueryReadsEntity
  QueryRequiresProvider
  QueryKeyDerivation

Legalize/lower passes:
  QueryPlan
  StoreQueryPlan
  CrossStoreCompositionPlan
  FieldAssignment
```

So I would keep these concepts, but move them into stages:

```txt id="smkxps"
query.ts
  logical query builders and graph-lowering helpers

query-plan.ts
  derived plan dialect nodes and protocols

query-passes.ts
  verify/derive/legalize passes

query-views.ts
  graph views for query dependencies
```

## 3. Query builder needs better inference

The current fluent builder is a good start, but it has a few type-inference compromises. For example, `select` returns `readonly InferField<Fields[number]>[]`, which loses object/alias shape. The implementation also sets `result_type` to the first selected field’s semantic type, which is a placeholder rather than a correct projection type.

I would redesign query projection around named object projection:

```ts id="xz720j"
const q = query.from(User)
  .select({
    id: User.fields.id,
    email: User.fields.email,
    displayName: User.fields.displayName,
  });
```

Infer:

```ts id="2k7x0o"
{
  id: Uuid;
  email: Email;
  displayName: string;
}
```

Instead of:

```ts id="5f0r1r"
readonly (Uuid | Email | string)[]
```

Support array projection as a lower-level mode if needed, but default to object projection because APIs, UI, JSON, OpenAPI, and docs usually need named outputs.

Better shape:

```ts id="vvz7ah"
type ProjectionSpec = Record<
  string,
  FieldRef | Expr | AggregateCall | NestedProjection
>;

type InferProjection<P> = {
  [K in keyof P]: InferProjectionValue<P[K]>;
};
```

Then:

```ts id="t73g6t"
query
  .from(Incident)
  .select({
    id: Incident.fields.id,
    title: Incident.fields.title,
    severity: Incident.fields.severity,
    status: Incident.fields.status,
  });
```

This also dovetails with the projection API we discussed.

## 4. Query sources should be refs/witnesses, not object pointers

`QuerySource` currently holds optional direct `Entity`, `Relation`, `QueryExpression`, or `Expr` objects.

For the new graph model, make source identity ref-based:

```ts id="egr684"
type QuerySource =
  | { kind: "entity"; entity: Ref<typeof domain.nodes.entity> }
  | { kind: "relation"; relation: Ref<typeof domain.edges.relation> }
  | { kind: "subquery"; query: Ref<typeof callable.nodes.query> }
  | { kind: "expr"; expr: Ref<typeof expr.nodes.expr> };
```

The public API can still accept `Entity` witnesses, but canonical IR should store refs.

This matters for:

```txt id="5lgx5d"
serialization
graph diffing
artifact provenance
AI edits
cross-module references
pass indexing
```

## 5. Query checks should become diagnostic-producing passes

`checkQueries` and `checkQueryRuntimes` are useful, but they should become dialect passes. The current checks validate aggregate operation kind, numeric aggregate fields, projected field existence, join predicate shape, wrong-entity field refs, join condition refs, and runtime effect support.

That maps very cleanly to:

```txt id="nbs3s6"
query.verify.projectionFieldsExist
query.verify.aggregateOperationCompatibility
query.verify.joinPredicateReferencesJoinedSource
query.verify.predicateScope
query.verify.runtimeEffectsSupported
query.derive.readEdges
query.derive.requirements
query.legalize.targetStorePlan
```

The diagnostics should also become definitions with remediation:

```ts id="be8psr"
diagnostic.define("query.projection.field_not_in_source", {
  severity: "error",
  message:
    "Projected field does not belong to the query source or joined sources.",
  remediation: {
    kind: "replace_field",
    source: "valid_fields_from_query_scope",
  },
});
```

This is better than ad hoc string diagnostics.

## 6. `kernel(2).ts`: this is the closest to the new architecture

The relation adapter is very aligned with the revised kernel. It turns a legacy `Relation` into a `DOMAIN_RELATION` edge with four endpoints: `from_entity`, `to_entity`, `from_field`, and `to_field`. It also emits relation kind and integrity mode as typed traits and derives endpoint cardinality from relation kind.

That is exactly the right migration style:

```txt id="cd1oj6"
legacy semantic object
  -> pure graph-fragment lowering
  -> typed edge kind
  -> named endpoints
  -> traits for semantic claims
  -> metadata only for passive bridge info
```

I would use this as the pattern for other old modules.

For example:

```txt id="0k60iz"
Action -> ActionNode + ActionWrites + ActionAppliesOperation + GuardedBy
Query -> QueryNode + QueryReads + QueryReturnsType + QueryHasPredicate
StateResource -> StateResourceNode + PlacedIn + HasKeyFamily + HydratesThrough
UI Behavior -> BehaviorNode + AttachesToSlot + RunsAction + HasEffect
```

## 7. Improve relation traits into dialect-owned symbols

The relation adapter defines relation traits locally because they are stdlib-domain claims, not hard kernel claims. That is conceptually correct.

I would just move them into the domain dialect definition rather than the adapter file:

```ts id="0rzr4r"
export const domain = defineDialect("domain")((d) => {
  const relation = d.edgeKind("relation", { ... });

  const traits = {
    oneToOne: d.trait("relation.oneToOne", { target: ["edge"] }),
    oneToMany: d.trait("relation.oneToMany", { target: ["edge"] }),
    databaseForeignKey: d.trait("relation.integrity.databaseForeignKey", {
      target: ["edge"],
    }),
  };

  return { edges: { relation }, traits };
});
```

Then the adapter imports:

```ts id="35b0zz"
domain.traits.relation.oneToMany
domain.edges.relation
```

not locally defined symbols.

This avoids duplicate symbols and makes plugin/dialect registration clean.

## 8. Relation cardinality should maybe be endpoint payload, not only traits

The adapter uses traits for relation kind and endpoint cardinality on endpoint records. That is a good hybrid. The endpoint cardinality is more structural than semantic; keeping it on endpoints is useful for traversal/planning. The relation kind trait is useful for querying and diagnostics.

I would standardize:

```txt id="qgbcep"
endpoint payload:
  cardinality at this endpoint

edge traits:
  relation kind
  integrity mode
  required/optional
  cascade/restrict semantics

edge metadata:
  label, docs, bridge ref only
```

That lets storage, UI, and sync passes ask different questions efficiently.

## 9. `state.ts`: strong concept, wrong final storage

`StateResource` is a good concept. It models non-query app state with value type, optional key family, storage, default value, read/write access, reactivity, sensitivity, lifetime, and hydration. It also has useful checks for unsafe sensitive persistence, server-only state in client-readable storage, and query-cache state without key family.

This should survive almost exactly, but not as `ctx.state_resources`.

It should become part of the `resource/state` dialect:

```txt id="81oak3"
Node(StateResource)
Edge(StateHasValueType)
Edge(StateHasKeyFamily)
Edge(StatePlacedIn)
Edge(StateReadableBy)
Edge(StateWritableBy)
Edge(StateHydratesThrough)
Trait(StateReactive)
Trait(StateHydratable)
Trait(StateSensitive)
Trait(StateServerOnly)
```

The current checker becomes passes:

```txt id="mlol9a"
state.verify.sensitivePlacementSafe
state.verify.serverOnlyNotClientReadable
state.verify.queryCacheHasKeyFamily
state.derive.hydrationPlan
state.derive.reactivityEdges
```

## 10. State access should be placement edges, not enum fields

`readable_by` and `writable_by` are currently `"server" | "client" | "shared"`.

That is fine as an initial facade, but the graph should express this through placement/boundary facts:

```ts id="jvvhaj"
state.resource("CurrentUserDraft", {
  value: UserDraft,
  storage: storage.client.localStorage(),
  readableBy: [ClientBoundary],
  writableBy: [ClientBoundary],
});
```

Graph:

```txt id="jsc2z4"
StateResource --placedIn--> ClientLocalStorage
StateResource --readableBy--> ClientBoundary
StateResource --writableBy--> ClientBoundary
StateResource --hasKeyFamily--> CurrentUserDraftKey
```

This is more general than server/client/shared and works for:

```txt id="541v3b"
worker
edge runtime
database
queue
session storage
tenant scope
request scope
test runtime
```

## 11. State resource should unify with UI and JSON-render

This file is directly relevant to the UI design. The UI doc argued that typed `StateResource` nodes are the bridge between AF-UI/Effect-style state and JSON-Render pointer state: React can lower it to an atom/signal, while JSON-Render can lower the same typed binding to a JSON pointer.

So `state.ts` should be treated as a core piece of `dialect.resource`, not a side module.

Ideal usage:

```ts id="t02fd7"
const CurrentIncidentDraft = gen.resource.state("CurrentIncidentDraft", {
  type: t.object({
    title: t.string,
    severity: Severity,
  }),

  key: IncidentDraftKey,
  storage: storage.client.sessionStorage(),
  readableBy: ClientBoundary,
  writableBy: ClientBoundary,
  hydrate: false,
});
```

UI binding:

```ts id="fnc0ne"
ui.input("Title").bind(CurrentIncidentDraft.fields.title);
```

JSON-Render lowering:

```json id="bsjyp5"
{ "$bindState": "/CurrentIncidentDraft/title" }
```

React lowering:

```ts id="t59pvr"
const title = useAtom(CurrentIncidentDraftAtom).title;
```

Same graph fact, different targets.

## Bottom line

These files are not throwaway.

They are three important seeds:

```txt id="g8bzox"
query.ts
  seed for callable/query dialect + query planning dialect

kernel(2).ts
  seed for how to migrate legacy semantic objects into graph IR

state.ts
  seed for resource/state dialect and UI/JSON-render state binding
```

The relation adapter is closest to the target architecture. The state resource model is conceptually right but needs to move from `ctx.state_resources` into graph nodes/edges. The query model has the richest semantics, but it needs the most refactoring: logical query, query expression, query reads, query planning, and target lowering should be separate graph stages rather than one large record.


These three files are important because they show the **migration layer** starting to exist in code.

My read:

```txt
obligations.ts
  very good concept; should become an obligation/artifact/test dialect

kernel(3).ts
  good policy → graph adapter, but should become more typed and dialect-owned

lifecycle.ts
  the main transitional bottleneck; it is half new pass pipeline, half old GenContext runner
```

## 1. `obligations.ts`: this should survive, but as graph IR

This file is conceptually excellent. It introduces a “semantic obligation graph” for tests, docs, and devtools. It derives obligations like policy tests, access matrix docs, mutation invalidation tests, provider mock tests, hydration safety tests, form validation tests, enum exhaustiveness tests, reaction delivery tests, cron idempotency tests, workflow error-handler tests, and boundary auth tests.

That is exactly the right idea.

The insight is:

```txt
Some graph facts imply generated-output responsibilities.
```

Examples:

```txt
Policy exists
  -> generate policy tests
  -> generate access matrix docs

Action invalidates keys
  -> generate mutation invalidation tests

Hydrated state resource exists
  -> generate hydration safety tests

At-least-once reaction/dispatch exists
  -> generate delivery/idempotency tests

Workflow has error handlers
  -> generate workflow error tests
```

This is broader than diagnostics. Diagnostics say “something is wrong or notable.” Obligations say “this semantic fact should produce a test/doc/devtool artifact.”

I would keep the concept, but not as a separate `ObligationGraph` object built by scanning `ctx.*` arrays.

### Revised model

Make obligations graph-native:

```txt
Node(Obligation)
  kind: policy_test | access_matrix_doc | mutation_invalidation_test | ...

Edges:
  ObligationSource -> source node/edge
  ObligationAffectsArtifact -> artifact kind/path/template
  ObligationConsumedBy -> target/test/docs/devtools pass
  ObligationSatisfiedBy -> generated artifact
  ObligationBlockedBy -> diagnostic/finding

Traits:
  Required
  Recommended
  Optional
  TestObligation
  DocumentationObligation
  DevtoolsObligation
```

Then a pass derives obligations:

```txt
derive.obligations.policyTests
derive.obligations.reactivityTests
derive.obligations.hydrationTests
derive.obligations.dispatchDeliveryTests
derive.obligations.workflowTests
```

And another pass verifies them:

```txt
verify.obligations.requiredSatisfied
verify.obligations.hasConsumer
```

### Better API shape

```ts
const PolicyTestObligation = obligations.kind("policy_test", {
  priority: "required",
  targetArtifacts: [targets.tests.artifacts.policyMatrix],
});

const derivePolicyTestObligations = pass.define("derive.policyTestObligations", {
  reads: {
    nodes: [auth.nodes.policy],
    edges: [auth.edges.policyTargetsEntity, auth.edges.policyUsesRule],
  },
  writes: {
    nodes: [obligations.nodes.obligation],
    edges: [
      obligations.edges.source,
      obligations.edges.affectsArtifact,
    ],
  },
  run(ctx) {
    for (const policy of ctx.graph.view(auth.views.policies).all()) {
      ctx.add(
        obligations.obligation("policy-test", {
          source: policy,
          kind: PolicyTestObligation,
          priority: "required",
          artifact: targets.tests.artifacts.policyTest,
        }),
      );
    }
  },
});
```

The current file hardcodes paths like `tests/policy/${policy.name}.test.ts`. That is okay as a first pass, but in the final design, artifact paths should be owned by target artifact kinds or path templates.

### What I would change

```txt
Keep:
  obligation kinds
  priority
  source
  affected artifacts
  consumers
  required/unhandled diagnostics

Change:
  source_kind/source_name -> source Ref
  affected_artifacts strings -> ArtifactKind refs / artifact path templates
  consumers strings -> target/pass refs
  deriveObligationGraph(ctx) -> derive obligation graph pass
  checkObligations(ctx) -> verify obligation satisfaction pass
  ctx array scans -> graph views
```

This should become a real dialect:

```txt
dialect.obligation
  nodes:
    Obligation
    ObligationKind

  edges:
    ObligationSource
    ObligationAffectsArtifact
    ObligationConsumedBy
    ObligationSatisfiedBy

  traits:
    Required
    Recommended
    Optional
```

I would also connect it to the tests/docs targets:

```txt
Obligation -> tests target
Obligation -> docs target
Obligation -> devtools target
```

That makes test generation part of the semantic graph, not an afterthought.

## 2. `kernel(3).ts`: policy adapter is directionally right

This file adapts a legacy `Policy` object into kernel graph IR: a `Policy` node plus a `TARGETS` edge to the target entity and a `POLICY_USES_RULE` edge to the predicate rule when present. It intentionally avoids mutating `ctx.graph`; registration happens through a dual-write binder.

That is the right migration pattern.

Current shape:

```txt
Policy
  -> Node(POLICY)

Policy targets entity
  -> Edge(TARGETS)

Policy uses predicate
  -> Edge(POLICY_USES_RULE)
```

That should survive.

### What is good

The file does three good things:

```txt
1. Treats policy as a graph node.
2. Treats policy relationships as graph edges.
3. Keeps conversion pure instead of mutating ctx.graph directly.
```

That is exactly how legacy adapters should work.

### What I would improve

The file manually converts dialect edge kind definitions into loose `EdgeKind` / `EndpointRole` objects using helper functions like `edgeKindFromDef` and `endpointRoleFromDef`.

That is a bridge smell. In the final API, use the typed edge kind witness directly:

```ts
defineEdgeFromKind(POLICY_TARGETS_ENTITY_EDGE_KIND, id, {
  policy: policyRef,
  entity: policy.target_entity.ref,
});
```

Not:

```ts
defineEdge(policyTargetsEntityKind, id, [
  { role: policyTargetsPolicyRole, target: policyRef },
  { role: policyTargetsEntityRole, target: entityRef },
]);
```

The typed version preserves endpoint names, endpoint target constraints, direction, and metadata shape.

### Policy needs more edges

The current adapter only emits:

```txt
Policy targets entity
Policy uses rule
```

But the target design needs more policy facts:

```txt
PolicyEnforcesOperation
PolicyAppliesToAction
PolicyAppliesToQuery
PolicyRequiresClaim
PolicyExposesClientHint
PolicyRequiresServerEnforcement
PolicyLowersToRls
PolicyHasAudience
PolicyHasDecisionMode
```

For example:

```txt
Policy IncidentPolicy
  targets Incident
  uses canViewIncident
  enforces read
  enforcement server + database
  exposes client hint true
```

Graph shape:

```txt
Node(Policy): IncidentPolicy
Edge(PolicyTargetsEntity): IncidentPolicy -> Incident
Edge(PolicyUsesRule): IncidentPolicy -> canViewIncident
Edge(PolicyEnforcesOperation): IncidentPolicy -> read
Edge(PolicyRequiresServerEnforcement): IncidentPolicy -> ServerBoundary
Edge(PolicyLowersTo): IncidentPolicy -> PostgresRlsPolicy
Edge(PolicyExposesClientHint): IncidentPolicy -> UIHint
```

### Revised policy adapter target

```ts
export const policyToGraphFragment = (policy: Policy): GraphFragment =>
  fragment(
    node(auth.nodes.policy, policy.id, {
      name: policy.name,
    }),

    edge(auth.edges.policyTargetsEntity, {
      policy: ref(policy),
      entity: ref(policy.target_entity),
    }),

    policy.predicate &&
      edge(auth.edges.policyUsesRule, {
        policy: ref(policy),
        rule: ref(policy.predicate),
      }),

    ...policy.enforcement.map((boundary) =>
      edge(auth.edges.requiresEnforcementAt, {
        policy: ref(policy),
        boundary: ref(boundary),
      }),
    ),
  );
```

The policy adapter is a good seed, but it should become a typed graph-fragment lowering rather than a loose bridge.

## 3. `lifecycle.ts`: this is the migration bottleneck

This is the biggest and most important file of the three.

It already contains the transition idea: lifecycle checks are routed through `PassRegistry`; built-in checks are registered as passes; target pipelines are represented as lower/emit pass sequences; and there are phase names like `verify-symbols`, `verify-dialects`, `derive`, `canonicalize`, and `legalize`.

But it is still deeply mixed with the old architecture.

It imports a long list of old checkers:

```txt
checkEntities
checkEvents
checkQueries
checkRelations
checkUi
checkCrud
checkReactivity
checkAuthz
checkStateResources
checkObligations
...
```

and the built-in passes still call those old checkers over `ctx.entities`, `ctx.queries`, `ctx.views`, `ctx.forms`, `ctx.reactive_resources`, `ctx.state_resources`, `ctx.workflows`, etc.

So this file is not wrong. It is a **bridge runner**.

But it should not survive as the final lifecycle architecture.

## The right interpretation

`lifecycle.ts` currently means:

```txt
The old checker world has been wrapped in the new pass vocabulary.
```

That is a useful transitional step.

The final architecture should become:

```txt
The checker world disappears.
Dialect-owned passes query the graph directly.
Targets consume legalized target dialect IR.
```

## What is good in `lifecycle.ts`

Several things are valuable and should remain conceptually:

```txt
Pass registry
Pipeline registry
Built-in pass names
Phased execution
Target lower/emit separation
Target input legalization marker
Compatibility helper for legacy checkers
Cross-store planner diagnostics
Fallback diagnostics
Context/storage diagnostics
Target capability diagnostics
```

The file is doing real migration work.

## What should change

### 1. `ctxCheckerToPass` should be temporary only

This adapter wraps old `GenContext` checkers into pass runners by passing `genContext` through `passCtx.options`.

That is fine for migration.

But in the final design, pass runners should look like:

```ts
run(graph, ctx) {
  const queries = ctx.view(query.views.all);
  ...
}
```

not:

```ts
const genCtx = passCtx.options?.genContext as GenContext;
return checkQueries(genCtx.queries);
```

A good rule:

```txt
No new pass may require passCtx.options.genContext.
Only legacy bridge passes may do that.
```

### 2. Built-in passes should move to dialect files

Right now `lifecycle.ts` owns a giant `builtInCheckPasses()` list.

Final structure should be:

```txt
domain.dialect.ts
  registers domain verify/derive passes

query.dialect.ts
  registers query verify/derive/legalize passes

ui.dialect.ts
  registers ui verify/legalize passes

reactivity.dialect.ts
  registers derive invalidation/optimistic passes

dispatch.dialect.ts
  registers delivery/idempotency passes

target/postgres.dialect.ts
  registers postgres legalization/lowering/emission passes
```

Then lifecycle only orchestrates:

```ts
const pipeline = pipelineRegistry.resolve("gen2.check");
runPipeline(graph, pipeline);
```

It should not know every module.

### 3. `standardPhases()` is old-shaped

The current phases are:

```txt
collect_refs
resolve_plugins
check_targets
run_checks
generate
```

But the revised compiler phases should be:

```txt
verify-symbols
verify-dialects
derive
canonicalize
legalize
lower
emit
```

The file already uses those internally, but `standardPhases()` still exposes the older lifecycle vocabulary.

I would replace it with:

```ts
export const standardPassPhases = () => [
  "verify-symbols",
  "verify-dialects",
  "derive",
  "canonicalize",
  "legalize",
  "lower",
  "emit",
] as const;
```

Plugin resolution can be a preflight step, not a semantic phase.

### 4. Target legalization is currently metadata/bridge based

The functions `markTargetInputLegalized` and `isTargetInputLegalized` create target/input nodes and a `TARGET_LEGALIZES_INPUT` edge. That idea is right. But `isTargetInputLegalized` scans all edges and checks `edge.metadata.custom.targetName/inputName/inputKind`.

That is exactly what the new design should avoid.

Better:

```txt
Edge(TargetLegalizesInput)
  target: TargetNodeRef
  input: TargetInputNodeRef
```

Then query:

```ts
graph.edges
  .ofKind(target.edges.legalizesInput)
  .whereEndpoint("target", target.ref)
  .whereEndpoint("input", input.ref)
  .exists();
```

No metadata-driven behavior. No global scan.

### 5. `bridge lower pass` is a stub

`registerBridgeLowerPass` currently registers a lower pass that just returns success.

That is acceptable as a placeholder, but the final architecture needs real lower passes:

```txt
domain.entity -> storage.record
storage.record -> postgres.table
rule.expr -> sql.predicate
action -> server.mutation
ui.view -> react.component_model
deployment.requirement -> alchemy.resource
```

A lower pass that does nothing means emitters are still doing too much.

### 6. Target emit pass still calls old target generators

The bridge emit pass looks up plugin contributions and calls `targetContrib.generate(input)` and codegen hooks directly.

Again: okay for bridge mode.

Final state:

```txt
emit pass consumes legalized target dialect nodes
emit pass emits Artifact nodes/artifacts
```

Not:

```txt
targetContrib.generate(old input record)
```

### 7. Async pass hooks should eventually be supported

The current runner rejects async check/codegen hooks with diagnostics like `lifecycle:async-check-hook-unsupported`.

For a compiler that targets deployment, remote schemas, AI imports, file IO, external OpenAPI, and package inspection, async will eventually matter.

I would keep the synchronous runner for deterministic local passes, but add:

```txt
runPipelineSync
runPipelineAsync
```

Rule:

```txt
Core semantic verification should be sync when possible.
Importers, external target probes, deployment planning, and remote capability discovery may be async.
```

## 4. Cross-store planning in `lifecycle.ts`

The cross-store planner types and checks are valuable. The file validates that cross-store planners have more than one store, distinct stores, projection coverage, explicit composition plans for cross-store reads, and coordinator requirements for cross-store transactional writes.

This should move out of lifecycle and into query/storage/dataflow legalization passes.

Final home:

```txt
dialects/query/passes/legalize-cross-store-read.ts
dialects/storage/passes/legalize-cross-store-write.ts
dialects/dataflow/passes/derive-materialized-composition.ts
```

Graph concepts:

```txt
Node(CrossStorePlan)
Node(StoreQueryPlan)
Edge(QueryHasPlan)
Edge(PlanReadsStore)
Edge(PlanCoversField)
Edge(PlanUsesCompositionStrategy)
```

Diagnostics:

```txt
query.cross_store.missing_plan
query.cross_store.duplicate_store
query.cross_store.missing_projected_field
write.cross_store.transaction_requires_coordinator
```

This is important. Keep it, but move it.

## 5. How these three files fit together

They point to a useful future pipeline:

```txt
Policy adapter
  Policy -> graph facts

Obligation pass
  Policy graph facts -> policy test/doc obligations

Lifecycle pipeline
  derive obligations -> legalize test/doc targets -> emit artifacts
```

Example final graph flow:

```txt
Node(Policy): IncidentPolicy
Edge(PolicyTargetsEntity): IncidentPolicy -> Incident
Edge(PolicyUsesRule): IncidentPolicy -> canViewIncident

derive.obligations.policy
  -> Node(Obligation): policy-test-IncidentPolicy
  -> Edge(ObligationSource): obligation -> IncidentPolicy
  -> Edge(ObligationAffectsArtifact): obligation -> PolicyTestArtifactKind

legalize.tests
  -> Node(TestPlan): IncidentPolicyPolicyTest

emit.tests
  -> Artifact: tests/policy/IncidentPolicy.test.ts
```

That is exactly the kind of graph-native derivation Gen2 should do.

## 7. My verdict

These files are valuable, but they are three different maturity levels:

```txt
obligations.ts
  strong product/compiler idea, needs graph-native dialect form

kernel(3).ts
  good migration adapter, should become typed auth graph fragment lowering

lifecycle.ts
  necessary transition bridge, but must shrink drastically over time
```

The biggest architectural takeaway:

```txt
Obligations should become first-class semantic graph facts.
Policy adapters show the right migration pattern.
Lifecycle should stop owning domain knowledge and become only a pipeline runner.
```

The immediate next refactor I’d do:

```txt
1. Create dialect.obligation.
2. Turn SemanticObligation into ObligationNode.
3. Port checkObligations into derive/verify passes.
4. Replace policy adapter's loose defineEdge calls with defineEdgeFromKind.
5. Split lifecycle.ts into runner + legacy bridge.
```

That would move these files closer to the final Gen2 architecture without throwing away the useful work already there.


These are both **important enough to become first-class dialects** in the new architecture.

My read:

```txt id="k9htq4"
merge.ts
  should become the merge/conflict/law dialect used by sync, offline, retry,
  optimistic updates, CRDT-ish dataflow, and migration planning.

boundary.ts
  should become the placement/boundary/transport dialect used by client-server,
  worker, queue, edge, hydration, offline, and deployment planning.
```

They are not throwaway. They are two of the main reasons Gen2 can be more than codegen.

## 1. `merge.ts`: this is a very strong semantic seed

This file defines typed merge strategies and conflict metadata for semantic types. The key idea is that merge behavior is inspectable metadata attached to semantic types and optionally overridden by fields, telling the compiler how values combine, conflict, fold, or reconcile. It includes operations like `replace`, `last_write_wins`, `max`, `sum_delta`, `set_union`, `add_remove_set`, `field_wise`, `by_id_collection`, `state_machine`, `manual_conflict`, `reject_conflict`, `custom_expr`, and `opaque_runtime`.

That is exactly the kind of semantic information Gen2 needs for:

```txt id="3a4fjo"
offline sync
optimistic updates
rollback
conflict resolution
collaborative editing
event replay
retry safety
parallel execution
state-machine transitions
CRDT-like merges
materialized views
migration repair
```

This should not disappear.

But I would change the framing.

Right now `MergeStrategy` is attached to `SemanticType` as metadata:

```txt id="hjl74i"
field.semantic_type.merge_strategy
```

That is useful, but too buried. In the final architecture, merge strategy should become graph-visible.

# Recommended final shape for merge

## Merge as graph dialect

```txt id="84vvjf"
dialect.merge

  MergeStrategy
  ConflictPolicy
  MergePlan
  FieldMergePlan
  EntityMergePlan
  ReconciliationPlan

  FieldUsesMergeStrategy
  EntityUsesMergePolicy

  ActionWritesMergeField

  Associative

  Idempotent
  Invertible
  Monotonic
```

The public API can still be ergonomic:

```ts id="5v0azj"
const Counter = t.number.merge(merge.sumDelta({
  associative: true,
  commutative: true,
}));

const Tags = t.set(t.string).merge(merge.setUnion({
  idempotent: true,
}));

  merge.stateMachine({
    machine: IncidentStatus,
    conflict: "may_conflict",
  }),

```

But internally this should lower to graph facts:

```txt id="u7m7jq"

Trait(Associative)
Trait(Commutative)
Edge(FieldUsesMergeStrategy): Incident.retryCount -> sum_delta
```

## Merge should connect to laws

`merge.ts` currently stores booleans like `associative`, `commutative`, `idempotent`, `invertible`, and `monotonic` directly on `MergeStrategy`.

That is useful, but in the final design these should be law/trait claims with assurance levels:

```ts id="f2n50x"
merge.setUnion({
  laws: [
    laws.associative({ assurance: "by_construction" }),
    laws.commutative({ assurance: "by_construction" }),
    laws.idempotent({ assurance: "by_construction" }),
  ],
});
```

Why? Because a law is not just metadata. It is a claim that other passes rely on.

Better distinction:

```txt id="qni3m1"
Merge operation:
  set_union

Law claims:
  associative
  commutative
  idempotent

Assurance:
  asserted | derived | tested | proved_by_solver | by_construction
```

This prevents accidental “metadata lies.”

---

## Merge strategy should be attached at multiple levels

Current code derives an entity merge plan by walking `entity.fieldList` and checking each field’s semantic type for a merge strategy. It emits diagnostics for missing strategies, delta/value type mismatch, and missing conflict policy.

That is right, but the final design needs hierarchy:

```txt id="spkali"
Type-level default merge
Field-level override
Entity-level conflict policy
Action-level conflict behavior
Plan-level retry/replay semantics
Target-level capability support
```

Example:

```ts id="2plyx6"
class Incident extends domain.entity.class("Incident", {
  merge: merge.entityPolicy({
    default: merge.fieldWise(),
    conflict: merge.manualResolution({
      surface: IncidentConflictDialog,
    }),
  }),

  fields: {
    status: field(IncidentStatus.type).merge(
      merge.stateMachine({ machine: IncidentStatus }),
    ),

    tags: field(t.set(t.string)).merge(
      merge.setUnion(),
    ),

    updatedAt: field(t.datetime).merge(
      merge.lastWriteWins({ clock: "server" }),
    ),
  },
}) {}
```

Graph facts:

```txt id="64pdz5"
EntityUsesMergePolicy: Incident -> IncidentMergePolicy
FieldUsesMergeStrategy: Incident.status -> state_machine
FieldUsesMergeStrategy: Incident.tags -> set_union
FieldUsesMergeStrategy: Incident.updatedAt -> last_write_wins
ConflictPolicyUsesSurface: IncidentMergePolicy -> IncidentConflictDialog
```

---

## Merge checks should become passes

The current file has `deriveEntityMergePlan`, `checkActionMergeSemantics`, and `checkPlanMergeSemantics`. These inspect entity fields, action body operations, retry plans, and parallel plans.

In the new architecture:

```txt id="mzsatv"
derive.merge.entityPlans
verify.merge.deltaTypeCompatibility
verify.merge.actionConflictSafety
verify.merge.retryRequiresIdempotency
verify.merge.parallelWritesCommutative
legalize.merge.targetCapability
```

Examples of diagnostics:

```txt id="kjwrn8"
merge.field.strategy_missing
merge.delta_type_mismatch
merge.entity.conflict_policy_missing
merge.action.reject_conflict_write
merge.action.manual_conflict_requires_handler
merge.retry.requires_idempotency
merge.parallel.requires_commutative_writes
merge.opaque_runtime_requires_broad_invalidation
```

This directly supports the sync story.

## Important merge design consideration

Do **not** make merge a subfeature of sync only.

Merge is used by:

```txt id="aflawr"
sync
offline commands
optimistic rollback
parallel workflows
retry plans
event replay
queue deduplication
state resources
CRDT-style collaboration
database migrations
field-level conflict UI
```

So it should probably be its own dialect:

```txt id="nbzjen"
dialect.merge
```

not merely `reactivity.merge`.

# 2. `boundary.ts`: this is also a core standard dialect

It models runtime boundaries like browser, server, database, worker, edge, native, queue, and external service; transport kinds like HTTP, RPC, WebSocket, server action, queue, offline command, and hydration; plus `TransportPlan` and `BoundaryCallPlan`.

This is very aligned with the “boundary anchor” idea.

But I would refine it.

The file currently treats a boundary call plan as a single object:

```txt id="xh1ef4"
BoundaryCallPlan

  client_boundary
  server_boundary
  transport
  input_contract
  output_contract
  error_contract
  auth_requirements
  provider_requirements
  invalidation_payloads
  optimistic_plan
  offline_plan
```

That is semantically good, but in final Gen2 it should be graph-native.

# 4. Boundary and merge should connect

These two files are related.

Boundary transport affects merge/conflict requirements:

```txt id="bggm4i"
offline_command transport
  requires merge strategy or conflict policy

queue transport
  requires idempotency and serialization

websocket stream
  requires ordering/replay/backpressure semantics

parallel worker execution
  requires commutative/idempotent merges

edge runtime
  restricts effects and storage access
```

So the final graph should let passes combine them:

```txt id="q7qrjp"
BoundaryCallPlan uses offline_command
Action writes Incident.status
Incident.status uses merge.stateMachine
Action has optimistic plan
State machine transition is valid
=> offline replay is legal

BoundaryCallPlan uses queue
Action writes field with manual_conflict
Action lacks conflict handler
=> diagnostic
```

Example final diagnostic:

```txt id="s2ezgm"
offline.command.requires_merge_policy

acknowledgeIncident is allowed offline, but it writes Incident.status.
Incident.status has state_machine merge, but no conflict policy for concurrent
open -> acknowledged and open -> cancelled transitions.
```

This is exactly why merge and boundary should be graph-visible dialects.

# 8. Most important design point

Merge and boundary should be treated as **compiler reasoning dialects**, not just metadata.

They answer questions like:

```txt id="29wbev"
Can this action be retried?
Can this action run offline?
Can this write be merged after concurrent edits?
Can this call cross from browser to server?
Can this queue message be serialized?
Can this effect run on edge?
Can this optimistic patch be safely rolled back?
Can this target legally emit this transport?
```

That is the heart of Gen2.

# My verdict

These are strong, useful modules.

```txt id="isqfan"
merge.ts
  should become dialect.merge, tied to laws, sync, retry, offline,
  optimistic updates, and conflict resolution.

boundary.ts
  should become dialect.boundary, tied to placement, transports,
  serialization, auth, hydration, offline, queues, workers, and deployment.
```

They should not remain as isolated check helpers over `GenContext`.

The target shape is:

```txt id="98wo3c"

Diagnostics explain unsafe retries, unsafe transports, missing serializers,
```

In the ultimate API, these two dialects are what make the compiler capable of reasoning about **real distributed application behavior**, not just schemas and components.

## 1. `forms.ts`: keep the idea, make it a UI form dialect/recipe

This file is good because it says forms are not an independent model. They derive from action function contracts and produce UI IR. It maps semantic field types to default widgets, derives validation rules from field nullability/traits, checks platform widget capability, and builds forms from action input fields.

That is the right product idea:

```txt id="zc1cvi"
Action contract
  -> form fields
  -> widgets
  -> validation
  -> slots
  -> error mapping
  -> UI IR
  -> target component / JSON-render form / tests
```

But in the final design, `Form` should not be a parallel subsystem. It should be a **UI dialect graph fragment**.

### Final shape

```txt id="k9ov35"
Node(Form)
Node(FormField)
Node(Widget)
Node(ValidationRule)
Node(FormErrorMapping)

Edges:
  FormSubmitsAction
  FormHasField
  FormFieldBindsInput
  FormFieldUsesWidget
  FormFieldHasValidation
  FormMapsError
  WidgetRequiresCapability
  FormHasSlot
```

The public API can still stay high-level:

```ts id="nsg47q"

  action: declareIncident,

  fields: {
    title: {
      widget: ui.widget.textInput(),
      label: "Incident title",
    },

    severity: {
      widget: ui.widget.select({
        options: Severity,
      }),
    },

    assignedTeamId: {
      widget: ui.widget.relationSelect({
        relation: Team,
      }),
      visibleWhen: canAssignIncident,
    },
  },

  errors: {
    "incident.title.required": "title",
    "incident.sev1.requires_team": "assignedTeamId",
  },
});
```

Internally:

```txt id="878hde"

Field title binds declareIncident.input.title
Field title uses TextInput widget
TextInput requires TextInput capability
Field severity uses Select widget
Select options come from Severity enum
Error incident.title.required maps to title field
```

### What I would change

The current `defaultWidget` function eagerly falls back to `textInput` when a platform lacks support. That is useful ergonomically, but the final compiler should separate:

```txt id="tiad54"
authoring derivation
  choose semantic widget

legalization
  choose target-supported widget or emit diagnostic

lowering
  emit concrete React/JSON-render/native UI
```

So:

```txt id="rul1l5"

  belongs in ui.form derivation

platformSupportsWidget(...)
  belongs in ui target legalization

fallback to textInput
  should be a legalization decision with a diagnostic/explanation
```

This way the graph still knows the intended control, not just the fallback.

## 2. `reactivity.ts`: this is essential, but it should stop being a parallel graph

This file contains a lot of the right semantic ingredients: `KeyFamily`, `ReactiveKey`, key patterns, resource states, refresh plans, reactive resources, pull/infinite/stream resources, derived resources, scoped resources, tracking scopes, mutations, optimistic plans, resource composition, and a derived reactive graph with edges like `reads_key`, `writes_entity`, `invalidates_key`, `wraps_query`, `wraps_action`, `form_submits`, `reads_state`, and `hydrates_state`.

The problem is not the concepts. The problem is that `ReactiveGraph` is another graph.

Final stance:

```txt id="d1ifvp"
Keep manual keys.
Keep resources.
Keep mutations.
Keep optimistic plans.
Keep tracking scopes.
Keep single-flight/resource-chain/resource-all concepts.

But move them into the kernel graph as node/edge kinds.
```

## 3. `rule-derived.ts`: this is one of the strongest files

This file is very aligned with the new design. It explicitly says rule-derived reactivity should derive invalidation from `WRITES` / `READS` edge overlap rather than ad hoc AST walking. It walks policies, rules, queries, action writes, rule reads, derives invalidation plans, computes precision levels, and derives IVM plans based on rule monotonicity.

This is exactly the compiler advantage.

The core idea is:

```txt id="vhhqlh"
Action writes field
Rule reads field
Policy/query depends on rule
Query has key family
Therefore action invalidates key family
```

That is the right architecture.

### What should change

The implementation still uses bridge metadata and global graph scans. It has helpers like `getBridgeRule`, `getBridgeQuery`, `getBridgeAction`, scans `graph.edges.values()`, and manually matches endpoint role IDs.

That is fine during migration, but the final version should use graph views and indexes:

```ts id="9eq7si"
const rw = ctx.view(reactivity.views.readWriteIndex);
const policies = ctx.view(auth.views.policyDependencyIndex);
const keys = ctx.view(reactivity.views.queryKeyIndex);

for (const action of rw.actionsWritingFields()) {
  const affectedRules = rw.rulesReadingAny(action.writtenFields);
  const affectedQueries = policies.queriesGuardedByRules(affectedRules);
  const invalidatedKeys = keys.keysForQueries(affectedQueries);

  ctx.add(
    reactivity.derivedInvalidationPlan({
      action,
      rules: affectedRules,
      keys: invalidatedKeys,
      precision: derivePrecision(action, affectedRules),
    }),
  );
}
```

### Final outputs should be graph facts

Currently it returns records like:

```txt id="q13bjk"
DerivedInvalidationPlan
IvmMaintenancePlan
RulePatchPlan
```

Those should become graph nodes:

```txt id="l8gwfp"
Node(DerivedInvalidationPlan)
Node(IvmMaintenancePlan)
Node(RulePatchPlan)

Edges:
  PlanForAction
  PlanAffectedRule
  PlanInvalidatesKey
  PlanMaintainsRelation
  PlanUsesPatch
  PlanHasPrecision
```

The checker can still emit diagnostics like broad invalidation selected, non-monotonic IVM unsupported, cross-store dependency, or time-dependent rule, but the plans themselves should be visible graph artifacts. The file already produces warnings for broad invalidation and info diagnostics when mutations write fields/entities read by rules.

## 4. `kernel(4).ts`: KeyFamily adapter is useful, but bridge-only

This file converts a legacy `KeyFamily` object into a `KEY_FAMILY` kernel node, stores the original family in metadata, and provides graph extraction helpers.

That is a useful migration bridge.

But final KeyFamily should not live in metadata. It should be an actual graph node with edges:

```txt id="szwhhi"
Node(KeyFamily): openIncidents
Edge(KeyFamilyHasInputType): openIncidents -> OpenIncidentsKeyPayload
Trait(CollectionKey)
Trait(PropagatesToChildren)
```

Current bridge:

```txt id="s1wdmd"

metadata.custom._bridgeKeyFamily = family
```

Final:

```txt id="e1m823"
Node(KeyFamily)
Edge(HasInputType)
Edge(HasInvalidationSemantics)
Trait(EntityKey | CollectionKey | FieldKey | RelationKey | ViewKey)
```

Also, `findKeyFamilyByNameOnGraph` should eventually go away. Name lookup is okay for UI/devtools, but compiler logic should use refs/witnesses.

## 5. `kernel(5).ts`: Reaction adapter should become dispatch

This file bridges a `Reaction` into a `REACTION` node and stores the original reaction as bridge metadata so downstream passes can recover it without `ctx.reactions`.

Again: useful migration helper, not final design.

The bigger design call is that **Reaction should not remain a special standalone subsystem**.

From the newer model:

```txt id="wwsenu"
Reaction = dispatch triggered by a rule becoming true
Subscription = dispatch triggered by an event
Reducer = event-triggered state/resource update
Dispatch = generic trigger -> select/project -> handler -> delivery plan
```

So final reaction lowering:

```txt id="68d8hf"
Node(Dispatch): notifyWhenIncidentSev1
Edge(DispatchTriggeredByRule): dispatch -> isSev1Incident
Edge(DispatchRunsAction): dispatch -> enqueueNotification
Edge(DispatchUsesDelivery): dispatch -> outbox/queue
Edge(DispatchUsesIdempotency): dispatch -> eventId/inputHash
```

If you keep `Reaction` as a public convenience API, it should lower to a dispatch graph fragment:

```ts id="92youb"
const notifyOnSev1 = app.reaction("notifyOnSev1", {
  when: incidentBecomesSev1,
  run: enqueueIncidentNotification,
  delivery: delivery.outbox(),
  idempotency: idempotency.ruleMatchId(),
});
```

Internally:

```txt id="l8wz55"
Reaction builder -> Dispatch node + trigger edges
```

## 6. How these five pieces fit together

These files describe a complete loop:

```txt id="1zc5ei"
forms.ts
  UI submits actions and binds validation/errors.

reactivity.ts
  resources wrap queries; mutations wrap actions; keys track stable identity.

rule-derived.ts
  compiler derives invalidation from action writes and rule/query reads.

KeyFamily adapter
  moves key identities into graph.

Reaction adapter
  moves old reactions toward dispatch graph facts.
```

The important relationship:

```txt id="i5xc02"
Form submits Action
Action writes Field
Rule reads Field
Query guarded by Rule has KeyFamily
Resource wraps Query
Mutation wraps Action
Mutation invalidates Resource/Key
UI reads Resource
```

That chain is the heart of the app compiler.

Graph version:

```txt id="xty9zl"
Form --submits--> Action
Action --writes--> Field
Rule --reads--> Field
Policy --usesRule--> Rule
Query --guardedBy--> Policy
Query --hasKey--> KeyFamily
Resource --wrapsQuery--> Query
Mutation --wrapsAction--> Action
Mutation --invalidatesKey--> KeyFamily
View --readsResource--> Resource
```

That is exactly what should power React hooks, JSON-render forms, tests, docs, devtools, optimistic updates, and cache invalidation.

## 5. `kernel(7).ts`: this is the best of this batch

This file is the graph-native requirement/provider adapter. It converts requirements and providers into kernel nodes, emits `SATISFIES`, `DEPENDS_ON_PROVIDER`, `PLACED_IN`, and `SOURCED_FROM` edges, adapts storage locations into nodes, and derives a graph-native requirement satisfaction plan from the kernel graph.

This is very close to the target architecture.

The strongest part is that it no longer only checks `ctx.providers`; it reconstructs requirements/providers/bindings from graph nodes and edges, then diagnoses missing providers, ambiguous providers, unsafe placement, lifetime escape, global cache misuse, regulated client exposure, and provider cycles.

That is exactly the migration pattern you want.

Current graph flow:

```txt id="ys0qne"
RequirementRef -> Node(REQUIREMENT)
Provider -> Node(PROVIDER)
Provider satisfies target -> Edge(SATISFIES)
Provider depends on provider -> Edge(DEPENDS_ON_PROVIDER)
Provider placement/storage -> Edge(PLACED_IN)
Provider source storage -> Edge(SOURCED_FROM)
StorageLocation -> Node(STORAGE_LOCATION)
```

This should become the final provider/requirement dialect, with less bridge metadata.

## 1. `entity-to-semantic.ts`: useful, but it exposes a design smell

The helper converts an `Entity` into a struct-shaped `SemanticType`, mainly so expression builders and function DSL boundaries can accept `SemanticType | Entity`. It detects entities using `"fieldList" in value`, then synthesizes a struct type with the entity name and document storage representation.

That is practical, but in the ultimate design I would not let `Entity` silently become an anonymous-ish `SemanticType` at runtime.

The problem:

```ts
entityToSemanticType(User)
```

looks convenient, but semantically there are at least three different things:

```txt
Entity node:
  User as a domain object/table/resource

Entity value type:
  the shape of a User record

Projection type:
  a client-safe subset or target-specific view of User
```

So I’d replace the helper with explicit witness fields:

```ts
User.entity       // Entity witness / node ref
User.type         // full semantic value type
User.inputType    // create/update input type, if derived
User.ref          // graph ref
User.projection(...) // explicit safe projection
```

Then public APIs can accept entity witnesses ergonomically:

```ts
action.output(User)
```

but internally normalize through:

```ts
toValueType(User) === User.type
```

not synthesize a fresh struct every time.

### Recommendation

Keep `entityToSemanticType` temporarily as compatibility glue, but rename its final version to something explicit:

```ts
typeOf(User)
valueTypeOf(User)
toSemanticValueType(User)
```

And ensure it returns a **stable graph type ref**, not a synthetic object with no serializer/deserializer and empty traits.

## 2. `kernel(8).ts`: entity/field adapter is the right bridge pattern

This file converts legacy `Entity` / `Field` objects into graph IR: one `ENTITY` node per entity, one `FIELD` node per field, `ENTITY_OWNS_FIELD` edges, and `FIELD_HAS_TYPE` edges pointing to synthesized type refs. It also pays attention to stable IDs where available and falls back to name-based IDs.

This is exactly the migration pattern you want:

```txt
legacy object
  -> graph nodes
  -> graph edges
  -> stable IDs
  -> no ctx mutation
```

But it still has two bridge smells.

First, it manually converts edge kind definitions into loose `EdgeKind` and endpoint-role records.  Final code should use typed `defineEdgeFromKind(...)` directly:

```ts
defineEdgeFromKind(ENTITY_OWNS_FIELD_EDGE_KIND, id, {
  entity: entity.ref,
  field: field.ref,
});
```

not:

```ts
defineEdge(edgeKind, id, [
  { role, target },
]);
```

Second, the field type edge points to a synthesized `KernelRef<"type">` that is not yet registered as a real type node.  That is fine as a bridge phase, but the final graph should contain first-class type nodes.

Final shape:

```txt
Node(Entity): User
Node(Field): User.email
Node(Type): Email
Edge(EntityOwnsField): User -> User.email
Edge(FieldHasType): User.email -> Email
Edge(TypeHasCodec): Email -> EmailCodec
Trait(Unique): User.email
Trait(ClientReadable): User.email
```

### Recommendation

Promote this adapter pattern, but change the destination:

```txt
field.semantic_type.name as ref
  -> registered Type node / Type witness

manual endpoint roles
  -> defineEdgeFromKind

_bridgeRef metadata
  -> only temporary provenance, not semantic behavior
```

Also, stable IDs should become mandatory sooner than later. Name fallback is okay for prototypes, but versioning and migration need stable IDs.

## 3. `kernel(9).ts`: context is basically requirement/provider now

This file adapts `ContextDef`, `ContextProvision`, and `ContextRequirement` into graph IR. It creates context nodes, provision edges from context to storage location, requirement edges, and checks duplicate contexts, unsafe storage locations, and missing required context provisions directly from the graph.

This is good work. It is more graph-native than many older modules.

But architecturally, I would avoid keeping `context` as a separate conceptual system from requirements/providers.

A context is really:

```txt
Requirement:
  something a callable/view/pass needs

Provider:
  something that satisfies that requirement

Provider source:
  request header, cookie, env var, runtime, state resource, reactive resource

Placement/storage:
  where the provided value lives
```

So `ContextDef` should likely lower into the same provider/requirement graph as `RequirementRef`.

For example:

```ts
const AuthSession = app.context("AuthSession", ...)
```

and:

```ts
const AuthSession = app.requirement("AuthSession", ...)
```

should not produce unrelated graph models.

### Final unification

```txt
Node(Requirement): AuthSession
Node(Provider): AuthSessionProvider
Node(ProviderSource): Cookie(opsdesk_session)
Node(StorageLocation): SessionCookieStorage

Edge(ProviderSatisfies): AuthSessionProvider -> AuthSession
Edge(ProviderSourcedFrom): AuthSessionProvider -> CookieSource
Edge(ProviderPlacedIn): AuthSessionProvider -> RequestStorage
Edge(ConsumerRequires): resolveIncident -> AuthSession
```

`Context` can remain a public convenience name, but internally it should be a requirement/provider pattern.

### Recommendation

Keep `kernel(9).ts` as a bridge adapter, but eventually fold it into:

```txt
dialects/core/requirement
dialects/core/provider
dialects/core/placement
```

Also move behavior-relevant facts out of metadata:

```txt
semantic_type
optional
storage safety
request scoped
```

Those should be graph facts, traits, or edges. Metadata can keep descriptions and source locations.

## 4. `versioning-plan.md`: this should become a major standard dialect

This plan is very important. It says the current system already has stable identity, structural diffing, migration artifacts, migration-step traits, storage versioning, and optimistic-locking fields, but lacks a migration runner, schema versioning on the graph, snapshot persistence, and semantic-version derivation.

That is exactly right.

I would not treat this as a side CLI feature. This should become a first-class **evolution dialect**.

```txt
dialect.evolution

Nodes:
  SchemaManifest
  GraphSnapshot
  GraphVersion
  MigrationPlan
  MigrationStep
  MigrationHook
  MigrationState
  BreakingChange
  CompatibilityReport
  BackfillPlan
  RenameHint

Edges:
  VersionFollowsVersion
  SnapshotCapturesGraph
  MigrationFromSnapshot
  MigrationToSnapshot
  MigrationHasStep
  StepAffectsEntity
  StepAffectsField
  StepRequiresBackfill
  StepHasHook
  StepEmitsArtifact
  VersionHasSemverDelta
```

The plan’s milestones map very naturally:

```txt
Schema versioning
  -> SchemaManifest node

Snapshot persistence
  -> GraphSnapshot artifact + snapshot format

Migration plan generation
  -> MigrationPlan / MigrationStep nodes

Target-specific execution
  -> target lower/emit migration artifacts

Semantic version derivation
  -> CompatibilityReport / SemverDelta

User-defined migration hooks
  -> MigrationHook nodes

Validation & integration
  -> diagnostics + obligations + test artifacts
```

### My main change to the plan

The plan asks whether version should live on `GenContext` or a first-class `Schema` node, and recommends starting with `GenContext.version`.

Given everything we’ve designed, I’d now choose the first-class graph node earlier:

```ts
export const Schema = gen.evolution.schema("opsdesk", {
  version: "1.2.0",
  previous: "1.1.0",
});
```

Why? Because:

```txt
multiple schemas may exist
plugins may contribute schema fragments
targets need version metadata
snapshots need provenance
docs/tests need version surfaces
graph diff should target a schema node
AI migrations need explicit graph anchors
```

You can still mirror `schema.version` onto `GenContext` for convenience, but the graph should own it.

## 1. Semantic types and representations

Gen2 separates meaning from physical layout.

```ts
const t = gen.type;
const repr = gen.type.repr;

export const ProductId = t.brand("ProductId", t.uuid());

export const WarehouseId = t.brand("WarehouseId", t.uuid());

export const Sku = t
  .brand("Sku", t.string())
  .withTrait(
    traits.validate("sku_format", {
      expr: ({ value }) =>
        expr.matchRegex(value, /^[A-Z0-9][A-Z0-9_-]{2,63}$/),
      diagnostic: diagnostic.define("sku.invalid_format", {
        severity: "error",
        message: "SKU must be uppercase alphanumeric with optional _ or -.",
      }),
    }),
  );

export const Quantity = t
  .custom<number>({
    name: "Quantity",
    kind: "numeric",
    ts_type_name: "number",
    storage_repr: repr.i32(),
    validate: (value): value is number =>
      typeof value === "number" && Number.isInteger(value),
  })
  .withTrait(traits.numeric)
  .withTrait(traits.orderable);

export const NonNegativeQuantity = t.refinement("NonNegativeQuantity", {
  base: Quantity,
  predicate: ({ value }) => expr.gte(value, 0),
  diagnostic: diagnostic.define("quantity.non_negative", {
    severity: "error",
    message: "Quantity must be non-negative.",
  }),
});

export const PositiveQuantity = t.refinement("PositiveQuantity", {
  base: Quantity,
  predicate: ({ value }) => expr.gt(value, 0),
  diagnostic: diagnostic.define("quantity.positive", {
    severity: "error",
    message: "Quantity must be greater than zero.",
  }),
});

export const Money = t.custom<bigint>({
  name: "Money",
  kind: "money",
  ts_type_name: "bigint",
  storage_repr: repr.i64(),
  aggregate_on: "semantic",
  validate: (value): value is bigint => typeof value === "bigint",
});
```

Gen2 sees these as graph facts:

```txt
Node(Type): ProductId
Node(Type): uuid
Node(Type): Sku
Node(Type): Quantity
Node(Type): NonNegativeQuantity
Node(Type): PositiveQuantity
Node(Representation): fixed_bytes(16)
Node(Representation): text
Node(Representation): i32
Node(Representation): i64

Edge(TypeBrands): ProductId -> uuid
Edge(TypeHasStorageRepresentation): Quantity -> i32
Edge(TypeHasStorageRepresentation): Money -> i64
Edge(TypeRefines): PositiveQuantity -> Quantity
Edge(TypeHasPredicate): PositiveQuantity -> value > 0
Trait(Numeric): Quantity
Trait(Orderable): Quantity
```

## 3. Derived field: available inventory

`available` is not stored as a normal editable field. It is derived from `onHand - reserved`.

```ts
export const AvailableQuantity = app.derived.field("InventoryItem.available", {
```

## 4. Operations with laws

Operations are not opaque functions. They carry laws the compiler can use for optimization, optimistic updates, retries, and IVM.

```ts
export const AddQuantityDelta = gen.operation.define("AddQuantityDelta", {
  input: t.object({
    current: Quantity,
    delta: Quantity,
  }),

  output: Quantity,

  traits: [
    traits.pure,
    traits.deterministic,
    traits.patchable,
    traits.invertible,
  ],

  laws: [
    laws.associative({
      assurance: assurance.byConstruction(),
    }),

    laws.commutative({
      assurance: assurance.byConstruction(),
    }),

    laws.hasIdentity({
      value: 0,
      assurance: assurance.byConstruction(),
    }),

    laws.hasInverse({
      inverse: ({ delta }) => expr.mul(delta, -1),
      assurance: assurance.byConstruction(),
    }),
  ],

  implementations: {
    typescript: op.ts("(current, delta) => current + delta"),
    postgres: op.sql("($1 + $2)"),
  },

  protocols: {
    patch: gen.operation.patchProtocol({
      producePatch: ({ input }) =>
        gen.patch.increment(input.current, input.delta),

      invertPatch: ({ input }) =>
        gen.patch.increment(input.current, expr.mul(input.delta, -1)),
    }),
  },
});

export const SubtractQuantity = gen.operation.define("SubtractQuantity", {
  input: t.object({
    left: Quantity,
    right: Quantity,
  }),

  output: Quantity,

  traits: [
    traits.pure,
    traits.deterministic,
    traits.patchable,
  ],

  laws: [
    laws.rollbackSafe({
      assurance: assurance.byConstruction(),
    }),
  ],

  implementations: {
    typescript: op.ts("(left, right) => left - right"),
    postgres: op.sql("($1 - $2)"),
  },
});
```

Because `AddQuantityDelta` is associative, commutative, and invertible, Gen2 can safely use it for:

```txt

rollback patches
parallel updates
retry-safe queue handling
incremental materialized views
property tests
merge conflict resolution
```

```ts
export const hasAvailableInventory = app.rule("hasAvailableInventory")((r) =>
  r
    .vars({
      item: InventoryItem,
      requested: PositiveQuantity,

      expr.gte(
        expr.sub(item.onHand, item.reserved),
        requested,

export const canReserveInventory = app.rule("canReserveInventory")((r) =>
```

## 7. Action that applies operation laws

```ts
export const reserveInventory = app.action("reserveInventory")((a) =>
  a
    .input(ReserveInventoryInput)
    .requires(AuthSession)
    .requires(RequestClock)
    .runsIn(ServerBoundary)

    .reads([
      Product.fields.active,
      InventoryItem.fields.onHand,
      InventoryItem.fields.reserved,
    ])

    .writes([
      InventoryItem.fields.reserved,
      InventoryItem.fields.updatedAt,
    ])

    .guard(canReserveInventory)

    .applies([
      AddQuantityDelta,
    ])

    .laws([
      laws.idempotent({
        key: ({ input }) => input.commandId,
        assurance: assurance.byConstruction(),
      }),
    ])

    .body(({ input, clock }) => {
      const item = InventoryItem.findUnique({
        productId: input.productId,
        warehouseId: input.warehouseId,
      });

      InventoryItem.update(item.id, {
        reserved: AddQuantityDelta.call({
          current: item.reserved,
          delta: input.quantity,
        }),
        updatedAt: clock.now,
      });
    })

    .event("InventoryReserved", ({ input, clock, item }) => ({
      eventId: input.commandId,
      productId: input.productId,
      warehouseId: input.warehouseId,
      quantity: input.quantity,
      inventoryItemId: item.id,
      occurredAt: clock.now,
    }))

    .optimistic({
      derive: true,
      fallback: "invalidate",
    })

    .offline({
      allow: true,
      queue: "InventoryCommandQueue",
    }),
);
```

This produces facts like:

```txt
ActionReads: reserveInventory -> Product.active
ActionReads: reserveInventory -> InventoryItem.onHand
ActionReads: reserveInventory -> InventoryItem.reserved

ActionWrites: reserveInventory -> InventoryItem.reserved
ActionWrites: reserveInventory -> InventoryItem.updatedAt

ActionUsesRule: reserveInventory -> canReserveInventory
ActionAppliesOperation: reserveInventory -> AddQuantityDelta
ActionEmits: reserveInventory -> InventoryReserved

Trait(OfflineReplaySafe): reserveInventory
Law(Idempotent): reserveInventory keyed by commandId
```

The compiler can now derive safe behavior:

```txt
optimistic patch:
  reserved += quantity

rollback patch:
  reserved -= quantity

invalidation:
  inventory detail keys
  product availability keys
  cart availability keys

queue safety:
  commandId idempotency makes at-least-once replay safe

  update available materialized view by -quantity
```

```ts
export const InventoryItemKey = app.key.family("InventoryItemKey", {
```

Define queries/resources:

```ts
export const getInventoryItem = app.query("getInventoryItem")((q) =>
  q
    .input({
      productId: ProductId,
      warehouseId: WarehouseId,
    })
    .from(InventoryItem)
    .where(({ input, row }) =>
      expr.and(
        expr.eq(row.productId, input.productId),
        expr.eq(row.warehouseId, input.warehouseId),
      ),
    )
    .select({
      id: InventoryItem.fields.id,
      productId: InventoryItem.fields.productId,
      warehouseId: InventoryItem.fields.warehouseId,
      onHand: InventoryItem.fields.onHand,
      reserved: InventoryItem.fields.reserved,
      available: AvailableQuantity,
      updatedAt: InventoryItem.fields.updatedAt,
    })
    .key(InventoryItemKey),
);

export const getProductAvailability = app.query("getProductAvailability")((q) =>
  q
    .input({ productId: ProductId })
    .from(InventoryItem)
    .where(({ input, row }) => expr.eq(row.productId, input.productId))
    .select({
      productId: InventoryItem.fields.productId,
      totalOnHand: q.sum(InventoryItem.fields.onHand),
      totalReserved: q.sum(InventoryItem.fields.reserved),
      totalAvailable: q.sum(AvailableQuantity),
    })
    .groupBy([InventoryItem.fields.productId])
    .key(ProductAvailabilityKey),
);

export const InventoryItemResource = app.resource.query("InventoryItemResource", {
  query: getInventoryItem,
  refresh: ["on_mount", "on_invalidate"],
});

export const ProductAvailabilityResource = app.resource.query("ProductAvailabilityResource", {
  query: getProductAvailability,
  refresh: ["on_mount", "on_invalidate"],
});
```

Now add manual reactivity facts:

```ts
export const InventoryReactivity = app.reactivity.graph("InventoryReactivity", {
  keys: [
    InventoryItemKey,
    ProductAvailabilityKey,
    CartAvailabilityKey,
  ],

  resources: [
    InventoryItemResource,
    ProductAvailabilityResource,
  ],

  mutations: [
    reserveInventory,
  ],

  manual: [
    // reserveInventory changes one inventory row.
    app.reactivity.invalidates(reserveInventory, InventoryItemKey.match(({ input }) => ({
      productId: input.productId,
      warehouseId: input.warehouseId,
    })), {
      precision: "exact",
      confidence: "declared",
    }),

    // Product-level availability changes whenever any warehouse inventory changes.
    app.reactivity.invalidates(reserveInventory, ProductAvailabilityKey.match(({ input }) => ({
      productId: input.productId,
    })), {
      precision: "matched",
      confidence: "declared",
    }),

    // Carts may depend on availability through external cart service logic.
    // We cannot statically inspect that service, so we declare a conservative dependency.
    app.reactivity.invalidates(reserveInventory, CartAvailabilityKey.any(), {
      precision: "broad",
      confidence: "declared",
      reason: "External cart service computes purchasability from product availability.",
    }),
  ],
});
```

This produces graph facts:

```txt
Node(KeyFamily): InventoryItemKey
Node(KeyFamily): ProductAvailabilityKey
Node(KeyFamily): CartAvailabilityKey

Edge(ResourceWrapsQuery): InventoryItemResource -> getInventoryItem
Edge(ResourceWrapsQuery): ProductAvailabilityResource -> getProductAvailability

Edge(QueryHasKey): getInventoryItem -> InventoryItemKey
Edge(QueryHasKey): getProductAvailability -> ProductAvailabilityKey

Edge(ActionInvalidatesKey): reserveInventory -> InventoryItemKey
Edge(ActionInvalidatesKey): reserveInventory -> ProductAvailabilityKey
Edge(ActionInvalidatesKey): reserveInventory -> CartAvailabilityKey
```

Manual reactivity does not replace derivation. It complements it.

## 10. IVM: incremental view maintenance

The product availability query is aggregate-derived:

```ts
export const ProductAvailabilityView = app.ivm.materializedView("ProductAvailabilityView", {
  source: getProductAvailability,

  key: ProductAvailabilityKey,

  maintainedBy: {
    on: [InventoryReserved],

    delta: ({ event }) => ({
      productId: event.payload.productId,

      totalReserved: AddQuantityDelta.delta(event.payload.quantity),

      totalAvailable: AddQuantityDelta.delta(
        expr.mul(event.payload.quantity, -1),
      ),
    }),
  },

  laws: [
    laws.deltaMaintainsView({
      assurance: assurance.tested(),
    }),

    laws.eventReplaySafe({
      because: reserveInventory.laws.idempotent,
      assurance: assurance.byConstruction(),
    }),
  ],

  fallback: {
    ifUnsupported: "invalidate_and_refetch",
    ifOutOfOrder: "recompute_partition",
  },
});
```

This says:

```txt
When inventory is reserved:
  totalReserved += quantity
  totalAvailable -= quantity
```

Because `AddQuantityDelta` is associative and commutative, Gen2 can maintain the aggregate incrementally even when events arrive in batches.

Generated facts:

```txt
Node(MaterializedView): ProductAvailabilityView
Edge(ViewMaintainsQuery): ProductAvailabilityView -> getProductAvailability
Edge(ViewTriggeredByEvent): ProductAvailabilityView -> InventoryReserved
Edge(ViewUsesDeltaOperation): ProductAvailabilityView -> AddQuantityDelta
Edge(ViewHasFallback): ProductAvailabilityView -> invalidate_and_refetch
Law(DeltaMaintainsView): ProductAvailabilityView
```

Generated artifacts:

```txt

  materialized table or indexed aggregate table

Server:
  IVM maintenance worker
  recompute partition fallback

Client:
  direct cache patch for product availability

Tests:
  full recompute equals incremental update
```

```txt
  yes, very important for numeric/string/collection ops

class form
  mostly no; only for rare plugin/target implementation classes

decorator form
  no, not primary

raw JS function form
  yes, but only as opaque implementation with declared blast radius
```

## 1. Object form: canonical and readable

This should be the most stable/documented form.

```ts
export const AddQuantityDelta = gen.operation.define({
  name: "AddQuantityDelta",

  kind: "binary",

  input: {
    current: Quantity,
    delta: Quantity,
  },

  output: Quantity,

  traits: [
    traits.pure,
    traits.deterministic,
    traits.patchable,
    traits.invertible,
  ],

  laws: [
    laws.associative({ assurance: assurance.byConstruction() }),
    laws.commutative({ assurance: assurance.byConstruction() }),
    laws.hasIdentity({ value: 0, assurance: assurance.byConstruction() }),
    laws.hasInverse({
      inverse: ({ delta }) => expr.mul(delta, -1),
      assurance: assurance.byConstruction(),
    }),
  ],

  implementations: {
    typescript: op.ts("(current, delta) => current + delta"),
    postgres: op.sql("($1 + $2)"),
  },

  protocols: {
    patch: gen.operation.patchProtocol({
      producePatch: ({ input }) =>
        gen.patch.increment(input.current, input.delta),

      invertPatch: ({ input }) =>
        gen.patch.increment(input.current, expr.mul(input.delta, -1)),
    }),
  },
});
```

This is verbose but excellent for generated docs, AI editing, and code review.

## 2. Curried name form: best default DX

```ts
export const AddQuantityDelta = gen.operation.define("AddQuantityDelta")({
  kind: "binary",

  input: {
    current: Quantity,
    delta: Quantity,
  },

  output: Quantity,

  traits: [traits.pure, traits.deterministic, traits.patchable],

  laws: [
    laws.associative(),
    laws.commutative(),
  ],
});
```

This is likely the best everyday form.

It keeps the name out front and gives object-literal inference for the rest.

## 3. Kind-specific builders

You should absolutely have kind-specific helpers.

```ts
export const AddQuantityDelta = gen.operation.binary("AddQuantityDelta", {
  left: Quantity,
  right: Quantity,
  output: Quantity,

  laws: [
    laws.associative(),
    laws.commutative(),
    laws.hasIdentity({ value: 0 }),
  ],

  implementations: {
    postgres: op.sql("($1 + $2)"),
    typescript: op.ts("(a, b) => a + b"),
  },
});
```

And:

```ts
const IsPositive = gen.operation.predicate("IsPositive", {
  input: Quantity,
  output: t.boolean(),

  body: expr.define(({ input }) => expr.gt(input, 0)),
});

const SumQuantity = gen.operation.aggregate("SumQuantity", {
  input: Quantity,
  output: Quantity,

  laws: [
    laws.associative(),
    laws.commutative(),
  ],

  requires: [
    operation.constraints.numeric,
  ],
});

const SendEmail = gen.operation.effect("SendEmail", {
  input: t.object({
    to: t.email(),
    subject: t.string(),
    body: t.string(),
  }),

  output: t.void(),

  effects: [
    effects.emailSend(),
    effects.network(),
  ],

  requires: [EmailApiKey],

  placement: WorkerBoundary,
});
```

This improves inference and lets the builder enforce kind-specific invariants:

```txt
predicate must output boolean
comparison must output boolean
effect operation must declare effects
aggregate must have aggregate-compatible input
reducer should declare laws or diagnostics
```

## 4. Fluent builder form for complex operations

For complex operation protocols, fluent builders are useful.

```ts
export const AddQuantityDelta = gen.operation
  .binary("AddQuantityDelta")
  .left(Quantity)
  .right(Quantity)
  .output(Quantity)
  .trait(traits.pure)
  .trait(traits.deterministic)
  .trait(traits.patchable)
  .law(laws.associative({ assurance: assurance.byConstruction() }))
  .law(laws.commutative({ assurance: assurance.byConstruction() }))
  .law(laws.hasIdentity({ value: 0 }))
  .impl("typescript", op.ts("(a, b) => a + b"))
  .impl("postgres", op.sql("($1 + $2)"))
  .patch(({ input }) =>
    gen.patch.increment(input.left, input.right),
  )
  .inversePatch(({ input }) =>
    gen.patch.increment(input.left, expr.mul(input.right, -1)),
  );
```

This is best when users are building operations interactively.

The downside is inference can degrade if the builder is not carefully typed. So I would support it, but keep object/curried forms as the primary README style.

## 5. Callback builder form

This may be the nicest for complex inference.

```ts
export const AddQuantityDelta = gen.operation.binary("AddQuantityDelta")((op) =>
  op
    .left(Quantity)
    .right(Quantity)
    .output(Quantity)
    .traits([
      traits.pure,
      traits.deterministic,
      traits.patchable,
      traits.invertible,
    ])
    .laws([
      laws.associative({ assurance: assurance.byConstruction() }),
      laws.commutative({ assurance: assurance.byConstruction() }),
      laws.hasIdentity({ value: 0 }),
    ])
    .implementations({
      typescript: op.impl.ts("(a, b) => a + b"),
      postgres: op.impl.sql("($1 + $2)"),
    })
    .patch(({ input }) =>
      gen.patch.increment(input.left, input.right),
    )
    .inverse(({ input }) =>
      gen.patch.increment(input.left, expr.mul(input.right, -1)),
    ),
);
```

The callback form also gives you a clean place for contextual helpers:

```ts
op.impl.ts(...)
op.impl.sql(...)
op.law.associative(...)
op.patch.increment(...)
op.constraints.numeric()
```

## 6. Type-family operation builders

This is important and easy to miss.

Many operations are not one-off. They belong to type families:

```txt
numeric
string
boolean
array
set
map
datetime
money
state machine
```

So support operation families:

```ts
export const NumericOps = gen.operation.family("numeric", {
  typeParam: "T",
  constraint: type.traits.numeric,
}).define((ops) => ({
  add: ops.binary("add", {
    left: ops.T,
    right: ops.T,
    output: ops.T,
    laws: [
      laws.associative(),
      laws.commutative(),
    ],
  }),

  subtract: ops.binary("subtract", {
    left: ops.T,
    right: ops.T,
    output: ops.T,
  }),

  greaterThan: ops.comparison("greaterThan", {
    operand: ops.T,
    output: t.boolean(),
    requires: [type.traits.orderable],
  }),
}));
```

Then instantiate:

```ts
export const QuantityOps = NumericOps.for(Quantity);
export const MoneyOps = NumericOps.for(Money);
```

This is useful for:

```txt
expression builders
query lowering
target capability checks
generated operator overloads
operation law tests
```

## 7. Operation as graph step

Every operation should be composable as a graph fragment.

```ts
export const InventoryModule = app.module("inventory").pipe(
  Quantity,
  AddQuantityDelta,
  SubtractQuantity,
  reserveInventory,
);
```

That means an operation should expose:

```ts
AddQuantityDelta.ref;
AddQuantityDelta.type;
AddQuantityDelta.input;
AddQuantityDelta.output;
AddQuantityDelta.laws;
AddQuantityDelta.effects;
AddQuantityDelta.fragment;
AddQuantityDelta.$infer.input;
AddQuantityDelta.$infer.output;
```

Consistent witness surface matters.

## 8. Raw JS function wrapper should be explicit opaque implementation

Support this, but do not let it masquerade as a semantic operation.

```ts
export const ComputeRiskScore = gen.operation.opaque("ComputeRiskScore", {
  input: {
    incident: Incident,
  },

  output: t.number(),

  implementation: riskScoreImpl,

  placement: ServerBoundary,

  reads: [
    Incident.fields.severity,
    Incident.fields.createdAt,
  ],

  effects: [],

  lowerability: {
    sql: false,
    client: false,
    jsonRender: false,
  },

  reactivity: {
    precision: "conservative",
    fallback: "invalidate",
  },

  test: {
    fixtures: "required",
  },
});
```

Rule:

```txt
Opaque is allowed.
Unknown is not.
```

## 9. Class form should not be primary

I would not make operations class-first.

This is good:

```ts
class User extends app.entity.class("User", { ... }) {}
```

But this is probably not worth encouraging:

```ts
class AddQuantityDelta extends gen.operation.class(...) {}
```

Why?

```txt
Operations are semantic computation definitions.
Classes imply runtime behavior and inheritance.
Inheritance is usually the wrong semantic model for operations.
```

A rare plugin form might be okay:

```ts
class PostgresAddQuantityImpl extends gen.operation.implementation.class({
  operation: AddQuantityDelta,
  target: targets.postgres,
}) {
  emit() {
    return "($1 + $2)";
  }
}
```

But that is an implementation plugin, not the operation definition itself.

## 10. The overload shape I’d use

Something like:

```ts
type DefineOperation = {
  <const TDef extends OperationObjectDef>(def: TDef): OperationWitness<TDef>;

  <const TName extends string>(
    name: TName,
  ): <const TDef extends OperationBodyDef>(
    def: TDef,
  ) => OperationWitness<{ name: TName } & TDef>;

  unary<const TName extends string>(
    name: TName,
  ): UnaryOperationBuilder<TName>;

  binary<const TName extends string>(
    name: TName,
  ): BinaryOperationBuilder<TName>;

  predicate<const TName extends string>(
    name: TName,
  ): PredicateOperationBuilder<TName>;

  aggregate<const TName extends string>(
    name: TName,
  ): AggregateOperationBuilder<TName>;

  reducer<const TName extends string>(
    name: TName,
  ): ReducerOperationBuilder<TName>;

  effect<const TName extends string>(
    name: TName,
  ): EffectOperationBuilder<TName>;

  family<const TName extends string>(
    name: TName,
    config: OperationFamilyConfig,
  ): OperationFamilyBuilder<TName>;

  opaque<const TName extends string>(
    name: TName,
    config: OpaqueOperationConfig,
  ): OpaqueOperationWitness<TName>;
};
```

And support both:

```ts
gen.operation.binary("add", {
  left: Quantity,
  right: Quantity,
  output: Quantity,
});
```

and:

```ts
gen.operation.binary("add")((op) =>
  op.left(Quantity).right(Quantity).output(Quantity),
);
```

## 11. README-friendly example

I’d show operations like this:

```ts
export const AddQuantityDelta = gen.operation.binary("AddQuantityDelta", {
  left: Quantity,
  right: Quantity,
  output: Quantity,

  traits: [
    traits.pure,
    traits.deterministic,
    traits.patchable,
    traits.invertible,
  ],

  laws: [
    laws.associative({ assurance: assurance.byConstruction() }),
    laws.commutative({ assurance: assurance.byConstruction() }),
    laws.hasIdentity({ value: 0 }),
    laws.hasInverse({
      inverse: ({ right }) => expr.mul(right, -1),
    }),
  ],

  implementations: {
    typescript: op.ts("(current, delta) => current + delta"),
    postgres: op.sql("($1 + $2)"),
  },

  patch: {
    apply: ({ left, right }) =>
      gen.patch.increment(left, right),

    invert: ({ left, right }) =>
      gen.patch.increment(left, expr.mul(right, -1)),
  },
});
```

Then later show the callback form as the advanced equivalent.

## 12. Final recommendation

Yes, operations should support the matrix, but I would rank them like this:

```txt
Primary:
  object
  curried object
  kind-specific object

Secondary:
  fluent builder
  callback builder
  operation families

Advanced:
  opaque operation
  target implementation plugins

Avoid as primary:
  class operation definitions
  decorators
  implicit JS function extraction
```

The most important design rule:

```txt
Many authoring forms.
One operation IR.
Every operation is inspectable unless explicitly opaque.
Every opaque operation declares its blast radius.
```

That gives users great DX without sacrificing the compiler’s ability to reason about laws, rules, reactivity, IVM, optimistic updates, target lowering, and code generation.
