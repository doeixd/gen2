```txt id="yd5q92"
  collections

  streams
```

The current repo already has many seeds of this. `ResourceState` models loading/success/failure/defect-style resource state; `StateResource` models non-query app state with storage, key family, read/write access, reactivity, sensitivity, lifetime, and hydration; offline queues already model command envelopes, persistence, encryption, idempotency, ordering, conflict policy, retry policy, replay requirements, and drain triggers.

Yes. There are several very useful learnings, but the right conclusion is **not** “copy Effect Stream” or “copy MLIR async.” It is:

> Gen2 should define a small, target-neutral **dataflow layer** over the new kernel: collections, resources, streams, queues, mailboxes, dispatches, and durable messages are all graph dialects built from nodes, edges, operations, traits, protocols, scopes, and passes.

## 1. Effect Stream lessons

Effect’s `Stream<A, E, R>` is a strong model: it describes a program that may emit zero or more values of type `A`, may fail with `E`, and requires an environment/context `R`. The docs explicitly describe Stream as similar to an Effect that can emit multiple values. ([Effect TS][1])

Gen2 should mirror that shape:

```ts
StreamType<A, E, R, Eff, Traits>
```

Where:

```txt
A   = emitted value type
E   = expected error type
R   = required context/providers
Eff = effect footprint
Traits = ordered, replayable, durable, finite, hot, cold, etc.
```

The important part is not the exact API. It is the **typed channels**:

```txt
success values
expected errors
requirements
effects
lifetime/scope
```

That lines up perfectly with Gen2’s callable/query/action/resource model.

## 2. Streams need scoped resource semantics

Effect has scoped stream constructors like `Stream.scoped`, `unwrapScoped`, and `scopedWith`, which tie acquisition/release to stream execution. ([Effect TS][1])

Gen2 should steal this idea directly.

A stream/resource/queue consumer should be able to say:

```txt
this stream opens a DB cursor
this stream subscribes to a websocket
this stream owns a queue lease
this stream must release on scope end
this stream has finalizers
```

So add graph concepts like:

```txt
StreamNode --requires--> Provider
StreamNode --runsIn--> Scope
StreamNode --hasFinalizer--> Finalizer
StreamNode --acquires--> Resource
StreamNode --releasesWith--> CleanupAction
```

This connects to current Gen2: `ReactiveResource`, `ScopedResource`, `Finalizer`, lifecycle requirements, stream resources, and disposal policies already exist in the reactivity layer. 

## 3. Element streams and chunk streams should both exist

Effect exposes chunk-level operations: `chunks` turns a stream of elements into a stream of chunks, and `chunksWith` allows transformations at the chunk layer. ([Effect TS][1])

Gen2 should model this distinction:

```txt
Stream<T>
  logical element stream

Stream<Chunk<T>>
  batched/chunked stream

Queue<T>
  message-oriented stream with delivery semantics

Page<T>
  finite query window with cursor

List<T>
  finite in-memory or query result collection
```

This matters for:

```txt
batching UI updates
bulk SQL writes
queue drain batching
streaming server responses
IVM batch maintenance
outbox delivery
```

The Effect v4 event page also highlights “~20× faster streams & batching” as a focus of Effect 4.0, which is a signal that chunking/batching should be a first-class performance concept, not an emitter afterthought. ([effect.website][2])

## 4. Pure vs effectful stream operators

Effect separates pure operators like `filter` from effectful ones like `filterEffect`; the latter bubbles additional errors and requirements into the resulting stream. ([Effect TS][1])

Gen2 should copy the distinction:

```txt
filter
  pure predicate Expr
  preserves no new effects

filterEffect / filterByRuleWithProvider
  may require context/provider
  may fail
  may be server-only
```

For Gen2:

```ts
Stream.filter(rule)
Stream.filterEffect(callable)
```

Graph facts:

```txt
Stream uses Rule
Rule reads Field
Stream requires Provider
Stream has Effect
Stream is or is not client-safe
```

This is exactly the same inference philosophy we want everywhere: requirements/effects/errors bubble up.

## 5. Sink/run separation is important

Effect Streams are not “just arrays.” You run them with sinks/collectors, and there are conversions like `toAsyncIterable`. ([Effect TS][1])

Gen2 should separate:

```txt
Source
  produces values

Stream
  transforms values

Sink
  consumes values

Reducer
  consumes values into state

Queue
  stores values durably

Resource
  exposes values to UI/reactivity
```

Do not make `Stream<T>` automatically mean “collect into `T[]`.”

That gives clearer codegen:

```txt
Stream -> SSE
Stream -> WebSocket
Stream -> Effect Stream
Stream -> AsyncIterable
Stream -> queue consumer
Stream -> React/Solid resource
Stream -> materialized view maintenance
```

`AsyncIterable` should be a target adapter, not the canonical Gen2 stream model.

# 6. MLIR lessons

## Keep high-level semantics until late

MLIR bufferization converts high-level tensor semantics into physical memory-buffer semantics late in the pipeline, because many transformations are easier before lowering to memory. ([MLIR][3])

Gen2 should do the same.

Do not lower early:

```txt
Stream<T> -> WebSocket code
Queue<T> -> Redis list
Resource<T> -> TanStack Query
```

Keep high-level graph IR:

```txt
StreamNode
QueueNode
ResourceNode
DispatchNode
OperationNode
```

Then legalize late:

```txt
Stream -> Effect Stream / AsyncIterable / SSE / WebSocket
Queue -> Postgres outbox / Redis stream / browser IndexedDB queue
Resource -> React hook / Solid resource / Effect Atom
```

This is the same “logical dialect first, physical dialect later” principle.

## Model async explicitly

MLIR’s async dialect has explicit operations for async execution, await, groups, async calls, and async functions. ([MLIR][4])

Gen2 should not hide async behind “function returns Promise.” It should have explicit graph facts:

```txt
Node is async
Node awaits Resource
Node joins Group
Dispatch runs concurrently
Queue drain has parallelism
Stream consumer has backpressure
```

Suggested nodes/edges:

```txt
AsyncGroupNode
AwaitEdge
RunsConcurrentlyEdge
JoinEdge
CancellationScopeNode
BackpressurePlanNode
```

This will matter for generated queue workers, streaming UI, resource cleanup, and cancellation.

## Use placement/memory-space thinking

MLIR `memref.memory_space_cast` models casts between memory spaces while preserving shape/type/layout and aliasing the same underlying memory. ([MLIR][5])

Gen2 analogue:

```txt
server memory
client memory
query cache
localStorage
sessionStorage
database
queue
outbox
edge runtime
worker
```

A value crossing these spaces should be explicit:

```txt
Value placedIn StorageLocation
Value crosses Boundary
Value serializedWith Transform
Value hydratedInto StateResource
Value queuedAs MessageEnvelope
```

Current Gen2 already has storage locations with persistence/sensitivity/client/server readability and state resources with storage, key families, reactivity, sensitivity, lifetime, and hydration.  

## Structured control flow matters

MLIR’s SCF dialect models structured `if`, `for`, `while`, `parallel`, and `reduce` operations. ([MLIR][6])

Gen2 should have structured plan/stream/queue control flow:

```txt
forEach stream item
while queue has messages
parallel drain partitions
race sources
retry with policy
reduce stream into state
```

Not as opaque JS. As graph-visible plan/region nodes.

# 7. Current repo/planning docs lessons

## Keep ResourceState, but generalize it

The current `ResourceState` already distinguishes initial/loading/success/refreshing/failure/defect. 

I’d standardize this into:

```txt
Result<T, E>
  success or expected failure

Exit<T, E, Defect>
  success, expected failure, or defect

ResourceState<T, E, Defect>
  lifecycle state for async/reactive data
```

The 5-state model should probably be:

```txt
initial
loading
success
failure
defect
```

with flags:

```txt
stale
refreshing
optimistic
```

That avoids making `refreshing` a totally separate state when it is really `success + refresh in flight`.

## Keep offline queue semantics

The current offline plan already has exactly the right concepts: serializable command envelope, idempotency key, ordering key, conflict policy, retry policy, replay requirements, queue storage, persistence, encryption, drain trigger, and sensitivity. 

Rebase those into a queue/mailbox dialect:

```txt
QueueNode
CommandEnvelopeType
MessageNode
DrainTriggerNode
RetryPolicyNode
ConflictPolicyNode
IdempotencyPlanNode
OrderingKeyExpr
```

Edges:

```txt
Action enqueues Command
Queue stores CommandEnvelope
Queue drainsWith Dispatch
Command replays Action
Queue placedIn StorageLocation
```

## Keep dispatch/reaction/event semantics

The current reaction model says rules stay pure and reactions own the effectful interpretation.  Keep that boundary.

Events already have payloads, emissions, reducers, subscriptions, and outbox concepts. 

Rebase into:

```txt
EventNode
MessageNode
DispatchNode
ReducerNode
OutboxPlanNode
DeliveryPlanNode
```

Do not keep separate event/reaction/subscription registries. Make them views over dispatch graph patterns.

## Preserve Phase 4.5’s expression unification

Phase 4.5’s strongest lesson is that `RuleExpr` should disappear: rules are pure, effect-free predicates over the universal expression AST; dependency tracking should happen for every expression, not just rules. 

That matters for streams too:

```txt
Stream.filter(rule)
Query.where(rule)
Dispatch.when(rule)
IVM predicate maintenance
```

All should consume the same expression graph.

## Preserve Phase 5.5’s separation of scopes

Phase 5.5 warns not to collapse `ProviderScope` and `TrackingScope`: provider scope is about dependency identity, while tracking scope is about reactivity. 

For streams/queues/resources, keep the same discipline:

```txt
ExecutionScope
  where this runs

ProviderScope
  which dependencies are available

TrackingScope
  what reactive reads are tracked

PlacementScope
  where values live
```

# 9. The main architectural lesson

Effect teaches:

```txt
Streams need A/E/R channels, scope safety, chunking, sinks, and runtime adapters.
```

MLIR teaches:

```txt
Keep logical IR high-level, then legalize/lower late into physical runtimes/storage/control flow.
```

The current Gen2 repo teaches:

```txt
We already have the right concepts: resource state, stable keys, offline queues, events, reactions, state resources, storage locations, boundaries, and scopes.
```

So the final recommendation is:

> Do not add a pile of new primitives. Add a coherent **dataflow/async dialect family** where streams, queues, mailboxes, resources, messages, and dispatches are all graph patterns over typed operations, scopes, placements, and effects.

That gives Gen2 a path to support:

```txt
live queries
streaming responses
durable outbox
offline replay
mailboxes
queue workers
resource hydration
AI streaming output
incremental view maintenance
optimistic updates
typed state machines
typed event reducers
```

without losing the core philosophy: typed symbols, no magic strings, inspectable graph, derivable passes, and target-independent semantics.

# Hot streams vs cold streams

This distinction matters.

## Cold stream

A cold stream is a recipe. Each subscriber starts its own producer.


# Tracking scopes as subscribers

Current `TrackingScope` maps well to subscriptions.

# Scope is essential

Streams need multiple scopes, not one.

```txt
TrackingScope
  Who is observing this stream?
  Example: component, route, resource, effect.

ExecutionScope
  Where does the stream producer/consumer run?
  Example: client, server, worker, edge.

ProviderScope
  Which dependencies are available?
  Example: request, tenant, session, singleton.

CancellationScope
  When does subscription stop?
  Example: component unmount, request end, worker shutdown.

PlacementScope
  Where do values live?
  Example: memory, query cache, outbox, IndexedDB, Postgres.
```

A UI subscription and a queue subscription might read the same stream but have totally different scopes.

```txt
UserListComponent subscribes to UserStream
  tracking scope: component
  cancellation: component unmount
  placement: client query cache

EmailWorker subscribes to UserStream
  execution scope: worker
  cancellation: worker lifetime
  placement: outbox/queue
```

This is why Phase 5.5’s warning still applies: provider scope and tracking scope should share boundary identities where useful, but they are not the same concept.

# Streams and invalidation

There are two ways a stream can interact with reactivity.

## 1. Stream as invalidation signal

```txt
UserArchivedStream emits event
=> invalidate users.active key
```

This is simple and conservative.

## 2. Stream as patch signal

```txt
UserArchivedStream emits event
event payload includes userId
operation semantics say archived user leaves active list
=> patch users.active resource by removing user
```

This requires operation/rule semantics.

So stream subscriptions can produce:

```txt

refresh
append
remove
replace
reconcile
```

Those should be operation-backed.

```txt
  durable stream with delivery

  addressed durable stream

  pub/sub stream
```

This gives one coherent model.

# Example

```ts
const UserArchived = gen.event("UserArchived", {
  userId: User.fields.id.type,
  tenantId: Tenant.fields.id.type,
});

const UserArchivedStream = gen.stream("UserArchivedStream", {
  emits: UserArchived,
  key: gen.key.family("stream.userArchived", {
    tenantId: Tenant.fields.id.type,
  }),
  traits: [StreamHot, StreamOrdered, StreamReplayable],
  source: gen.source.outbox(UserArchived),
});

const ActiveUsers = gen.resource("ActiveUsers", {
  key: gen.key.family("users.active", {
    tenantId: Tenant.fields.id.type,
  }),
  type: gen.type.list(User),
  load: listActiveUsers,
});

gen.stream.subscribe("removeArchivedUsers", {
  stream: UserArchivedStream,
  scope: gen.scope.resource(ActiveUsers),
  run: gen.resource.patch(ActiveUsers, ({ event, list }) =>
    list.removeWhere((u) => u.id.eq(event.userId))
  ),
});
```

Graph facts:

```txt

Subscription runs patch operation
Patch operation removes user by id
Patch operation is deterministic
ActiveUsers key is patched, not broadly invalidated
```

If the patch is not provable, fallback:


# Are streams “just relationships”?

Not quite.

A stream has node identity and type:

```txt

```

A subscription is a relationship:

```txt
Subscriber --subscribesTo--> Stream
```

A publisher is also a relationship:

```txt

```

So:

```txt
Stream = node
Publish/Subscribe = edges
```

That fits the revised kernel perfectly.

# Final model

Yes, streams should be built on manual reactivity, but as a higher-level dialect:

```txt
Manual reactivity gives:
  stable keys
  resources
  mutations
  tracking scopes
  invalidation/patch edges

Streams add:
  temporal many-value semantics
  publishers/subscribers
  hot/cold distinction
  scope/cancellation
  backpressure
  replay/checkpointing
  durable queue/mailbox lowering
```

The compact architecture:

```txt
Publisher publishes Stream.
Subscriber subscribes to Stream.
Stream emits typed values over time.
Subscription runs in a scope.
Stream values materialize into resources or trigger dispatches.
Manual keys address streams/resources.
Queues/mailboxes are durable streams.
Passes derive invalidation, patches, codegen, cleanup, replay, and delivery.
```

So your intuition is right: **a stream is fundamentally publisher/subscriber plus scope**, but Gen2 should enrich that with type, error, delivery, replay, and materialization semantics so it can compile to resources, queues, workers, UI subscriptions, and runtime streams safely.

This doc is very strong. It is basically saying Gen2 needs a **dataflow / async dialect family**, not a pile of unrelated primitives.

The important claim is:

```txt id="t5t21g"
Do not make Queue, Mailbox, Stream, ResourceState, Event, Reaction,
Subscription, Reducer, ArrayOperation, and OfflineQueue separate hard primitives.

Model them as higher-level dialects built from:
Type, Node, Edge, Operation, Expr, Trait, Protocol, Scope, Placement, Pass.
```

I agree with that. It fits the ideal kernel architecture very well.

This doc is good and fits the ideal Gen2 design.

Its biggest contribution is naming the missing layer:

```txt id="dtdvf7"
dataflow / async dialect family
```

This is what lets Gen2 handle:

```txt id="0daabc"

resource lifecycles
streams
live queries
queues
mailboxes

durable outbox

AI streaming output
```

without bloating the hard kernel.

The core principle to keep:

