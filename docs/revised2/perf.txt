Yes — you need a serious story for both:

```txt
1. Compiler performance
   How fast Dirived can verify, derive, lower, emit, diff, and regenerate.

2. Generated app performance
   How fast the emitted app runs in the browser, server, database, worker, sync layer, etc.
```

And they should be designed together, but not confused.

# Compiler performance

Dirived is a compiler, so it needs compiler-grade infrastructure early.

The most important pieces are:

```txt
graph indexes
pass-level memoization
semantic hashing
incremental recomputation
artifact caching
graph snapshots
target-specific dependency tracking
```

The suggestions you uploaded are exactly right that the graph should not be “arrays of nodes and edges with filters everywhere.” It should maintain indexes like `edgesBySource`, `edgesByTarget`, `edgesByKind`, and `nodesByTrait`, so passes can answer questions such as “what rules read this field?” without scanning the whole graph. 

## Graph indexes

Internally, the graph should maintain indexes like:

```txt
nodesByKind
nodesByTrait
nodesByModule
nodesByRef

edgesByKind
edgesBySource
edgesByTarget
edgesByEndpointRole
edgesByTrait
edgesByProvenance

artifactsBySourceRef
diagnosticsBySubjectRef
passesByProducedFact
passesByConsumedFact
```

So this:

```txt
Action writes Field
Field is read by Query
Query derives Key
```

becomes fast graph traversal, not repeated full-graph search.

Public API:

```ts
graph.edgesFrom(archiveUser.ref, WritesEdgeKind)
graph.edgesTo(User.fields.archivedAt.ref, ReadsEdgeKind)
graph.nodesWithTrait(NodeEntrypoint)
graph.artifactsGeneratedFrom(User.ref)
```

Implementation: indexed.

## Pass memoization

Each pass should declare what it consumes and produces.

```ts
const DeriveReactivityPass = definePass({
  phase: "derive",
  consumes: {
    edges: [ReadsEdgeKind, WritesEdgeKind],
    nodes: [QueryNodeKind, ActionNodeKind],
  },
  produces: {
    edges: [InvalidatesKeyEdgeKind, PatchesResourceEdgeKind],
  },
  run: ...
});
```

Then Dirived can cache pass results based on the semantic hash of the facts the pass actually reads.

```txt
If User.email metadata changes,
  do not rerun the Postgres RLS lowering pass.

If canArchiveUser changes,
  rerun auth, UI state, tests, and affected target lowerings.

If a design token changes,
  rerun UI/style emitters, not database migration.
```

This is where the graph pays off: the compiler knows dependency structure at the semantic level.

## Incremental compilation

You want edits to behave like this:

```txt
Graph v12
  user changes one rule

Compute semantic diff
  Rule canArchiveUser changed

Find affected closure
  rules -> guards -> actions -> UI states -> RLS -> tests -> artifacts

Rerun only affected passes
  derive rule reads
  legalize auth policy
  lower UI disabled states
  emit changed artifacts
```

Not this:

```txt
rebuild entire app from scratch
rerun every pass
re-emit every file
redeploy everything
```

This matters a lot for an AI app builder because every chat turn is a graph patch.

## Semantic hashes

Every durable graph object should have a stable semantic hash.

```txt
Node hash
Edge hash
Trait application hash
Expr hash
Subgraph hash
Target IR hash
Artifact hash
```

The hash should ignore irrelevant presentation details unless those affect the target.

Example:

```txt
Changing field display label
  affects UI/docs artifacts

Changing field storage name
  affects migrations/database artifacts

Changing rule predicate
  affects auth, UI, tests, reactivity, maybe RLS
```

So hashes need to be aware of semantic categories.

## Pass cache and artifact cache

The revised phase notes already point toward `GraphVersion`, `PassCache`, `DerivedEdgeCache`, `ArtifactCache`, and `SemanticHash` as graph-native replacements for older checker/emitter caching ideas. 

I would make that explicit:

```txt
PassCache
  keyed by pass id + input subgraph hash + target capabilities

ArtifactCache
  keyed by target id + target IR hash + emitter version

DiagnosticCache
  keyed by verifier id + subject hash

LoweringCache
  keyed by source ref + target ref + capability hash
```

This lets Dirived regenerate quickly and know exactly what changed.

## Textual IR snapshots

For performance and migrations, textual IR snapshots matter.

Your suggestions file recommends a textual IR dumper and graph snapshots, with migrations generated by diffing old and new graph states.  That is the right model.

```txt
Graph(old).ir
Graph(new).ir
  -> diff
  -> migration plan
  -> artifacts
```

This also supports incremental compiler performance:

```txt
load previous graph snapshot
compare against current graph
reuse cached pass results for unchanged subgraphs
```

## Compiler graph shaking

Before target emission, prune the graph.

```txt
Start from:
  public boundaries
  UI entrypoints
  queue workers
  cron jobs
  exported functions
  forceEmit nodes

Follow:
  requires
  provides
  reads
  writes
  guards
  emits
  handles
  storedIn
  usesType
  lowersTo
```

Everything unreachable can be excluded from emission.

The phase revision notes call this graph shaking / pruning from boundaries and UI entrypoints so unused entities do not generate artifacts. 

That improves compiler performance and generated app size.

# Generated app performance

Generated code should not be “generic runtime interpreter over the graph” unless you intentionally choose that mode.

The graph is the **compile-time source of truth**.

Targets should emit specialized runtime artifacts.

```txt
Bad default:
  ship huge graph runtime to client
  evaluate everything dynamically

Good default:
  use graph at compile time
  emit small specialized code
```

## Smaller runtime through specialization

Because Dirived knows the exact app graph, it can emit only what is needed:

```txt
only reachable routes
only used queries
only client-safe rules
only required providers
only fields used by each view
only mutations reachable from UI/actions
```

This creates opportunities for:

```txt
dead-code elimination
tree-shaking
field-level selection
route-level splitting
server/client boundary splitting
generated narrow validators
generated narrow hooks
```

## Query and sync performance

Because Dirived knows reads, writes, predicates, operation laws, and keys, it can generate more precise reactivity.

```txt
Action writes User.archivedAt
Query reads User.archivedAt
Query filters archivedAt is null
Operation is reversible
```

From that, it can generate:

```txt
precise invalidation
optimistic patch
rollback patch
incremental count update
offline replay plan
fallback invalidation if uncertain
```

This avoids broad refetching where a precise patch is known.

But do not overpromise “optimal” globally. True optimality depends on data size, indexes, latency, runtime target, user behavior, and deployment topology.

Better phrase:

> Dirived generates target-specific, semantically precise default plans, and falls back conservatively when it cannot prove safety.

## Database performance

The same graph should drive database performance decisions:

```txt
Query reads fields
Predicate filters fields
Sort uses fields
Relation traverses edge
Policy reads tenantId
Materialized view aggregates count
```

Targets can derive:

```txt
indexes
foreign keys
join tables
RLS policies
partial indexes
materialized views
query projections
migration warnings
```

Example:

```txt
listActiveUsers filters User.archivedAt is null
  -> suggest or emit index on archived_at

tenant-scoped queries always filter organizationId
  -> suggest composite index

policy reads tenant_id
  -> ensure tenant_id is indexed
```

Some index generation should be automatic. Some should be diagnostic/suggestion-based, because indexes have write/storage tradeoffs.

## UI performance

The UI target can use the graph to avoid over-rendering.

```txt
View displays User.name
View disabledWhen canArchiveUser
canArchiveUser reads actor.role and user.organizationId
```

The generated UI can subscribe only to the state it needs.

Possible generated optimizations:

```txt
field-level form updates
query-level resource splitting
memoized derived UI states
route-level code splitting
component-level data dependencies
stable action bindings
minimal serialized props
```

## Server/runtime performance

Generated server code can be specialized around requirements and effects.

```txt
archiveUser requires:
  AuthSession
  Database
  Clock

sendArchiveEmail requires:
  EmailService
  Logger
```

Targets can generate narrow provider wiring rather than one global dependency bag.

Effect-style targets can map requirements to services/layers. Node/server targets can emit explicit parameters or request-local providers. Cloudflare/Alchemy targets can emit bindings and secrets only where needed.

## Deployment performance

If Alchemy/deployment is a target, graph facts can drive deployment shape:

```txt
queue worker only emitted if dispatch exists
cron only emitted if schedule exists
bucket only emitted if file storage exists
secret only required if provider needs it
```

This improves deploy speed, cold start size, and resource cost.

# The important distinction: compile-time graph vs runtime graph

Dirived should support both modes:

```txt
Compile-time mode
  Graph is used to emit specialized artifacts.
  Best for production performance.

Runtime/devtools mode
  Graph or graph slices are available at runtime for explanation, debugging, dynamic rendering, AI inspection.
  Useful for dev, admin, introspection, generated dashboards.
```

Do not always ship the whole graph to the client.

Instead:

```txt
client gets only safe graph slices
server/devtools may get richer graph
compiler keeps full graph
```

Example:

```txt
Client may receive:
  form schema
  safe validation diagnostics
  UI visibility hints
  action error contracts

Client should not receive:
  server-only rules
  secrets
  sensitive provider graph
  internal deployment details
```

# Memoization inside generated apps

Generated apps can also use memoization, but again it should be semantic.

## Rule memoization

Rules can be memoized based on their read dependencies.

```txt
canArchiveUser reads:
  actor.role
  actor.organizationId
  user.organizationId
  user.archivedAt
```

So the generated UI/runtime can recompute only when those values change.

## Query memoization

Queries can derive stable keys from typed inputs.

```txt
listUsers({ tenantId, status })
  -> key: users.byTenantStatus(tenantId, status)
```

Because keys are graph objects, not ad hoc strings, targets can generate consistent cache keys.

## Transform memoization

Transforms can memoize decode/encode when safe.

```txt
JSON payload -> domain object
database row -> entity value
URL params -> typed input
```

Only do this if the transform is pure/deterministic and input identity/value hashing is well-defined.

## Operation memoization

Pure operations can be memoized.

Effectful operations should not be memoized unless explicitly idempotent/cacheable and scoped.

```txt
Pure expression:
  memoizable

Database query:
  cacheable only through query/resource policy

Email send:
  never memoized, but can be idempotency-key protected
```

Traits/laws should control this.

# Performance risks

## 1. TypeScript type explosion

Your type system can get too deep.

Use:

```txt
public facade types
type collapsing
localized inference
optional full typed registry
```

The suggestions file calls this the “Hover of Death” problem and recommends facade interfaces/type collapsing at the public API boundary.  I agree.

## 2. Pass explosion

Too many passes can become slow or hard to reason about.

Mitigations:

```txt
consume/produce declarations
topological sorting
phase boundaries
pass caches
subgraph hashes
diagnostic timing reports
```

Add `vp profile` eventually:

```bash
vp profile compile
```

showing:

```txt
pass name
time
input facts read
facts produced
cache hit/miss
artifacts emitted
```

## 3. Graph bloat

The graph can become huge if every tiny thing becomes a node.

Mitigations:

```txt
only durable semantic facts become nodes
expression internals can be compact
edge indexes are lazy or chunked
target IR graphs are separate/prunable
debug graph can be richer than production graph
```

## 4. Over-precise derivation cost

Precise IVM/optimistic planning can be expensive.

Mitigation:

```txt
precision budgets
fallback to conservative invalidation
cache derived affect analysis
allow manual hints
target-specific heuristics
```

Do not spend 500ms proving a patch when a 20ms invalidation is good enough.

## 5. Shipping too much generated runtime

Mitigation:

```txt
tree-shake
prune graph
emit static code
split devtools graph from production bundle
only ship client-safe graph slices
```

# The crisp answer

For compiler performance:

> Dirived should behave like an incremental compiler: indexed graph queries, semantic hashes, pass-level memoization, graph diffs, cached target IR, artifact caching, and reachability pruning.

For generated app performance:

> Dirived should use the graph at compile time to emit specialized, pruned, target-specific code — precise queries, minimal UI subscriptions, generated indexes, derived optimistic updates, and only the runtime helpers each app actually needs.

The graph should make both sides faster:

```txt
Compiler:
  knows what changed, so it recompiles less.

Generated app:
  knows what changes, so it rerenders/refetches/recomputes less.
```


For performance, structure Gen2 as a **canonical graph store plus derived indexes plus pass-local materialized views**.

Right now the graph shape is a good starting point, but it is optimized for simplicity, not traversal speed. `KernelGraph` stores `types`, `transforms`, `exprs`, `traits`, `nodes`, and `edges` as maps, but the query helpers mostly do `Array.from(...).filter(...)`; `edgesFrom`, `edgesTo`, `edgesOfKind`, `nodesOfKind`, and `nodesWithTrait` all scan the graph, and `neighborhood` repeatedly calls scan-based `edgesFrom` / `edgesTo`. Registration also copy-on-writes whole maps, while bridge helpers mutate maps in place to avoid copying during dual-write migration.  

The revised design should keep the **semantic graph** as the source of truth, but add an indexed execution layer.

# 1. Use three graph layers

```txt id="byxlgj"
GraphStore
  canonical immutable-ish object storage

GraphIndex
  maintained indexes for fast traversal

GraphView
  pass-local or dialect-local materialized views
```

Conceptually:

```ts id="3s04fo"
type GraphStore = {
  version: number;

  types: Map<TypeId, TypeNode>;
  exprs: Map<ExprId, ExprNode>;
  nodes: Map<NodeId, KernelNode>;
  edges: Map<EdgeId, KernelEdge>;
  traits: Map<TraitId, TraitDef>;
  protocols: Map<ProtocolId, ProtocolDef>;

  index: GraphIndex;
};
```

The important part: **do not traverse by scanning `graph.edges.values()` inside hot paths.**

The current plan already says the graph should be the core kernel and pass pipelines should replace checker/emitter registries. That means graph traversal will become the dominant runtime cost in `verify`, `derive`, `canonicalize`, `legalize`, `lower`, and `emit`.

# 2. Maintain indexes at write time

At minimum:

```ts id="zamxjm"
type GraphIndex = {
  nodesByKind: Map<NodeKindId, Set<NodeId>>;
  nodesByTrait: Map<TraitId, Set<NodeId>>;
  nodesByProtocol: Map<ProtocolId, Set<NodeId>>;

  edgesByKind: Map<EdgeKindId, Set<EdgeId>>;
  edgesByTrait: Map<TraitId, Set<EdgeId>>;

  incidentEdgesByRef: Map<RefId, Set<EdgeId>>;

  edgesByKindAndEndpoint: Map<
    EdgeKindId,
    Map<EndpointRoleId, Map<RefId, Set<EdgeId>>>
  >;

  outgoingByRef: Map<RefId, Set<EdgeId>>;
  incomingByRef: Map<RefId, Set<EdgeId>>;

  outgoingByKind: Map<RefId, Map<EdgeKindId, Set<EdgeId>>>;
  incomingByKind: Map<RefId, Map<EdgeKindId, Set<EdgeId>>>;

  traitClosureByObject: Map<RefId, Set<TraitId>>;
};
```

That turns common queries into cheap index lookups:

```ts id="71fkzr"
graph.nodes.ofKind(domain.nodes.entity);
// index.nodesByKind.get(entityKind.id)

graph.edges.ofKind(app.edges.writes);
// index.edgesByKind.get(writesKind.id)

graph.edges
  .ofKind(app.edges.writes)
  .from("action", archiveUser.ref)
  .targets("field");
// index.edgesByKindAndEndpoint
//   .get(writes.id)
//   .get(actionRole.id)
//   .get(archiveUser.ref.id)
```

The hot path should be:

```txt id="7onau4"
kind lookup
endpoint role lookup
ref lookup
hydrate edge ids
hydrate target refs
```

not:

```txt id="lttw8u"
scan all edges
check edge.kind
scan endpoints
guess endpoint direction
```

# 3. Treat Gen2 edges as typed hyperedges, but index them like tables

Gen2 edges are not always binary. An edge may have multiple named endpoints:

```ts id="3m0ucx"
edge(app.edges.writes, {
  action: ref(archiveUser),
  field: ref(User.fields.archivedAt),
});
```

So internally, index each endpoint separately:

```txt id="w678x3"
edge_id | edge_kind | role_id | target_ref
```

Think of this as a secondary endpoint table:

```ts id="e9tsxv"
type EndpointRecord = {
  edgeId: EdgeId;
  edgeKindId: EdgeKindId;
  roleId: EndpointRoleId;
  roleName: string;
  targetId: RefId;
  direction: "source" | "target" | "context" | "metadata";
};
```

Then traversal is fast and uniform:

```ts id="u0ohdi"
edgesByKindAndEndpoint
  .get("app.edge.writes")
  ?.get("action")
  ?.get("action:archiveUser");
```

For very hot binary relationships, add specialized pair indexes:

```ts id="t5i710"
type PairIndexKey = `${EdgeKindId}:${FromRoleId}:${ToRoleId}`;

pairIndex: Map<
  PairIndexKey,
  Map<FromRefId, Map<ToRefId, Set<EdgeId>>>
>;
```

Use that for relationships like:

```txt id="gsro6y"
Entity -> Field
Action -> Field
Rule -> Field
Query -> Field
View -> Slot
Behavior -> Slot
Provider -> Requirement
```

# 4. Stop inferring direction from role-name prefixes

Current `edgesBetween` / `neighborhood` infer source-ish and target-ish endpoints by checking whether role IDs start with strings like `edge.role.owner`, `edge.role.source`, `edge.role.from`, `edge.role.writer`, etc. That works as a bridge, but it will become slow and brittle as dialects grow. 

Make direction part of the endpoint definition:

```ts id="cxn7yr"
const writes = d.edgeKind("writes", {
  endpoints: {
    action: d.endpoint("action")
      .target(app.nodes.action)
      .direction("source"),

    field: d.endpoint("field")
      .target(domain.nodes.field)
      .direction("target"),
  },
});
```

Then the index can maintain:

```ts id="d6p49h"
outgoingByRef
incomingByRef
outgoingByKind
incomingByKind
```

without string-prefix heuristics.

# 5. Traversal API should compile to index probes

Public graph traversal should feel semantic:

```ts id="17uzc8"
graph
  .from(archiveUser)
  .via(app.edges.writes)
  .targets("field");
```

or:

```ts id="8dryzz"
graph.edges
  .ofKind(app.edges.writes)
  .whereEndpoint("action", archiveUser.ref)
  .mapEndpoint("field");
```

Under the hood:

```txt id="ps3stg"
ofKind
  restricts edge ID set by kind index

whereEndpoint
  intersects with endpoint-role/ref index

mapEndpoint
  reads named endpoint records without rescanning endpoint arrays
```

For example:

```ts id="lzn8nx"
const writtenFields = graph.edges
  .ofKind(app.edges.writes)
  .whereEndpoint("action", ref(archiveUser))
  .targets("field");
```

should be roughly:

```ts id="7a2l48"
const edgeIds =
  index.edgesByKindAndEndpoint
    .get(app.edges.writes.id)
    ?.get(app.edges.writes.endpoints.action.id)
    ?.get(archiveUser.ref.id) ?? emptySet;

return hydrateEndpointTargets(edgeIds, app.edges.writes.endpoints.field);
```

No global scan.

# 6. Use a real traversal engine for neighborhoods

The current `neighborhood` recursively collects result nodes and then recursively iterates over the growing result list. It also calls scan-based `edgesFrom` and `edgesTo`, so it can get expensive quickly. 

Use iterative BFS with adjacency indexes:

```ts id="6at0v7"
function neighborhood(
  graph: IndexedGraph,
  start: RefId,
  options: {
    depth?: number;
    edgeKinds?: readonly EdgeKindWitness[];
    direction?: "out" | "in" | "both";
    role?: EndpointRoleWitness;
    nodeKinds?: readonly NodeKindWitness[];
  } = {},
) {
  const maxDepth = options.depth ?? 1;
  const seenNodes = new Set<RefId>([start]);
  const seenEdges = new Set<EdgeId>();
  const queue: Array<{ id: RefId; depth: number }> = [{ id: start, depth: 0 }];

  while (queue.length > 0) {
    const { id, depth } = queue.shift()!;
    if (depth >= maxDepth) continue;

    const edges = graph.index.adjacent(id, options);

    for (const edgeId of edges) {
      if (seenEdges.has(edgeId)) continue;
      seenEdges.add(edgeId);

      for (const next of graph.index.otherEndpoints(edgeId, id, options)) {
        if (seenNodes.has(next)) continue;
        if (!graph.index.refMatchesNodeKinds(next, options.nodeKinds)) continue;

        seenNodes.add(next);
        queue.push({ id: next, depth: depth + 1 });
      }
    }
  }

  return graph.hydrate({ nodes: seenNodes, edges: seenEdges });
}
```

Also: default `depth` should probably be `1`, not `2`, because semantic graphs can fan out quickly.

# 7. Add pass-local materialized views

Do not make every pass manually traverse raw graph indexes.

Create dialect-specific views:

```ts id="2u6fj6"
const domain = graph.view(domainView);
const callable = graph.view(callableView);
const reactivity = graph.view(reactivityView);
const providers = graph.view(providerView);
```

Example:

```ts id="4iuz17"
type DomainView = {
  entities(): readonly EntityNode[];
  fieldsOf(entity: EntityRef): readonly FieldNode[];
  typeOfField(field: FieldRef): TypeRef;
  relationsFrom(entity: EntityRef): readonly RelationEdge[];
};
```

Provider checking should not repeatedly scan all nodes and all edges. The current requirement/provider derivation builds maps by looping graph nodes and edges, which is fine as a first materialization step, but it should be cached as a view for the rest of the pass pipeline. 

Use versioned memoization:

```ts id="h2y23e"
class ViewCache {
  get<T>(graphVersion: number, viewId: string, build: () => T): T;
}
```

Cache key:

```txt id="4nsov0"
graph.version
pass.id
view.id
optional target dialect id
```

# 8. Use incremental indexes, not recomputed indexes

During graph building:

```ts id="equz2n"
writer.addNode(node);
writer.addEdge(edge);
```

should update both canonical storage and indexes:

```ts id="hvnp6i"
addEdge(edge) {
  edges.set(edge.id, edge);
  index.edgesByKind.add(edge.kind.id, edge.id);

  for (const ep of edge.endpoints) {
    index.incidentEdgesByRef.add(ep.target.id, edge.id);
    index.edgesByKindAndEndpoint.add(edge.kind.id, ep.role.id, ep.target.id, edge.id);

    if (ep.direction === "source") {
      index.outgoingByRef.add(ep.target.id, edge.id);
      index.outgoingByKind.add(ep.target.id, edge.kind.id, edge.id);
    }

    if (ep.direction === "target") {
      index.incomingByRef.add(ep.target.id, edge.id);
      index.incomingByKind.add(ep.target.id, edge.kind.id, edge.id);
    }
  }
}
```

Do not build the whole index from scratch after every graph step.

For immutable snapshots, use:

```txt id="yshuwi"
mutable writer
  -> freeze/snapshot
  -> pass pipeline reads frozen graph
```

This matches the bridge note: in-place attachment exists because copy-on-write registration is too expensive during dual-write builder paths, while copy-on-write is more appropriate for pass snapshots.

# 9. Prefer bulk graph construction

Avoid this for large graphs:

```ts id="9e4q1y"
graph = registerNode(graph, a);
graph = registerNode(graph, b);
graph = registerEdge(graph, e1);
graph = registerEdge(graph, e2);
```

Current `register*` helpers clone the corresponding map on each call, which is simple but can become expensive for builders that emit many nodes/edges. 

Prefer:

```ts id="fwtn3r"
const graph = kernel.graph.build((w) => {
  w.add(User);
  w.add(canArchiveUser);
  w.add(archiveUser);
  w.edge(app.edges.guards, { rule: canArchiveUser, action: archiveUser });
  w.edge(app.edges.writes, { action: archiveUser, field: User.fields.archivedAt });
});
```

The writer mutates internally, updates indexes, then freezes:

```ts id="mntl8x"
const frozen = writer.freeze();
```

This gives good build performance without exposing mutation as the public model.

# 10. Add derived edge indexes for common compiler questions

Some traversals are so central that they deserve dedicated derived indexes.

For reactivity:

```ts id="q9fpwq"
readsByReader: Map<RefId, Set<RefId>>;
readersByField: Map<FieldRefId, Set<RefId>>;

writesByWriter: Map<RefId, Set<RefId>>;
writersByField: Map<FieldRefId, Set<RefId>>;

queriesByFieldRead: Map<FieldRefId, Set<QueryRefId>>;
actionsByFieldWrite: Map<FieldRefId, Set<ActionRefId>>;
keysByQuery: Map<QueryRefId, Set<KeyFamilyRefId>>;
```

Then invalidation planning becomes:

```txt id="yxqzoj"
for each written field:
  find queries reading that field
  find keys/resources for those queries
  derive invalidation/patch
```

not:

```txt id="uswlaj"
for each action:
  scan all queries
  scan all rule expressions
  compare dependencies
```

For operations:

```ts id="7g05pm"
operationsByTrait: Map<TraitId, Set<OperationRefId>>;
operationsByInputType: Map<TypeRefId, Set<OperationRefId>>;
operationsByOutputType: Map<TypeRefId, Set<OperationRefId>>;
operationLoweringsByTarget: Map<TargetId, Map<OperationRefId, LoweringRefId>>;
```

For UI:

```ts id="0h1r5m"
slotsByView: Map<ViewRefId, Map<SlotName, SlotRefId>>;
behaviorsBySlot: Map<SlotRefId, Set<BehaviorRefId>>;
stylesBySlot: Map<SlotRefId, Set<StyleRefId>>;
componentsByView: Map<ViewRefId, Set<ComponentRefId>>;
```

For providers:

```ts id="85jnlx"
providersByRequirementKey: Map<RequirementKey, Set<ProviderRefId>>;
requirementsByConsumer: Map<RefId, Set<RequirementRefId>>;
providersByScope: Map<ScopeRefId, Set<ProviderRefId>>;
```

These should be built as **views**, not necessarily permanent core indexes.

# 11. Keep provenance and location out of hot indexes

Every fact should carry provenance and location, but do not index every provenance field by default.

Default hot indexes:

```txt id="8pq2qk"
id
kind
trait
protocol
endpoint target
endpoint role
direction
dialect
```

Optional/debug indexes:

```txt id="qybd1u"
source file
prompt span
provenance kind
generatedBy pass
artifact path
diagnostic code
```

Build optional indexes only for devtools, diagnostics, or agent-diff modes.

---

# 12. Use dense numeric IDs internally if graphs get large

The public API should keep stable string IDs/refs.

Internally, you can map them to dense integers:

```ts id="hblglc"
type RefId = string;
type DenseId = number;

stringToDense: Map<RefId, DenseId>;
denseToString: string[];
```

Then hot indexes can store:

```ts id="dcu4il"
Uint32Array
Set<number>
RoaringBitmap-like sets later
```

You do not need this immediately. Start with `Map<string, Set<string>>`. But design the graph index boundary so dense IDs can be added later without rewriting public APIs.

---

# 13. Traversal should be role-aware

For hyperedges, “neighbor” is not enough.

You need:

```ts id="0m60t3"
graph.from(action).via(app.edges.writes).targets("field");
graph.to(field).via(app.edges.writes).sources("action");

graph.from(view).via(ui.edges.viewExposesSlot).targets("slot");
graph.from(behavior).via(ui.edges.attachesToSlot).targets("slot");

graph.from(rule).via(rule.edges.reads).targets("field");
```

A generic neighbor traversal is okay for devtools, but compiler passes should almost always be role-specific.

This avoids accidental traversal explosions like:

```txt id="lqqe4t"
Action -> Writes edge -> Field -> OwnsField edge -> Entity -> OwnsField edge -> every field
```

when the pass only wanted written fields.

---

# 14. Passes should declare the indexes/views they need

Pass definition:

```ts id="l1nb7m"
const deriveInvalidation = definePass({
  id: "reactivity.deriveInvalidation",

  reads: {
    nodes: [query.nodes.query, action.nodes.action],
    edges: [
      callable.edges.queryReads,
      callable.edges.actionWrites,
      reactivity.edges.derivesKey,
    ],
    traits: [operation.traits.patchable],
    views: [reactivityViews.readWriteIndex],
  },

  writes: {
    edges: [reactivity.edges.invalidatesKey],
    nodes: [reactivity.nodes.optimisticPlan],
  },

  run(ctx) {
    const rw = ctx.view(reactivityViews.readWriteIndex);
    // ...
  },
});
```

This lets the pass engine:

```txt id="7gkh94"
build only needed views
cache views across passes
invalidate views only when relevant edge/node kinds changed
schedule passes by declared dependencies
parallelize independent passes later
```

---

# 15. Use delta-aware invalidation for pass caches

Each graph write should record a delta:

```ts id="fhkva9"
type GraphDelta = {
  addedNodesByKind: Map<NodeKindId, Set<NodeId>>;
  addedEdgesByKind: Map<EdgeKindId, Set<EdgeId>>;
  removedNodesByKind: Map<NodeKindId, Set<NodeId>>;
  removedEdgesByKind: Map<EdgeKindId, Set<EdgeId>>;
  changedTraitsByObject: Set<RefId>;
};
```

Then a cached view can say:

```ts id="m8b0v5"
isInvalidatedBy(delta) {
  return delta.touchesEdgeKind(app.edges.writes)
      || delta.touchesEdgeKind(app.edges.reads)
      || delta.touchesNodeKind(app.nodes.query);
}
```

This matters once pipelines start deriving more facts in stages:

```txt id="kokxn4"
verify -> derive reads -> derive invalidation -> derive optimistic plans -> legalize target
```

---

# 16. Recommended traversal cost model

Design for these approximate complexities:

| Query                          |                          Desired cost |
| ------------------------------ | ------------------------------------: |
| node by id                     |                                `O(1)` |
| edge by id                     |                                `O(1)` |
| nodes of kind                  | `O(k)` where `k = nodes of that kind` |
| edges of kind                  | `O(k)` where `k = edges of that kind` |
| edges from node                |                     `O(degree(node))` |
| edges from node of kind        |               `O(degree(node, kind))` |
| edge by kind + role + endpoint |                          `O(matches)` |
| fields of entity               |                       `O(fieldCount)` |
| queries reading field          |                   `O(readers(field))` |
| actions writing field          |                   `O(writers(field))` |
| slot behaviors                 |                  `O(behaviors(slot))` |
| provider for requirement       |        `O(providers(requirementKey))` |
| target lowerings for operation |      `O(lowerings(operation,target))` |

Avoid any hot query that is:

```txt id="upk9gn"
O(all nodes)
O(all edges)
O(all expressions)
O(all passes)
```

unless it is a one-time index/view build.

---

# 17. File format: adjacency-oriented snapshot

For serialized graph artifacts, store canonical objects plus optional precomputed indexes.

```json id="gp0wul"
{
  "version": 1,
  "nodes": [...],
  "edges": [...],
  "types": [...],
  "exprs": [...],

  "indexes": {
    "optional": true,
    "nodesByKind": {...},
    "edgesByKind": {...},
    "incidentEdgesByRef": {...}
  }
}
```

On load:

```txt id="brfkmb"
if index exists and schema version matches:
  validate cheaply and use
else:
  rebuild index from canonical graph
```

Never trust serialized indexes without validating version/hash.

---

# 18. Practical implementation order

I would implement performance in this order:

```txt id="jagsyv"
1. Add GraphIndex with nodesByKind, nodesByTrait, edgesByKind.
2. Add incidentEdgesByRef.
3. Add edgesByKindAndEndpoint.
4. Replace nodesOfKind / edgesOfKind / edgesFrom / edgesTo with index-backed versions.
5. Replace prefix-based direction with endpoint direction metadata.
6. Add GraphWriter that updates indexes incrementally.
7. Add GraphView cache keyed by graph.version.
8. Add dialect views for domain, callable, reactivity, UI, provider.
9. Add pass-declared reads/writes/views.
10. Add graph deltas for incremental pass cache invalidation.
```

This sequence gives immediate wins without overengineering.

---

# The compact rule

The best performance model is:

```txt id="y38cd3"
Canonical graph:
  simple, normalized, serializable.

Indexes:
  kind, trait, protocol, endpoint, direction, dialect.

Views:
  materialized dialect-specific query surfaces.

Passes:
  declare what they read/write and consume views.

Traversal:
  role-aware, index-backed, bounded, no global scans in hot paths.

Mutation:
  bulk writer updates graph and indexes, then freezes snapshots.
```

That keeps the semantic graph flexible while making compiler passes fast enough to run repeatedly during generation, diagnostics, AI repair, devtools inspection, and target emission.
